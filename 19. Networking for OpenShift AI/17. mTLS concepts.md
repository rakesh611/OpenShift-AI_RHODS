# 17. mTLS concepts

> Corporate/L3 deep-dive guide for experienced Linux, Kubernetes, OpenShift, DevOps, SRE, and platform engineers.
>
> Primary baseline: Red Hat OpenShift AI Self-Managed 3.4 with a supported modern OpenShift Container Platform release using OVN-Kubernetes. Commands and CRD fields must be validated against the exact versions installed in the target cluster.

## Purpose and expected outcome

This guide explains how to protect service-to-service AI traffic with mutual identity and encrypted transport.
It treats networking as an end-to-end system rather than a single YAML object. The reader will build a
practical project from scratch, validate each traffic hop, apply least privilege, create observability, inject
failures, and produce an enterprise support runbook.

**Capstone project:** Enforce strict mTLS between a client and model service, then demonstrate and repair a policy mismatch.

## How to use this guide

1. Read the architecture chapters before applying manifests.
2. Replace every ${PLACEHOLDER} with values from a non-production lab first.
3. Capture command output before and after each change.
4. Commit manifests to Git and use peer review for production changes.
5. Treat private keys, tokens, S3 credentials, and proxy credentials as secrets.
6. Verify the exact Red Hat support matrix for the installed OpenShift AI and OpenShift versions.
7. Do not copy a legacy OpenShift SDN procedure into an OVN-Kubernetes cluster without checking semantics.
8. Use least privilege for RBAC and network access.
9. Prefer deterministic evidence over restarts.
10. Record all deviations from the corporate baseline.

## Learning objectives

- Explain mTLS concepts using control-plane and data-plane terminology.
- Map OpenShift AI user actions to Kubernetes and OpenShift resources.
- Trace traffic from source process to destination process.
- Create a reproducible lab and production-ready design.
- Validate DNS, TCP, TLS, HTTP, authentication, authorization, and application behavior independently.
- Implement NetworkPolicy, egress controls, proxy rules, and certificate trust safely.
- Diagnose failures without weakening security.
- Create operational dashboards, alerts, and runbooks.
- Prepare audit evidence and change records.
- Mentor L1 and L2 engineers using a decision-tree approach.

## Terminology and key objects

### 1. PeerAuthentication

In the context of mTLS concepts, **PeerAuthentication** is a resource or concept that must be included in
discovery and troubleshooting. An L3 engineer does not assume it is correct merely because it exists. Inspect
its desired state, status, owner references, labels, selectors, events, and relationship to adjacent
resources.

- Discovery question: Which controller creates or reconciles `PeerAuthentication`?
- Dependency question: Which of workload identity, client certificate, server certificate, trust root depends on `PeerAuthentication`?
- Security question: Which identities may read, create, update, or use it?
- Failure question: How does a broken value appear to the client?
- Evidence question: Which YAML fields and logs prove its actual behavior?

## Architecture: control plane, data plane, and trust boundaries

### Component 1: workload identity

Role: workload identity participates in mTLS concepts. Determine whether it makes decisions, carries packets,
terminates TLS, enforces policy, stores state, or reports status.

Ownership: identify the operator, namespace, deployment, daemonset, or external team responsible for workload
identity. Production incidents become longer when ownership is unclear.

Inputs: list configuration objects, Secrets, ConfigMaps, labels, selectors, certificates, and environment
variables consumed by workload identity.

Outputs: list Services, routes, endpoints, logs, metrics, status conditions, and network connections produced
by workload identity.

Security boundary: document which identities can reach workload identity, what authentication it performs, and
whether traffic is plaintext, TLS, or mTLS.

Availability boundary: document replica count, node placement, disruption budget, health checks, and
dependencies for workload identity.

Troubleshooting evidence: capture status, recent events, logs around the failure timestamp, and one
packet-level or request-level proof when permitted.

  name: ${MODEL}
  namespace: ${CLIENT_PROJECT}

  host: ${MODEL_SERVICE}.${PROJECT}.svc.cluster.local

    tls:
      mode: ISTIO_MUTUAL

- Confirm no secret value is committed to Git.
- Confirm all ports are named consistently.
- Confirm TLS material comes from an approved issuer.
- Confirm selectors do not unintentionally match unrelated workloads.
- Confirm rollback is a Git revert or known oc operation.
- Run server-side dry-run before apply.

## Troubleshooting methodology

1. Confirm the exact source namespace, pod, container, and ServiceAccount.
2. Confirm the exact destination hostname, IP, port, protocol, and HTTP path.
3. Capture timestamps in UTC so logs from different components can be correlated.
4. Test from the failing pod, not only from an administrator workstation.
5. Record whether failure is deterministic, intermittent, node-specific, or load-dependent.
6. Separate DNS, TCP, TLS, HTTP, authentication, authorization, and application stages.
7. Inspect object status conditions before reading large log volumes.
8. Check Services and EndpointSlices before restarting workloads.
9. Validate NetworkPolicy selectors against current labels.
10. Validate EgressFirewall rule ordering and destination resolution.
11. Inspect effective proxy and noProxy environment inside the actual container.
12. Verify certificate subject alternative names, issuer, chain, and expiration.
13. Compare internal and external endpoint behavior using the same request body.
14. Check readiness and liveness probes separately from process state.
15. Avoid broad RBAC grants as a diagnostic shortcut.
16. Avoid disabling TLS verification as a production workaround.
17. Collect a before-and-after evidence set for every change.
18. Roll back one change at a time when causality is uncertain.
19. Use packet capture only with authorization and a narrow filter.
20. Close the incident with a permanent control, not only a restart.

Context: this scenario is analyzed through the lens of mTLS concepts. The same user-visible symptom can
originate at several layers, so the investigation must preserve evidence and test the path in order.

### Triage questions
1. When did the failure start, and what changed immediately before it?
2. Which exact clients fail, and which exact clients succeed?
3. Is the problem namespace-specific, node-specific, model-specific, or cluster-wide?
4. Does internal access behave differently from external access?
5. Does the request fail before or after authentication?
6. Do Service endpoints exist and show ready conditions?
7. Which network and security policies apply to the source and destination?
8. Is the proxy or noProxy path expected?
9. Does TLS verification fail, or does the backend return an HTTP status?
10. What are DNS, connect, TLS, time-to-first-byte, and total timings?

### Investigation sequence
1. Reproduce once with a timestamped verbose client request.
2. Resolve the destination from the failing client pod.
3. Verify the expected IP, port, and network path.
4. Inspect Route or Gateway admission when external traffic is involved.
5. Inspect Service selectors and EndpointSlices.
6. Inspect pod readiness, restarts, resource throttling, and logs.
7. Inspect authentication and authorization decisions.
8. Inspect NetworkPolicy, EgressFirewall, mesh policy, and external firewall rules.
9. Inspect TLS chain and CA bundle.
10. Compare with a known-good client or node.
11. Apply one minimal repair and retest all layers.
12. Document root cause, contributing factors, and prevention.

### Acceptance criteria
- The expected client succeeds with normal certificate verification.
- An unauthorized client remains denied.
- No unrelated tenant receives broader access.
- Latency and error rate return to baseline.
- The fix survives pod restart and reconciliation.
- Monitoring detects recurrence.

## Security and compliance controls

1. Default-deny ingress and egress where operationally validated.
2. Explicit DNS access rather than broad egress.
3. ServiceAccount identity for automation; no shared human tokens.
4. Namespace-scoped RoleBindings for model access.
5. TLS verification with approved enterprise or public roots.
6. mTLS when workload identity and encryption are required end to end.
7. Secrets stored in Kubernetes Secrets or approved external secret managers.
8. No credentials in command history, Git, notebooks, or pipeline logs.
9. Egress allowlists for S3, Git, registries, and approved APIs.
10. External endpoints protected by authentication, authorization, rate limits, and audit logs.
11. Certificate and token rotation tested before production rollout.
12. Network changes peer-reviewed and represented as code.
13. Administrative access separated from application access.
14. Packet capture restricted, approved, filtered, and securely stored.
15. Audit evidence retained according to policy.
16. Emergency access time-bound and removed after the incident.
17. No production use of curl -k or TLS skip verification.
18. No permanent allow-all policy used as a workaround.
19. Regular access review for client namespaces and ServiceAccounts.
20. Threat modeling for model theft, data exfiltration, prompt leakage, and denial of service.

## High availability, disaster recovery, and lifecycle

1. Place routers, gateways, and critical proxies across failure domains.
2. Use readiness probes that represent real backend availability.
3. Define PodDisruptionBudgets where supported and meaningful.
4. Test node drain and zone failure for endpoint continuity.
5. Back up Git manifests, Secrets through approved mechanisms, and custom CA bundles.
6. Record external DNS, load balancer, firewall, and certificate dependencies outside the cluster.
7. Test certificate rotation and trust-bundle propagation.
8. Test proxy outage and define approved direct-access exceptions only where required.
9. Document RTO and RPO for pipeline metadata, model artifacts, and configuration.
10. Validate routes and internal Services after cluster upgrade.
11. Review deprecated APIs and behavior changes before upgrades.
12. Capture a known-good baseline after every production release.
13. Use canary or staged rollout for policy and mesh changes.
14. Rehearse rollback of NetworkPolicy, EgressFirewall, proxy, and TLS changes.
15. Keep an offline copy of critical runbooks for disconnected incidents.
