## 3. Product facts and support-aware boundaries
- In a new OpenShift AI 3.5 installation, the modelregistry component is enabled by default; an upgraded environment might require explicit enablement if the component was not previously enabled.
- The standard registries namespace shown in current Red Hat documentation is rhoai-model-registries.
- The registry stores model metadata in a relational database and references the location of model artifacts.
- The default PostgreSQL database option is intended for evaluation, development, and testing, not supported production use.
- Current Red Hat documentation identifies external PostgreSQL 16.x or MySQL for production registry database use; verify the exact supported matrix for the installed release.
- A registered model can contain multiple versions. Model and version metadata can include descriptions, labels, custom properties, owner or author, format, location, and timestamps.
- OpenShift AI 3.5 can register metadata for an existing artifact or start a model-transfer Kubernetes Job that packages model files as a ModelCar-compatible OCI image.
- Registry access is implemented through OpenShift RBAC and can be assigned to users, groups, and service accounts associated with a project.
- The registry is a passive metadata repository, not a Kubernetes orchestration control plane. Pipelines and serving systems act on information retrieved from it.
- Models or model versions with active deployments must have those deployments removed before archival in the documented dashboard workflow.
## 4. Architecture deep dive
### 4.1 Logical architecture
```text
Users / Pipelines / Automation
          |
          v
OpenShift AI Dashboard and Registry API
          |
          +---------------------> OpenShift RBAC / OAuth identity
          |
          +---------------------> Relational metadata database
          |
          +---------------------> S3-compatible object storage URI
          |
          +---------------------> OCI registry / ModelCar URI
          |
          +---------------------> KServe model-serving workflow
          |
          +---------------------> Audit, monitoring, backup, governance
```
- OpenShift AI dashboard provides the administrative and user-facing registry workflows.
- The modelregistry component is managed through the DataScienceCluster resource and is enabled by default on a new OpenShift AI 3.5 installation.
- Registry workloads and instance-specific RBAC resources are associated with the rhoai-model-registries namespace.
- The registry service is a metadata repository; it is not an orchestration control plane for Kubernetes workloads.
- The metadata backend is a relational database. The default database is for evaluation and non-production use only.
- Production designs should use a supported external PostgreSQL or MySQL database with TLS, backup, monitoring, and high availability appropriate to the business requirement.
- Model artifacts remain in object storage, an OCI registry, or another supported URI location; the registry records the location and metadata.
- Registered models contain one or more versions. Each version can reference an artifact and include format, description, labels, properties, and deployment information.
- OpenShift RBAC controls user, group, and project service-account access to each registry instance.
- OpenShift AI can deploy a registered model version through the model-serving workflow and track deployments initiated from the registry.
### 4.2 Control-plane versus data-plane thinking
- Registry metadata describes what a model is, where its artifact exists, who owns it, which version is approved, and where it was deployed.
- The artifact data plane carries large model binaries and must be designed for throughput, integrity, encryption, versioning, and retention.
- The serving data plane loads the artifact into a runtime and exposes inference endpoints; its availability and performance are separate from registry availability.
- Pipelines provide orchestration and automation. They should treat registry operations as idempotent, evidence-producing steps.
- The database is a critical metadata dependency. Its backup, recovery, TLS, capacity, and maintenance must be part of the platform design.
## 5. Domain model and terminology
- **Registry instance:** An independently configured registry service and metadata database connection with its own access scope.
- **Registered model:** The stable logical identity of a model family, such as fraud-classifier.
- **Model version:** A specific immutable release or candidate under the registered model.
- **Model artifact:** The physical model files referenced by a URI, commonly in S3-compatible object storage or an OCI registry.
- **Model format:** The serialization or framework format used to select or validate an appropriate serving runtime.
- **Labels:** Searchable classifications used for discovery and operational grouping.
- **Custom properties:** Key-value metadata used to record governance, lineage, evaluation, support, and automation information.
- **Deployment record:** The link between a registered version and a model-serving deployment initiated from the registry workflow.
- **Archive state:** A reversible lifecycle state that removes a model or version from normal use without treating it as an active candidate.
- **Model catalog:** A read-only discovery and curation layer that is distinct from the writable model registry.

## 8. Project from scratch
### Project: Build a dev-test-prod model delivery blueprint
**Goal:** Create environment namespaces, service accounts, registry permissions, promotion rules, object-storage prefixes, and deployment validation for each stage.
### Phase 1 - Define acceptance criteria
1. Write the business outcome, in-scope environments, owners, risk tier, data classification, and service-level expectations.
2. Define success criteria specifically for Dev test prod model flow.
3. Define rollback criteria before implementation begins.
4. Record which controls are mandatory and which require formal exceptions.
### Phase 2 - Validate platform readiness
1. Confirm OpenShift and OpenShift AI versions are supported together.
2. Confirm the OpenShift AI operator and DataScienceCluster report healthy status.
3. Confirm the modelregistry component is Managed and the registry operator pod is Running.
4. Confirm DNS, network, and TLS paths to the external database, object storage, and OCI registry.
### Phase 3 - Prepare identity and namespaces
1. Create or validate team groups and group membership through the enterprise identity provider.
2. Create the project namespaces and dedicated service accounts.
3. Apply resource quotas, LimitRanges, NetworkPolicies, and approved security context controls.
4. Document who can administer registry instances and who can use each registry.
### Phase 4 - Provision the metadata database
1. Create a dedicated database and least-privilege database account.
2. Enable TLS, backup, monitoring, capacity alerts, and log retention.
3. Test authentication and certificate validation from an approved cluster workload.
4. Record the backup and recovery owner, RPO, RTO, and maintenance window.
### Phase 5 - Create the registry instance
1. Use OpenShift AI dashboard: Settings -> Model resources and operations -> Model registry settings.
2. Create a unique human-readable name and immutable Kubernetes resource name.
3. Select the external database and configure host, port, user, password, database name, and CA certificate.
4. Wait for reconciliation and confirm the instance is available before granting access.
### Phase 6 - Configure least-privilege access
1. Grant access to approved OpenShift groups rather than broad cluster-wide groups.
2. Grant project service-account access only to namespaces that run approved pipelines or transfer jobs.
3. Use oc auth can-i and a real negative test to prove denied access.
4. Capture role and role-binding evidence for the change record.
### Phase 7 - Prepare immutable artifact storage
1. Create a versioned object-storage prefix or an OCI repository.
2. Upload the model under a unique version path and calculate a SHA-256 digest.
3. Apply encryption, retention, replication, and access policies.
4. Verify that the intended pipeline or serving service account can read the artifact without write access when write is unnecessary.
### Phase 8 - Register the model and first version
1. Open AI hub -> Registry and select the target registry.
2. Register the model with a stable model name and a unique version name.
3. Specify model format, format version, artifact location, description, labels, and required custom properties.
4. Validate that the model and version appear in search and that the artifact URI is correct.
### Phase 9 - Automate validation and evidence
1. Create a pipeline step that validates metadata completeness, artifact existence, checksum, and evaluation threshold.
2. Make the registration operation idempotent and fail safely on a duplicate or conflicting version.
3. Attach pipeline run, source commit, dataset version, test evidence, and approval references.
4. Store logs and evidence in a controlled retention location.
### Phase 10 - Integrate serving and operations
1. Deploy the approved version through the registry workflow into a non-production project.
2. Validate storage connection matching, ServingRuntime compatibility, resource sizing, endpoint health, and inference response.
3. Record deployment identity, environment, time, change reference, and rollback version.
4. Enable monitoring and create alerts for service health, latency, error rate, resource saturation, and dependency failures.
### Phase 11 - Test lifecycle operations
1. Register a second version and compare metadata and evaluation results.
2. Promote the selected version using defined approval properties and deployment controls.
3. Execute a rollback test to the previous known-good version.
4. Remove test deployments, archive an obsolete version, restore it, and verify history is preserved.
### Phase 12 - Close with governance evidence
1. Complete security, platform, MLOps, model-risk, and application-owner reviews.
2. Attach validation output, access evidence, backup evidence, runbooks, and rollback proof.
3. Record residual risks and time-bound exceptions.
4. Schedule ownership, access, metadata, backup, and lifecycle reviews.

## 11. Versioning and immutability standard
- Never silently replace the bytes referenced by an approved version.
- Use a unique model-version identifier and an immutable artifact digest.
- Record source code commit, dependency lockfile or image digest, training configuration, dataset version, and evaluation evidence.
- Treat a retrained model as a new version even when the algorithm family is unchanged.
- Separate model semantic version from build metadata when multiple rebuilds are possible.
- Document input and output schema compatibility and preprocessing dependencies.
- Use OCI digests rather than mutable tags for production deployment whenever the supported serving pattern allows it.
- Use object version IDs, retention lock, or a write-once prefix policy for S3-compatible storage.
- Do not edit historical approval facts to represent a new decision; create a new decision property or evidence record.
- Define a version-retention policy that preserves audit and rollback requirements.

### Idempotency rules
- Query the model and version before creation.
- If a version exists with the same digest and metadata, return success without creating a duplicate.
- If a version exists with a different digest, fail and require a new version identifier.
- Use bounded retries only for transient network or 5xx failures.
- Do not retry authorization failures until RBAC is corrected.
- Write a structured result containing model ID, version ID, artifact URI, digest, actor, and timestamp.
- Emit evidence to the pipeline artifact store or approved log destination.

## 15. Security hardening
- Use enterprise identity groups; avoid individual bindings except for temporary, justified cases.
- Do not grant system:authenticated access to a production registry.
- Use dedicated service accounts for pipelines, transfer jobs, and serving; do not reuse personal tokens.
- Store database and storage credentials in Secrets and rotate them through an approved process.
- Use TLS for database, registry API, object storage, and OCI registry connections.
- Limit network paths with NetworkPolicy and external firewall controls.
- Use immutable artifacts, checksums, signed commits, image signatures, or approved provenance mechanisms.
- Scan custom pipeline and transfer images for vulnerabilities and pin by digest.
- Prevent secrets, personal data, or confidential samples from being written into labels and custom properties.
- Separate production approval and deployment authority from model development where risk requires it.
- Log administrative, registration, metadata, approval, archival, restore, and deployment actions.
- Review access, ownership, secrets, certificates, and exceptions on a defined schedule.

## 17. Backup and disaster recovery
- Back up the external relational database using database-native, application-consistent methods.
- Enable point-in-time recovery when required by RPO and supported by the database platform.
- Export registry-related OpenShift configuration, RBAC, certificate references, and non-secret inventory.
- Back up or inventory the secrets through an approved cluster backup solution; never store plaintext secrets in Git.
- Maintain an artifact inventory containing URI, version ID, digest, object version, retention, and replication status.
- Back up model artifacts according to their own storage policy; a database backup alone does not protect model binaries.
- Encrypt backups, restrict access, and maintain off-site or cross-failure-domain copies.
- Test restoration into an isolated environment and validate model search, version history, access, artifact retrieval, and deployment.
- Record RPO, RTO, restore order, owners, dependencies, and rollback steps.
- Perform periodic game days and close every finding with an owner and due date.
### Restore order
1. Declare incident or planned recovery and freeze conflicting writes.
2. Provision compatible OpenShift AI and database prerequisites.
3. Restore database and validate schema, users, and integrity.
4. Restore registry instance configuration, CA material, secrets, and RBAC through approved mechanisms.
5. Allow operator reconciliation and confirm service health.
6. Validate user and service-account access.
7. Validate model, version, metadata, and archive history.
8. Validate every critical artifact URI and checksum.
9. Deploy a test model version and run inference.
10. Complete business and technical sign-off before reopening normal changes.
## 18. Observability and SLO design
| Signal | Measurement | Example objective |
|---|---|---|
| Registry API availability | Successful authenticated request ratio | 99.9% monthly or business-defined |
| Read latency | p95 model/version lookup latency | Business-defined based on pipeline and dashboard needs |
| Write success | Successful register/update operations | Alert on sustained failure ratio |
| Database health | Connectivity, replication, storage, locks, latency | No data-loss condition and capacity headroom |
| Operator health | Ready replicas and reconciliation errors | No sustained degraded state |
| Transfer jobs | Pending time, success ratio, duration | Threshold based on artifact size and network |
| Artifact validity | URI reachability and checksum validation | 100% for approved active versions |
| Audit completeness | Events with actor, action, object, result, timestamp | 100% for controlled actions |
### Alert principles
- Alert on user-impacting symptoms and critical dependency failures, not every transient log line.
- Include registry instance, namespace, environment, severity, owner, runbook link, and correlation context.
- Route database alerts to the database owner and platform integration alerts to the OpenShift AI platform owner.
- Test alerts during game days and verify acknowledgement and escalation paths.
- Measure backup age and restore-test age as operational signals.
## 19. Troubleshooting methodology
1. State the symptom, start time, affected registry, affected users or service accounts, environment, and business impact.
2. Preserve evidence before restarts, edits, or deletions.
3. Separate dashboard, identity, registry API, operator, database, storage, transfer job, and serving layers.
4. Check recent changes, certificate rotation, secret rotation, database maintenance, network policy, and upgrades.
5. Use negative and positive tests with exact identities.
6. Change one variable at a time and record the outcome.
7. Prefer declarative correction and operator reconciliation over manual mutation of managed resources.
8. Validate both service recovery and data integrity.
9. Document root cause, contributing factors, detection gap, recovery, and preventive actions.

## 22. Operational runbook
1. Confirm incident severity and business impact.
2. Identify registry instance, environment, owners, and affected workflows.
3. Freeze unsafe writes or promotions when data integrity is at risk.
4. Capture operator, registry namespace, project, and database evidence.
5. Validate identity and RBAC for the affected actor.
6. Validate database reachability, TLS, credentials, capacity, and recent maintenance.
7. Validate artifact storage reachability, credentials, URI, checksum, and retention status.
8. Validate pipeline or transfer job resources and events.
9. Validate serving runtime compatibility and deployment objects.
10. Apply the smallest safe corrective change.
11. Repeat the original transaction and a read-back validation.
12. Confirm no metadata, artifact, or deployment history was lost.
13. Remove temporary access or diagnostic resources.
14. Document root cause and preventive actions.
15. Update monitoring, tests, runbook, and training materials.

- **Situation:** A change affecting development namespace is proposed in the lab environment for dev test prod model flow.
- **Risk:** Shared credentials across environments could create availability, integrity, security, compliance, or operational impact.
- **Design task:** define architecture, data flow, RBAC, metadata, artifact handling, failure domains, and recovery for development namespace.
- **Implementation task:** provide dashboard steps, discovery-first `oc` commands, automation approach, and safe validation.
- **Control task:** specify preventive, detective, corrective, and recovery controls with evidence retention.
- **Owner:** Platform administrator; identify consulted and informed stakeholders using a RACI.
- **Test:** perform a positive test, negative authorization test, dependency failure test, rollback test, and post-recovery integrity test.
- **Evidence:** attach versioned configuration, command output, logs, metrics, approval reference, artifact digest, test result, and closure record.
