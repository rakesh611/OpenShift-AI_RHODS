## 3. Enterprise reference architecture
```text
Users / Pipelines / Applications
             |
             | OAuth-authenticated API calls and inference traffic
             v
OpenShift Route -> OAuth Proxy -> TrustyAI Service
                                  |
                +-----------------+------------------+
                |                                    |
                v                                    v
         PVC or MariaDB                    Metric computation engine
                |                                    |
                v                                    v
      Captured reference/live data          Prometheus metric exposure
                                                     |
                                                     v
                                     OpenShift Monitoring / Dashboard
                                                     |
                                                     v
                                   Alerting, incident and governance flow

Supported model path in the 3.5 monitoring guide:
Client -> KServe/OVMS model endpoint -> inference data integration -> TrustyAI
```

### Component responsibilities

| Component | Responsibility | L3 checks |
|---|---|---|
| Red Hat OpenShift AI Operator | Reconciles OpenShift AI components | DataScienceCluster conditions, CSV, operator logs |
| TrustyAI service operator | Watches TrustyAIService CRs and creates service resources | CR status, generated Deployment, Service, Route, ServiceMonitor |
| TrustyAI Service | Receives data, stores observations, calculates metrics, exposes API | health, logs, API responses, resource usage |
| OAuth proxy | Protects external endpoints | token, RBAC, redirects, headers, certificates |
| OVMS model serving | Supported tabular-model inference runtime path | model readiness, schema, input/output names, inference logs |
| PVC or MariaDB | Stores captured monitoring data | capacity, latency, backup, permissions, connectivity |
| Prometheus stack | Scrapes and stores monitoring metrics | targets, labels, query latency, retention |
| OpenShift AI dashboard | Provides model metric views | project/model selection, permissions, time range |
| Alertmanager / incident system | Routes actionable threshold breaches | ownership, severity, inhibition, escalation |
| Governance repository | Stores model cards, approvals, thresholds, evidence | versioning, access, retention, audit trail |

### Data-state model

1. **Training/reference data:** A governed representation of expected feature distributions.
2. **Live inference data:** Inputs and outputs captured from production or controlled tests.
3. **Metadata:** Model identifier, version, feature names, output names, tags, timestamps, and tenant.
4. **Metric definition:** Algorithm, protected attribute or feature, favorable outcome, reference tag, schedule, and window.
5. **Metric result:** Numeric value plus labels and time.
6. **Threshold state:** Normal, warning, critical, unknown, or insufficient-data.
7. **Decision evidence:** Investigation, owner, corrective action, approval, and closure.

- **Interpretation:** Values near zero indicate parity; direction and threshold must be interpreted with sample size and policy context.

## 12. L3 troubleshooting methodology
Use this order to avoid random changes:

1. Confirm scope: cluster, project, model, version, start time, user, and change history.
2. Reproduce with one minimal request and capture HTTP status and body.
3. Check custom-resource status and operator reconciliation.
4. Check generated Kubernetes resources, events, readiness, and endpoints.
5. Check route, OAuth proxy, certificates, DNS, Service, and NetworkPolicy.
6. Check PVC or MariaDB health, capacity, credentials, schema, and latency.
7. Check data contract: model ID, input/output names, types, shapes, tags, and timestamps.
8. Check metric definition, schedule, batch/window, reference data, and sample count.
9. Check Prometheus target, metric exposition, labels, cardinality, and time range.
10. Correlate with recent releases, schema changes, threshold changes, and infrastructure incidents.
11. Apply the smallest reversible change.
12. Verify recovery, remove temporary access, and complete root-cause evidence.

- **Observed symptom:** The trustyai-service-operator-controller-manager deployment is unavailable.
- **Primary approach:** Check DataScienceCluster managementState, operator namespace events, image pulls, CSV health, and resource pressure.
- **Name mapping hypothesis A:** Configuration or version mismatch.
- **Hypothesis B:** Kubernetes scheduling, networking, storage, or security failure.
- **Hypothesis C:** Data schema, reference-data, or metric-definition error.
- **Hypothesis D:** Monitoring discovery, query, dashboard, or time-range error.

- **Decision point:** If CR reconciliation fails, stay at operator/resource layer; if API works but metric is absent, move to data/metric/Prometheus layer.

- **Implementation:** Store code/configuration in version control and reference the exact model and environment.
- **Test:** Define positive, negative, failure, and recovery test cases.
- **Metric/evidence:** Capture measurable output, timestamp, version, and approver.
- **Exception:** Record risk acceptance, compensating control, expiry date, and reviewer.
- **Review trigger:** Reassess after release, incident, schema change, traffic change, or policy update.
## 18. Glossary
- **Bias:** Systematic difference in outcomes that can disadvantage a group or violate policy.
- **Protected attribute:** A feature used to evaluate group fairness under approved governance.
- **Privileged group:** A comparison group designated by the fairness analysis.
- **Unprivileged group:** A group evaluated for potential disadvantage relative to the privileged group.
- **Favorable outcome:** A decision or output treated as beneficial in the metric definition.
- **Data drift:** Change in live input distribution relative to a reference distribution.
- **Concept drift:** Change in the relationship between inputs and the target or outcome.
- **Reference data:** Governed baseline data used for comparison.
- **TrustyAIService:** Custom resource representing an operator-managed TrustyAI service instance.
- **OVMS:** OpenVINO Model Server, the documented supported model serving path for TrustyAI monitoring in the product guide.
- **OAuth proxy:** Authentication layer protecting external TrustyAI endpoints.
- **Name mapping:** Mapping technical input/output names to readable domain names.
- **Metric schedule:** Recurring interval for metric computation.
- **Batch size:** Historical observation window used for calculation in the PVC configuration.
- **ServiceMonitor:** Prometheus Operator resource defining a scrape target.
- **SPD:** Statistical Parity Difference.
- **DIR:** Disparate Impact Ratio.
- **MMD:** Maximum Mean Discrepancy.
- **KS test:** Kolmogorov-Smirnov distribution comparison.
- **SLO:** Service-level objective.
- **RTO:** Recovery time objective.
- **RPO:** Recovery point objective.
- **Model card:** Governance record describing intended use, limitations, validation, and ownership.
- **Hysteresis:** Different trigger and recovery boundaries to reduce alert flapping.
- **Insufficient data:** State where sample size or coverage is inadequate for reliable interpretation.
