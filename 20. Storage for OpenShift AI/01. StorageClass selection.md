# 01. StorageClass selection
> Corporate L3 / senior platform-engineering guide for administrators with approximately 10+ years of Linux, OpenShift, Kubernetes, networking, and operations experience.
**Version scope:** Red Hat OpenShift AI Self-Managed 3.5, OpenShift Container Platform 4.21, and OpenShift Data Foundation 4.x concepts. Validate exact supported combinations in the Red Hat support matrix before production changes.
**Training outcome:** Select the correct storage service level for every openshift ai workload.
---
## 1. Executive summary
StorageClass selection is treated here as a production platform capability rather than a one-time UI task. The objective is to design, implement, validate, observe, protect, troubleshoot, and govern the storage path used by OpenShift AI components and user workloads.
- Map workload I/O pattern to block, file, or object storage.
- Validate access modes, topology, expansion, snapshots, encryption, reclaim policy, and supportability.
- Separate platform defaults from OpenShift AI enabled/default storage classes.
- Use explicit storageClassName in production manifests to avoid default drift.
### 1.1 Senior-level mental model
1. Storage is a service chain: workload -> filesystem or S3 client -> kernel/network -> CSI or gateway -> backend -> protection and monitoring layers.
2. A successful PVC bind does not prove acceptable application performance, recoverability, or security.
3. A successful S3 login does not prove bucket policy correctness, large-object reliability, lifecycle safety, or disaster recovery.
4. Every design decision must be traceable to workload requirements, supported configuration, failure-domain assumptions, RPO/RTO, and an owner.
5. Production acceptance requires evidence: manifests, events, metrics, benchmarks, backup results, restore results, and operational handover.
## 2. Scope and non-goals
- In scope: select the correct storage service level for every OpenShift AI workload.
- In scope: OpenShift API objects, OpenShift AI integration, storage backend dependencies, security, observability, capacity, protection, and L3 troubleshooting.
- In scope: both dashboard workflows and declarative/API workflows where appropriate.
- Non-goal: replacing the Red Hat support matrix or vendor-specific design guide.
- Non-goal: prescribing one storage backend for every cluster.
- Non-goal: using unsupported privileged workarounds to bypass CSI, SCC, or security controls.

### 9.20 Capacity formula worksheet
- Usable PVC capacity = requested capacity - filesystem reserve - operational headroom.
- Peak required capacity = active data + checkpoints + temporary files + growth during backup window.
- Object capacity = current versions + noncurrent versions + multipart uploads + replication overhead + lifecycle delay.
- Recovery capacity must include restored copies and temporary coexistence with the failed workload.
- Alert thresholds must leave enough time for procurement, backend expansion, and data movement.

### 10.2 Alert design
- **PVC pending:** PVC is Pending beyond workload-specific threshold. Include project, PVC/bucket, storage class, node, backend, first-seen time, runbook, and owner in the alert.
- **Capacity warning:** Usage or backend fullness leaves insufficient remediation time. Include project, PVC/bucket, storage class, node, backend, first-seen time, runbook, and owner in the alert.
- **CSI errors:** Provision, attach, mount, resize, or snapshot errors exceed baseline. Include project, PVC/bucket, storage class, node, backend, first-seen time, runbook, and owner in the alert.
- **Latency SLO:** p95/p99 latency breaches agreed SLO for a sustained period. Include project, PVC/bucket, storage class, node, backend, first-seen time, runbook, and owner in the alert.
- **Object errors:** S3 4xx/5xx, timeout, or retry rates exceed baseline. Include project, PVC/bucket, storage class, node, backend, first-seen time, runbook, and owner in the alert.
- **Backup stale:** No successful backup within the RPO window. Include project, PVC/bucket, storage class, node, backend, first-seen time, runbook, and owner in the alert.
## 11. Backup, restore, and disaster recovery
1. Classify data and identify authoritative source.
2. Select crash-consistent or application-consistent method.
3. Capture Kubernetes objects, secrets references, and external dependencies.
4. Store backups outside the failure domain.
5. Encrypt and restrict backup access.
6. Monitor backup completion and retention.
7. Restore to an isolated namespace.
8. Verify checksums, permissions, schema, and application behavior.
9. Record achieved RPO/RTO.
10. Schedule recurring restore tests.

## 13. L3 troubleshooting method
### 13.1 Confirm impact
Identify affected project, workload, users, zones, nodes, PVCs/buckets, and business service.
### 13.2 Build timeline
Record first failure, alerts, deploys, upgrades, certificate changes, quota changes, and backend events.
### 13.3 Preserve evidence
Export YAML, events, logs, metrics, request IDs, and benchmark output before destructive action.
### 13.4 Localize plane
Decide whether failure is API/control plane, node/CSI, network, backend, identity/TLS, or application.
### 13.5 Test smallest hypothesis
Use a read-only or low-risk test that can disprove one cause.
### 13.6 Remediate safely
Prefer reversible and supported changes; define abort and rollback.
### 13.7 Verify original path
Re-run the failing workbench, pipeline, registry, or model operation.
### 13.8 Prevent recurrence
Add alerting, policy, validation, automation, and documentation.

## 16. Advanced operational scenarios
### 16.1 Scenario 1: reclaim-policy risk
- **Trigger:** The incident begins after a object lifecycle change.
- **Observed symptom:** The I/O latency rises only during peak training.
- **Primary hypothesis:** Dns, proxy, or no-proxy misconfiguration.
- **Alternative hypothesis:** Network packet loss, mtu mismatch, or congestion.
- **First evidence:** Collect backend health output.
- **Second evidence:** Correlate backend health output for the same timestamp.
- **Command:** `oc get pvc,pv -n <project> -o wide`
- **Metric:** Compare p95 read latency against baseline and SLO.
- **Decision point:** If the healthy control workload fails in the same failure domain, escalate toward the shared storage or network layer; otherwise remain at namespace/workload scope.
- **Containment:** Pause aggressive retries and protect unaffected workloads from saturation.
- **Remediation:** Apply one reversible change, then rerun the original operation.
- **Rollback:** Restore the previous manifest, secret, policy, route, or storage setting if validation fails.
- **Proof of recovery:** Capture successful operation, clean events, normal metric range, and user confirmation.
- **Prevention:** Add automated preflight checks and an alert for the earliest measurable failure signal.
