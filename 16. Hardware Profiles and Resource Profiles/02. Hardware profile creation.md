A hardware profile is useful only when the complete path works:

1. The profile object is valid and visible to the intended user.
2. The selected identifiers match Kubernetes resource names.
3. Default, minimum, and maximum values are internally consistent.
4. Project quota and policy admit the requested resources.
5. Node selectors and tolerations match real nodes.
6. A suitable node has allocatable capacity.
7. Required operators, drivers, runtimes, and device plugins are healthy.
8. The generated workload receives the intended requests and limits.
9. The application can use the resources exposed inside the container.
10. Monitoring and governance can prove that the profile behaves as designed.

## 1. Architecture and mental model

### 1.1 Control-plane view

The OpenShift AI dashboard presents a catalog of hardware profiles to permitted users.
The HardwareProfile custom resource stores the reusable resource and scheduling contract.
A controller or workload-specific integration translates the selected profile into workload configuration.
Kubernetes admission evaluates schema, policy, quota, LimitRange, and security constraints.
The scheduler evaluates resource requests, selectors, affinity, taints, tolerations, topology, and queue admission.
The kubelet and runtime create the pod on the selected node.
Accelerator device plugins expose vendor resources and allocate devices to containers.
The application runtime finally initializes CPU, memory, or accelerator libraries.

### 1.2 Data-plane view

CPU is represented in Kubernetes as cores or millicores.
Memory is represented as binary or decimal byte quantities.
Vendor accelerators are normally represented as extended resources such as `vendor.example/device`.
Extended resources are integer resources and are advertised in node Capacity and Allocatable.
A pod cannot use a vendor resource merely because a profile contains its name.
The corresponding node plugin must advertise the resource and the runtime stack must expose the device.

### 1.3 Failure-domain model

| Layer | Typical failure | Primary evidence |
|---|---|---|
| Dashboard | profile missing or disabled | UI state, browser request, dashboard logs |
| API | rejected object or wrong version | `oc explain`, CRD, API error |
| Profile | invalid identifier or scheduling | HardwareProfile YAML and status/events |
| Admission | quota, policy, or limit rejection | events and admission-controller message |
| Queue | workload not admitted | LocalQueue, ClusterQueue, Workload state |
| Scheduler | pod remains Pending | pod events and scheduler diagnostics |
| Node | label, taint, or capacity mismatch | node labels, taints, Capacity, Allocatable |
| Device | driver or plugin unhealthy | operator operands, daemonset logs, device files |
| Runtime | library or image mismatch | container logs and runtime diagnostics |
| Application | OOM, timeout, or poor throughput | application metrics and traces |

## 2. Terminology

- **HardwareProfile:** reusable OpenShift AI resource and scheduling definition.
- **Identifier:** Kubernetes resource key such as `cpu`, `memory`, or a vendor extended resource.
- **Default count:** value initially proposed to the user or workload.
- **Minimum count:** lowest permitted value when customization is allowed.
- **Maximum count:** highest permitted value when customization is allowed.
- **Resource type:** semantic classification such as CPU, Memory, or Accelerator.
- **Node selector:** exact label constraint used for workload placement.
- **Toleration:** permission for a pod to schedule onto a node with a matching taint.
- **Global profile:** profile intended for use across projects, subject to product configuration and authorization.
- **Project-scoped profile:** profile available within an authorized data-science project.
- **LocalQueue:** namespace-level Kueue entry point mapping workloads to cluster capacity.
- **Runtime matching:** selection or recommendation of a serving runtime compatible with an accelerator.
- **ResourceQuota:** namespace admission boundary for aggregate requested or limited resources.
- **LimitRange:** namespace defaults and per-object min/max constraints.

## 4. From-scratch implementation project

### Project: Build and validate `hardware-profile-creation`

#### Business objective

Provide a governed, repeatable resource selection for platform-managed AI workloads.
Prevent users from guessing arbitrary resource values.
Route workloads to the intended capacity pool.
Align profile maxima with namespace and queue entitlements.
Produce observable evidence for platform support and capacity planning.

#### Deliverables

- Hardware profile manifest for `hardware-profile-creation`.
- Namespace quota and LimitRange review.
- Node-label and taint inventory.
- Workload validation evidence.
- Monitoring dashboard or saved queries.
- Failure-injection results.
- Rollback and retirement procedure.
- Owner, approver, and review date.

#### Assumptions

- The OpenShift cluster is healthy.
- The OpenShift AI Operator is installed and reconciled.
- The user has access to a data science project.
- Required accelerator operators are installed when an accelerator is used.
- Image registry, storage, networking, DNS, and certificates are functional.
- Production changes follow organizational change control.

### 4.1 Create the project and baseline controls

```bash
export PROJECT=hardware-profile-creation-lab
oc new-project "$PROJECT"

cat <<'EOF' | oc apply -f -
apiVersion: v1
kind: ResourceQuota
metadata:
  name: profile-lab-quota
  namespace: hardware-profile-creation-lab
spec:
  hard:
    requests.cpu: "32"
    requests.memory: "256Gi"
    limits.cpu: "64"
    limits.memory: "512Gi"
    pods: "30"
---
apiVersion: v1
kind: LimitRange
metadata:
  name: profile-lab-limits
  namespace: hardware-profile-creation-lab
spec:
  limits:
    - type: Container
      defaultRequest:
        cpu: "500m"
        memory: "1Gi"
      default:
        cpu: "2"
        memory: "4Gi"
      min:
        cpu: "100m"
        memory: "256Mi"
      max:
        cpu: "32"
        memory: "256Gi"
EOF

oc get resourcequota,limitrange -n "$PROJECT"
```

For accelerator profiles, add an extended-resource quota only after confirming the exact resource key.
Test quota changes in a non-production project before broad rollout.

1. Sign in to the OpenShift AI dashboard with an authorized administrator account.

### 4.4 Create through YAML

Use `oc explain` and export an existing profile from the same cluster before finalizing metadata and API version.

```yaml
# Template only. Discover the served API version first and replace the value below.
apiVersion: infrastructure.opendatahub.io/<served-version>
kind: HardwareProfile
metadata:
  name: hardware-profile-creation
  namespace: <profile-namespace>
spec:
  identifiers:
      - displayName: CPU
        identifier: cpu
        minCount: "1"
        defaultCount: "4"
        maxCount: "8"
        resourceType: CPU
      - displayName: Memory
        identifier: memory
        minCount: "2Gi"
        defaultCount: "16Gi"
        maxCount: "128Gi"
        resourceType: Memory
  scheduling:
    type: Node
    node:
      nodeSelector:
        workload.platform.example.com/pool: "true"
      tolerations:
        - key: workload.platform.example.com/dedicated
          operator: Equal
          value: "true"
          effect: NoSchedule
```

```bash
SERVED_VERSION="$(oc get crd hardwareprofiles.infrastructure.opendatahub.io       -o jsonpath='{.spec.versions[?(@.served==true)].name}' | awk '{print $1}')"
test -n "$SERVED_VERSION"
echo "Served version: $SERVED_VERSION"

sed "s#<served-version>#$SERVED_VERSION#; s#<profile-namespace>#$PROJECT#"       hardware-profile-creation.yaml | oc apply --server-side --dry-run=server -f -

sed "s#<served-version>#$SERVED_VERSION#; s#<profile-namespace>#$PROJECT#"       hardware-profile-creation.yaml | oc apply -f -

oc get hardwareprofile -n "$PROJECT"
oc get hardwareprofile hardware-profile-creation -n "$PROJECT" -o yaml
```

Never bypass a server-side dry run for a new schema or after an OpenShift AI upgrade.
Store the reviewed manifest in Git and deploy through the organization’s approved GitOps path.

### 4.7 Pipeline component pattern

```python
from kfp import dsl

@dsl.component(base_image="registry.access.redhat.com/ubi9/python-311")
def validate_profile_contract() -> str:
    # Keep the component deterministic and log the resolved resources.
    return "profile contract validated"

@dsl.pipeline(name="hardware-profile-creation-validation")
def profile_validation_pipeline():
    task = validate_profile_contract()
    task.set_cpu_request("4")
```

Do not assume that a dashboard hardware-profile selection automatically rewrites every compiled pipeline component.

## 5. Design decisions

### 5.1 Requests versus limits

The scheduler places pods using requests, not observed future usage.
CPU limits can throttle a busy process.
Memory limits can terminate a container with OOMKilled.
For extended accelerators, request and limit behavior is controlled by Kubernetes extended-resource rules and the device plugin.
Choose defaults from measured workload behavior and concurrency targets.
Choose maxima from entitlement and node-capacity boundaries.

### 5.2 Profile granularity

Create distinct profiles when workload behavior, cost, accelerator class, isolation, or SLO differs materially.
Avoid dozens of nearly identical profiles that users cannot distinguish.
Avoid a single unrestricted profile that permits arbitrary high values.
Use a small catalog with evidence-based tiers.

### 5.3 Placement

Use selectors to express mandatory placement.
Use taints to repel unrelated workloads from scarce or specialized nodes.
Use tolerations only for workloads entitled to the tainted pool.
Remember that a toleration permits placement but does not force placement.
Use topology constraints and anti-affinity outside the profile where workload availability requires them.

### 5.4 Visibility and authorization

Profile visibility affects discoverability and selection.
Kubernetes RBAC controls who can read or modify resources.
ResourceQuota controls aggregate namespace entitlement.
Node labels and taints control placement, not user identity.
Admission policy can enforce approved identifiers, maxima, labels, and ownership metadata.

## 6. Capacity and quota alignment

Use this inequality as a first admission check:

`profile default request <= remaining namespace quota <= usable cluster or queue capacity`

Also verify:

- Per-container LimitRange maximum.
- Namespace aggregate requests and limits.
- Extended-resource quota.
- LocalQueue and ClusterQueue nominal quota.
- ResourceFlavor node labels and taints.
- Node Allocatable after system reservations.
- Rollout surge and duplicate replicas.
- Fragmentation across accelerator devices or MIG slices.
- Storage, network, and image-pull capacity.

## 7. Security and multi-tenancy

Apply least privilege to profile creation and modification.
Separate catalog administrators from workload consumers.
Restrict who can change node labels and taints.
Protect accelerator operator namespaces and service accounts.
Use signed and approved images for vendor runtime validation.
Do not put credentials in profile names, descriptions, labels, or annotations.
Apply NetworkPolicy to workloads independently of hardware-profile selection.
Record all profile mutations through audit logging and Git history.
Use admission policy to reject unapproved resource domains or excessive maxima.

## 8. Observability

Collect evidence at four levels:

1. Catalog: profile existence, scope, generation, and configuration.
2. Admission and scheduling: rejected requests, Pending pods, queue state, and scheduler reasons.
3. Node/device: allocatable resources, operator health, device-plugin state, and hardware telemetry.
4. Application: utilization, latency, throughput, OOM events, errors, and saturation.

Suggested alerts include:

- HardwareProfile object missing from an expected namespace.
- Profile references an identifier absent from every node.
- Accelerator operator or device-plugin daemonset unavailable.
- Pending profile-backed workload exceeds the operational threshold.
- Namespace quota usage exceeds a warning threshold.
- Queue admission wait exceeds the SLO.
- GPU or accelerator utilization remains near zero for an expensive allocation.
- OOMKilled or CPU throttling increases after a profile change.
- Node temperature, ECC, XID, or vendor health errors occur.

## 10. Production acceptance criteria

- The profile is visible only to the intended audience.
- The profile object passes schema validation.
- Every identifier exists and is spelled exactly as advertised.
- Defaults, minima, and maxima are valid and documented.
- Quota admits at least one workload at the default size.
- Node placement matches the intended pool.
- No unrelated node pool satisfies accidental selectors.
- The workload reaches Ready within the agreed threshold.
- Accelerator diagnostics pass when applicable.
- Application latency, throughput, and error rate meet acceptance criteria.
- Monitoring and alerting cover catalog, scheduling, node, device, and application layers.
- Rollback has been tested.
- Ownership and review date are recorded.

## 11. L3 operational scenario playbooks

### Scenario 001: Profile does not appear in the dashboard

**Observed symptom:** profile does not appear in the dashboard.
**Primary hypothesis:** the installed CRD schema differs from the manifest.
**First command:** `oc auth can-i get hardwareprofiles.infrastructure.opendatahub.io -n <namespace>`.

## 16. Command reference

```bash
# API and schema
oc api-resources | grep -i hardwareprofile
oc get crd hardwareprofiles.infrastructure.opendatahub.io
oc explain hardwareprofile --recursive

# Profiles
oc get hardwareprofile -A
oc get hardwareprofile <name> -n <namespace> -o yaml
oc describe hardwareprofile <name> -n <namespace>

# Workloads
oc get pods -n <namespace> -o wide
oc describe pod <pod> -n <namespace>
oc get pod <pod> -n <namespace> -o json | jq '.spec.containers[].resources'
oc get events -n <namespace> --sort-by=.lastTimestamp

# Capacity and placement
oc get nodes --show-labels
oc describe node <node>
oc get node <node> -o json | jq '.spec.taints,.status.capacity,.status.allocatable'
oc adm top nodes
oc adm top pods -A --containers

# Namespace controls
oc get resourcequota,limitrange -n <namespace>
oc describe resourcequota -n <namespace>
oc describe limitrange -n <namespace>

# Authorization
oc auth can-i get hardwareprofiles.infrastructure.opendatahub.io -n <namespace>
oc auth can-i create hardwareprofiles.infrastructure.opendatahub.io -n <namespace>

# Queueing, when Kueue is used
oc get localqueue,clusterqueue,resourceflavor -A
oc get workloads.kueue.x-k8s.io -A
```
