# 20. Kernel startup troubleshooting

> **Scope:** This chapter develops expert-level capability in Jupyter kernelspec discovery, interpreter paths, virtual environments, permissions, package conflicts, memory pressure, and logs.
> **Version discipline:** Validate every manifest against the CRDs installed on your cluster before production use.

## 2. Product and architecture context

- A workbench is represented by an OpenShift AI Notebook custom resource and reconciled into runtime resources in the user project.
- The workbench image supplies the IDE, language runtime, libraries, entrypoint, and HTTP behavior expected by OpenShift AI.
- A workbench normally uses project-scoped compute, a service account, a PVC, a Service, routing/proxy integration, configuration, and optional connections.
- The dashboard is a management interface; the Kubernetes and OpenShift API objects remain the operational source of truth.
- The controller continuously compares desired state with observed state and attempts to reconcile differences.
- Readiness means the workbench can safely receive user traffic; running does not automatically mean ready or usable.
- The primary IDE container must honor the configured base path and health endpoints expected by the platform.
- Persistent storage protects notebooks and project files from normal pod replacement, but it does not replace a backup strategy.
- CPU, memory, ephemeral storage, and accelerators participate in scheduling, quota, fairness, and cost management.
- Connections and secrets should be injected by reference and limited to the project and identities that require them.
- Stopping a workbench should release compute while retaining intended persistent data.
- Starting a workbench is a chain: admission, scheduling, image pull, volume attach/mount, container start, probes, proxy readiness, and user access.
- Custom images must work with OpenShift's arbitrary non-root UID model and restricted security posture.
- ImageStream annotations and labels determine whether a custom image is discoverable and how it is presented to users.
- Hardware profiles can standardize resource choices, but feature status and fields must be checked for the installed OpenShift AI release.

## 7. Troubleshooting decision tree

| State | Next evidence-based action |
|---|---|
| Object absent | Check project, RBAC, admission errors, dashboard request, and controller CRDs. |
| Object exists but no pod | Inspect Notebook status, controller logs, owner references, events, and reconciliation errors. |
| Pod Pending | Read PodScheduled condition and scheduler events; then check quota, requests, PVCs, taints, affinity, GPUs, and queue constraints. |
| Pod initializing | Inspect init containers, image pulls, volume attach/mount, projected volumes, and CNI setup. |
| Pod Running but not Ready | Inspect readiness probe path, port, base URL, OAuth proxy, process listeners, and application logs. |
| CrashLoopBackOff | Capture current and previous logs, exit code, reason, OOM evidence, probe failures, command, args, and assigned UID. |
| ImagePullBackOff | Read exact event; validate name, tag/digest, credentials, CA trust, DNS, proxy, mirrors, and registry policy. |
| PVC Pending | Validate StorageClass, provisioner, capacity, topology, access mode, quota, and CSI events. |
| PVC Bound but mount fails | Check attach/mount events, node plugin, access mode conflicts, permissions, SELinux, root-squash, and backend health. |
| Workbench opens but IDE fails | Inspect base path, websocket behavior, kernelspecs, interpreter, package conflicts, extensions, and user configuration. |
| Intermittent failure | Correlate node changes, storage latency, network resets, probe timing, resource pressure, and operator reconciliation. |
| Only one user affected | Compare project permissions, browser session, user files, kernels, extensions, environment, and credentials. |
| All workbenches affected | Check cluster operators, OpenShift AI components, ingress, OAuth, registry, storage, DNS, network, and recent upgrades. |

## 8. Enterprise controls

1. Maintain an approved image catalog with owner, purpose, supported frameworks, digest, build source, SBOM, scan result, signature, and expiry date.
2. Require Git-based review for ImageStream, hardware profile, quota, RBAC, NetworkPolicy, and namespace policy changes.
3. Separate platform-admin access from project contributor access and review both periodically.
4. Use namespace quotas and hardware profiles to prevent accidental oversized workbenches.
5. Define a documented idle policy and a business exception process.
6. Require persistent user work to be stored on PVC or an approved external repository, not container ephemeral storage.
7. Back up data according to business criticality and test restore procedures.
8. Monitor startup latency, failed starts, Pending duration, restart count, storage latency, GPU allocation, and idle capacity.
9. Record every production incident with exact image digest, Notebook generation, pod UID, node, PVC, and event timeline.
10. Do not automatically delete failed pods before logs, events, status, and relevant objects are collected.
11. Promote images through development, test, security approval, and production rather than pulling arbitrary tags.
12. Use immutable digests for controlled environments and treat tag movement as a change.
13. Rotate connections and secrets without embedding values in notebooks, Git repositories, images, or support bundles.
14. Apply default-deny network policies only with tested allowances for DNS, registries, object storage, Git, package repositories, and platform services.
15. Define RTO and RPO for workbench data; a bound PVC alone does not satisfy recovery objectives.
16. Review Technology Preview features before production use and record the risk acceptance when applicable.
