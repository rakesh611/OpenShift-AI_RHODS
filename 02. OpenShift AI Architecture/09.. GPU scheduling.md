GPU Scheduling in Red Hat OpenShift AI Architecture

GPU scheduling in Red Hat OpenShift AI is the process of intelligently allocating GPU resources to AI/ML workloads running inside Kubernetes pods.

For a experienced DevOps/OpenShift engineer, GPU scheduling is not just about assigning GPUs — it involves:

Resource isolation

Multi-tenant governance

Performance optimization

NUMA awareness

GPU sharing

Queue-based scheduling

Autoscaling

MIG partitioning

AI workload prioritization

Integration with model serving and pipelines

1. Why GPU Scheduling is Important in OpenShift AI

AI workloads are GPU-intensive:

| Workload                | GPU Requirement      |
| ----------------------- | -------------------- |
| Model training          | High GPU utilization |
| LLM fine-tuning         | Multi-GPU            |
| Inference serving       | Shared/small GPU     |
| Vector DB acceleration  | CUDA support         |
| Deep learning notebooks | Interactive GPU      |
| Distributed training    | GPU topology-aware   |

Without proper scheduling:

GPU starvation occurs

Expensive GPUs remain idle

Pods get stuck in Pending

One tenant monopolizes GPUs

Training jobs become slow

PCIe/NVLink topology becomes inefficient

Responsibilities

| Component             | Purpose                      |
| --------------------- | ---------------------------- |

| DCGM Exporter         | GPU monitoring               |

4. GPU Resource Advertisement

NVIDIA device plugin exposes GPU resources:
```bash
kubectl describe node gpu-worker01
```
Example:
```plain
Capacity:
  cpu:                32
  memory:             128Gi
  nvidia.com/gpu:     4
```
Now scheduler knows:

This node has 4 GPUs

Pods can request GPU resources

6. GPU Requests and Limits

Example training pod:
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: pytorch-training
spec:
  containers:
  - name: trainer
    image: pytorch/pytorch:latest
    resources:
      limits:
        nvidia.com/gpu: 1
```
Important:

GPUs only support limits

Requests automatically equal limits

GPU resources are non-compressible

7. GPU Node Labeling

GPU nodes are labeled automatically.

Example:
```bash
kubectl get nodes --show-labels
```
Labels:
```plain
feature.node.kubernetes.io/pci-10de.present=true
nvidia.com/gpu.present=true
nvidia.com/gpu.product=NVIDIA-A100
```
Use nodeSelector:
```yaml
nodeSelector:
  nvidia.com/gpu.product: NVIDIA-A100
```
8. Taints and Tolerations for GPU Isolation

GPU nodes are expensive.

Prevent normal workloads from using them.

GPU Node Taint
```bash
kubectl taint nodes gpu-node gpu=true:NoSchedule
```
AI Workload Toleration
```yaml
tolerations:
- key: "gpu"
  operator: "Equal"
  value: "true"
  effect: "NoSchedule"
```
9. GPU Affinity Rules

Used for:

Hardware locality

NUMA optimization

High-speed NVLink communication

Example:
```yaml
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
      - matchExpressions:
        - key: accelerator
          operator: In
          values:
          - nvidia-a100
```

11. GPU Topology Awareness

Critical for performance.

Not all GPUs communicate equally.

Topology-aware scheduling considers:

PCIe lanes

NUMA zones

NVLink topology

CPU-GPU locality

Example:
```plain
GPU0 <-> GPU1 via NVLink
GPU2 <-> GPU3 via PCIe only
```
Scheduler should allocate:

GPU0 + GPU1 together

instead of

GPU0 + GPU3

12. MIG (Multi-Instance GPU)

Supported mainly on NVIDIA A100/H100.

Allows partitioning one GPU into multiple logical GPUs.

Example:
```plain
1 A100 GPU
   ->
7 MIG instances
```
Useful for:

Multi-tenancy

Notebook environments

Small inference jobs

MIG Scheduling Example

Node resources:
```plain
nvidia.com/mig-1g.5gb: 7
```
Pod request:
```yaml
resources:
  limits:
    nvidia.com/mig-1g.5gb: 1
```
Benefits:

Better utilization

Cost optimization

Isolation between teams

13. Time-Slicing GPU Sharing

Alternative to MIG.

GPU shared across pods using time-sharing.

Configured in NVIDIA device plugin.

Example:
```yaml
sharing:
  timeSlicing:
    resources:
    - name: nvidia.com/gpu
      replicas: 10
```
Now:
```plain
1 GPU = shared among 10 pods
```
Best for:

Jupyter notebooks

Development

Small inference

Not ideal for heavy training.

15. Volcano Scheduler in AI

Used for distributed AI workloads.

Features:

Gang scheduling

Queue priority

Fair-share scheduling

AI batch optimization

Gang Scheduling

All GPUs must be available together.

Example:
```plain
Job requires 8 GPUs
```
Without gang scheduling:

4 pods start

4 remain pending

Training fails

Volcano ensures:
```plain
Either all 8 start together
OR none start
```
16. Kueue in OpenShift AI

Kubernetes-native queue manager.

Used for:

AI job admission control

Fair resource allocation

Cluster quota enforcement

Example:
```plain
Team-A -> 8 GPUs max
Team-B -> 4 GPUs max
```
