Pipeline Controller in OpenShift AI Architecture

In Red Hat OpenShift AI, the Pipeline Controller is the core orchestration component responsible for managing, scheduling, executing, and monitoring AI/ML workflows (pipelines) across the Kubernetes/OpenShift cluster.

For a experienced DevOps/OpenShift/Kubernetes engineer, you should understand it not just as a “workflow runner,” but as a:

Kubernetes-native workflow orchestrator

ML lifecycle automation engine

CRD-based execution controller

Multi-tenant AI workload scheduler

CI/CD-like system for ML operations (MLOps)

1. What is a Pipeline in OpenShift AI?

A pipeline is a sequence of automated ML tasks such as:

Data ingestion

Data preprocessing

Feature engineering

Model training

Validation/testing

Model registration

Deployment

Monitoring

Example:
```plain
Fetch Data
   ↓
Clean Dataset
   ↓
Train Model
   ↓
Evaluate Accuracy
   ↓
Store Model
   ↓
Deploy to Serving
```
The Pipeline Controller manages this entire lifecycle.

3. Core Responsibilities of Pipeline Controller

The Pipeline Controller performs:

| Function               | Description                       |
| ---------------------- | --------------------------------- |
| Workflow orchestration | Executes ML steps in order        |
| DAG management         | Handles dependency graph          |
| Pod scheduling         | Creates Kubernetes pods           |
| Retry handling         | Retries failed stages             |
| Artifact passing       | Shares models/data between stages |
| State tracking         | Tracks execution progress         |
| Resource management    | CPU/GPU/Memory allocation         |
| Multi-user isolation   | Namespace-based execution         |
| Logging & monitoring   | Tracks logs/metrics               |
| Pipeline lifecycle     | Create/update/delete runs         |


6. Pipeline Controller Workflow Lifecycle

Step-by-Step Internal Flow

Step 1 — User Submits Pipeline

User submits from:

Jupyter notebook

Kubeflow UI

SDK

GitOps

API

Example:
```python
client.create_run_from_pipeline_func()
```
Step 2 — Pipeline Compiled

Pipeline SDK converts Python DSL into YAML.
```plain
Python DSL → Workflow YAML
```
Step 3 — API Server Receives Request

Pipeline API stores metadata:

pipeline name

version

experiment

run info

Step 4 — Pipeline Controller Watches CRDs

Controller continuously watches:
```plain
etcd → API Server → Watch Events
```
Like Kubernetes Deployment controller.

Step 5 — Controller Creates Workflow Objects

Creates:
```plain
Workflow
Pods
PVCs
Secrets
Service Accounts
```
Step 6 — Scheduler Places Pods

Kubernetes scheduler assigns nodes.

GPU workloads may use:
```plain
resources:
  limits:
    nvidia.com/gpu: 1
```
Step 7 — Execute DAG

Controller ensures dependency order.

Example DAG:
```plain
A → B → C
 \      ↓
  → D → E
```
Node B runs only after A succeeds.

Step 8 — Artifact Storage

Artifacts stored in:

MinIO

S3

Ceph

PVCs

Examples:

trained model

datasets

logs

metrics

Step 9 — Status Updates

Controller updates workflow state:
```plain
Pending
Running
Succeeded
Failed
Skipped
Retrying
```

8. Retry & Failure Management

Enterprise AI pipelines must tolerate failures.

Pipeline Controller supports:

| Feature       | Example                |
| ------------- | ---------------------- |
| Retry policy  | Retry training 3 times |
| Timeout       | Stop after 2 hours     |
| Resume        | Resume failed workflow |
| Caching       | Skip completed steps   |
| Rollback      | Revert deployment      |
| Notifications | Slack/email alerts     |

Example:
```yaml
retryStrategy:
  limit: 3
```
