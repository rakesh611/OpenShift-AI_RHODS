Service Mesh Integration in OpenShift AI Architecture

In Red Hat OpenShift AI, Service Mesh integration provides secure, observable, and policy-driven communication between AI/ML components running on Red Hat OpenShift.

For a experienced DevOps/OpenShift engineer, think of Service Mesh as:

“An infrastructure layer that controls all east-west traffic between AI services without modifying application code.”

In OpenShift AI environments, Service Mesh is mainly used for:

Secure communication between notebooks, pipelines, model servers, and APIs

Traffic management for inference services

Multi-tenant isolation

mTLS encryption

Observability and tracing

Canary deployments of ML models

Rate limiting and policy enforcement

Zero-trust networking

1. What is Service Mesh in OpenShift AI?

OpenShift AI workloads are highly distributed:

Jupyter notebooks

ML pipelines

Model serving runtimes

Feature stores

Data APIs

GPU inference services

Monitoring components

External AI gateways

All these communicate over Kubernetes networking.

Without mesh:

Traffic is unmanaged

No encryption by default

Difficult tracing

No advanced routing

No traffic intelligence

With Service Mesh:

Every pod gets a sidecar proxy (Envoy)

Traffic flows through proxies

Policies are centrally managed

6. mTLS in OpenShift AI

Why important?

AI workloads often process:

confidential datasets

enterprise prompts

internal APIs

financial/healthcare inference

mTLS ensures:

encrypted communication

workload identity verification

mTLS Flow
```plain
Notebook Pod <----TLS----> Model Server Pod
```
Both Envoy proxies exchange certificates automatically.

PeerAuthentication Example
```yaml
apiVersion: security.istio.io/v1beta1
kind: PeerAuthentication
metadata:
  name: default
spec:
  mtls:
    mode: STRICT
```
STRICT means:

plain-text traffic blocked

only encrypted traffic allowed

8. Canary Deployment Example

Example:

v1 model = stable fraud detection

v2 model = new ML algorithm

Traffic split:
```plain
90% -> v1
10% -> v2
```
VirtualService Example
```yaml
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: fraud-model
spec:
  hosts:
  - fraud-model
  http:
  - route:
    - destination:
        host: fraud-model
        subset: v1
      weight: 90
    - destination:
        host: fraud-model
        subset: v2
      weight: 10
```
This is extremely important in:

MLOps

continuous model deployment

safe AI releases

13. Multi-Tenancy Security

In enterprise AI platforms:

multiple teams share cluster.

Examples:

Finance team

HR AI team

Healthcare AI team

Need strict isolation.

AuthorizationPolicy Example
```yaml
apiVersion: security.istio.io/v1beta1
kind: AuthorizationPolicy
metadata:
  name: allow-finance
spec:
  selector:
    matchLabels:
      app: finance-model
  rules:
  - from:
    - source:
        namespaces: ["finance"]
```
This restricts access to:

only finance namespace
