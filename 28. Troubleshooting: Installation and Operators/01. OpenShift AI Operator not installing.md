## 1. Executive overview
`OpenShift AI Operator not installing` must be diagnosed as a control-loop failure, not merely as a pod failure.
The normal chain is catalog content → Subscription → resolver → InstallPlan → CSV → Operator deployment → DSCI/DSC → operands → service/route/OAuth/user access.
A late symptom can originate much earlier in this chain. The senior engineer locates the earliest broken boundary and verifies ownership before remediation.
- Typical symptom: Operator remains Installing.
- Typical symptom: no rhods-operator deployment.
- Typical symptom: Subscription resolution failure.
- Typical symptom: bundle unpack failure.
- Typical symptom: CSV never Succeeded.

### Senior principles
1. Identify desired state, observed state, and responsible controller.
2. Use status reasons and messages before assumptions.
3. Running does not imply Ready or Available.
4. CSV Succeeded does not prove every operand is healthy.
5. Do not delete CRDs as a troubleshooting experiment.
6. Test with the same identity, namespace, proxy, DNS, and CA context.
7. Preserve timestamps and correlate events across controllers.
8. Make one reversible change per iteration.
9. Define success and rollback before change.
10. Use Red Hat documentation matching the installed release.

### Control flow
1. Catalog serves package, channel, bundle, CSV, CRD, related-image, and dependency metadata.
2. Subscription requests package, source, channel, and approval policy.
3. Resolver calculates a compatible Operator set.
4. InstallPlan records ordered resource steps.
5. Approval policy allows or blocks execution.
6. CSV evaluates requirements and deploys the Operator.
7. OpenShift AI Operator reconciles DSCI and DSC.
8. Component controllers create operands.
9. Shared infrastructure determines image, network, certificate, storage, and route readiness.
10. User access validates the complete path.

### Validate DSCI and DSC
1. Live schema. Evidence: current logs. Practice: test with the exact service account.
2. observedGeneration. Evidence: rollout status. Practice: confirm the intended channel.
3. conditions. Evidence: probe result. Practice: avoid premature deletion.
4. component dependency. Evidence: route admission. Practice: watch reconciliation.

### Validate infrastructure
1. registry. Evidence: current logs. Practice: test with the exact service account.
2. proxy. Evidence: rollout status. Practice: confirm the intended channel.
3. CA. Evidence: probe result. Practice: avoid premature deletion.
4. DNS. Evidence: route admission. Practice: watch reconciliation.
5. ingress. Evidence: image pull event. Practice: collect before mutation.
6. storage. Evidence: InstallPlan step. Practice: test with the exact service account.
7. scheduling. Evidence: API discovery. Practice: confirm the intended channel.
8. network policy. Evidence: ownerReferences. Practice: avoid premature deletion.

### Prove recovery
1. one change. Evidence: current logs. Practice: test with the exact service account.
2. watch reconciliation. Evidence: rollout status. Practice: confirm the intended channel.
3. validate generated resources. Evidence: probe result. Practice: avoid premature deletion.
4. test user path. Evidence: route admission. Practice: watch reconciliation.
5. document prevention. Evidence: image pull event. Practice: collect before mutation.

### Decision tree
1. **Package visible?** No: catalog or mirror path. Yes: Subscription.
2. **InstallPlan present?** No: resolver conditions. Yes: approval and phase.
3. **InstallPlan Complete?** No: failed/pending step. Yes: CSV.
4. **CSV Succeeded?** No: requirementStatus/deployment. Yes: Operator/operands.
5. **Operator Available?** No: scheduling/pull/admission/probes/logs. Yes: DSCI/DSC.
6. **DSCI and DSC current?** No: reconcile issue. Yes: component conditions.
7. **Operands ready?** No: component path. Yes: route/OAuth/user test.
