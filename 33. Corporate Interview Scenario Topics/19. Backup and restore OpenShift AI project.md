# 19. Backup and restore OpenShift AI project

> Corporate Interview Scenario Guide — Red Hat OpenShift AI L3 / Senior Platform Engineer

- **Production baseline:** Red Hat OpenShift AI Self-Managed 3.4 and OpenShift Container Platform 4.20
- **Generated:** 2026-07-21
- **Audience:** 10+ year Linux, Kubernetes, OpenShift, DevOps and production-support engineers
- **Safety:** Validate fields with `oc api-resources` and `oc explain` before applying manifests.


## Scenario objective

Protect project configuration, PVC data, pipeline metadata, object-store artifacts, model metadata, secrets and access controls with verified recovery.


## Senior interview answer structure

1. Clarify business impact, data class, tenancy, SLO, RPO, RTO, compliance and operating ownership.

4. Define namespace, RBAC, quota, NetworkPolicy, secret, image and artifact boundaries.
5. Build a minimum production pattern in non-production.
6. Run functional, security, performance, failure, restore and upgrade tests.
7. Promote through GitOps with approvals and evidence.
8. Operate with SLOs, alerts, capacity, backup, incident and change management.

## Project creation from scratch

### Phase 0 — supported-version discovery

1. Record cluster version, channel, CSV, dependent Operators, storage classes, ingress, identity, proxy and disconnected status.
2. Read release notes, known issues, deprecated and removed features.
3. Run `oc api-resources` and `oc explain` for every custom resource.
4. Create a RACI across platform, security, network, storage, data science and application teams.

### Phase 1 — requirements

1. Define users, data classes, model type, request pattern, peak concurrency, latency, availability, RPO, RTO and retention.
2. Convert each requirement into a measurable acceptance test.
3. Record constraints such as air gap, private connectivity, HSM, GPU scarcity and regulated change.
4. Document assumptions and explicit exclusions.

### Phase 2 — dependency readiness

1. Validate cluster operators, DNS, NTP, ingress, storage, registry, monitoring, identity, certificate trust and backup.
2. Verify node labels, taints, capacity and scheduling.
3. Verify credentials come from an approved secret system.
4. Create an automated preflight report.

### Phase 3 — tenant foundation

1. Create namespaces with owner, environment, cost center, data class and lifecycle labels.
2. Bind groups rather than individuals where practical.
3. Apply ResourceQuota, LimitRange, default-deny and required allow policies.
4. Register approved images, hardware profiles, runtimes and connections.

### Phase 4 — implementation

1. Deploy the minimum representative workload.
2. Pin images and models by digest or immutable version.
3. Use Git overlays for environment differences.
4. Expose only required endpoints and verify authentication and authorization.

### Phase 5 — validation

1. Run positive and negative functional tests.
2. Test scheduling, images, storage, DNS, TLS, RBAC, policy and quota.
3. Run load, soak and capacity tests.
4. Capture YAML, events, logs, metrics and test output.

### Phase 6 — failure and recovery

1. Inject one dependency failure at a time in non-production.
2. Confirm actionable alerts.
3. Execute remediation and rollback.
4. Measure restoration against SLO and RTO.

### Phase 7 — production promotion

1. Require review, policy checks, artifact verification, approvals and change record.
2. Use canary or controlled traffic migration.
3. Observe a defined bake period.
4. Retain last-known-good manifests and artifacts.

### Phase 8 — day-2 operations

1. Review capacity, latency, errors, security, backup age, certificate expiry and deprecations.
2. Patch and upgrade through rehearsal environments.
3. Review access and exceptions.
4. Improve the runbook after every incident and exercise.


## Command and evidence toolkit

Run read-only commands first and preserve timestamped output.

```bash
oc whoami
oc version
oc get clusterversion
oc get csv -A
oc get subscriptions.operators.coreos.com -A

oc get datasciencecluster -A -o yaml

oc get nodes -o wide
oc describe node <node>
oc auth can-i --list -n <project>
oc get resourcequota,limitrange -n <project> -o yaml
oc get networkpolicy -n <project> -o yaml
oc get secrets,pvc -n <project>
oc get routes,services,endpointslices -n <project>
oc logs <pod> -n <project> --all-containers --prefix
oc adm inspect namespace/<project>
oc adm must-gather
```

Evidence path: `<incident>/<timestamp>/<cluster>/<namespace>/<resource>/<command-output>`.

For every command record expected result, actual result and interpretation. Output without interpretation is not diagnosis.

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: ai-team-a-prechange
  namespace: openshift-adp
spec:
  includedNamespaces:
  - ai-team-a-dev
  - ai-team-a-prod
  snapshotMoveData: true
  ttl: 720h0m0s
```

## L3 diagnostic methodology

1. Capture exact symptom, timestamp, user, namespace, endpoint, request ID and reproduction.
2. Inspect desired custom resource, generation, observed generation, conditions and owning controller.
3. Inspect Deployment or StatefulSet, ReplicaSet, Pod, init containers, sidecars, probes and termination.
4. Inspect requests, limits, quota, selectors, affinity, taints, tolerations, priority, queue and PVC topology.
5. Inspect image digest, entrypoint, environment, mounts, certificates, runtime flags, GPU visibility and permissions.
6. Inspect DNS, service selector, EndpointSlice, route or gateway, TLS, NetworkPolicy, proxy and firewall.
7. Inspect PVC, S3 endpoint, credentials, bucket policy, object path, capacity, latency and throughput.
8. Correlate logs, metrics, traces, audit and events by time.
9. Correlate recent Git, Operator, node, certificate, secret, quota and policy changes.
10. Apply the smallest reversible remediation with a declared rollback trigger.

Collect events early because they expire. Read init-container and sidecar logs as well as the primary container.


## Security and compliance

1. Use enterprise groups and least privilege.
2. Separate platform admin, tenant admin, model approval, production deployment and audit roles.
3. Use private network paths where required.
4. Encrypt in transit and at rest.
5. Use external or short-lived secrets and test rotation.
6. Pin and sign images and artifacts.
7. Apply default deny and explicit allows.
8. Retain audit and promotion evidence.
9. Mask prompts, tokens and sensitive features in logs.
10. Threat-model model theft, injection, exfiltration and supply-chain compromise.

## Performance and capacity

1. Baseline before tuning.
2. Separate cold start, model load, queue, prefill, decode, storage and network latency.
3. Size CPU, memory, storage and accelerators from measurements.
4. Reserve headroom for failover and upgrades.
5. Use representative prompt, output, batch and concurrency distributions.
6. Track p50, p95, p99, max, errors, saturation and queue.
7. Test noisy-neighbor behavior.
8. Validate GPU and NUMA topology.
9. Correlate utilization, memory, power, temperature and throughput.
10. Tune one variable at a time with rollback thresholds.

## Backup and recovery

1. Inventory every stateful dependency.
2. Define RPO and RTO by dependency.
3. Protect project and required cluster-scoped resources.
4. Snapshot PVCs with supported CSI mechanisms.
5. Replicate or back up S3 objects and versions.
6. Protect external databases consistently.
7. Keep backup credentials outside the cluster.
8. Restore into isolation first.
9. Rotate credentials after restore where required.
10. Validate function, security, integrity and performance.

## L3 operational drill catalog

Each drill is a mini interview case and a production rehearsal. Execute only in approved non-production environments.

### Drill 001 — OADP / objects missing

1. **Context:** A production-like workload shows `objects missing` while validating `OADP`.
2. **Primary resource:** Inspect `Backup`, its owner and dependencies.
3. **First command:** `oc get nodes -o wide`.
4. **Healthy evidence:** Status, events, logs, endpoints and usage agree that `OADP` works.
5. **Metric correlation:** Compare the incident timestamp with `RTO achieved` and one dependency metric.
6. **Negative test:** Reproduce from an in-cluster debug pod and from the intended client path.
7. **Branches:** drift; dependency; identity; DNS or policy; storage; scheduling; runtime; capacity.
8. **Safe remediation:** Restore `evidence retention` with the smallest reversible change.
9. **Validation:** Repeat the request, inspect conditions, verify SLO recovery and check collateral impact.
10. **Rollback:** Roll back if SLO is not restored, blast radius grows or another tenant is affected.
11. **Evidence:** Save before/after YAML, events, logs, metrics, Git diff, approver and timestamps.
12. **Interview point:** Explain why this order reduces guesswork and protects production.
