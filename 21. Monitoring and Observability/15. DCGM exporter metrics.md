# 15. DCGM exporter metrics

## 1. Scope and outcome

Deploy, discover, validate, govern, and troubleshoot DCGM Exporter metrics in OpenShift using GPU Operator and UWM/platform monitoring integration.

By the end of this guide, you will have a deployable reference project, validation commands, PromQL, dashboard design, alert rules, production controls, and a troubleshooting runbook.

> **Version and support note:** The examples are written for OpenShift AI 3.5 and OpenShift monitoring 4.19. Verify compatibility with your installed minor releases. The dedicated OpenShift AI centralized observability stack in 3.5 is Technology Preview; use UWM and supported platform monitoring as the production baseline unless Red Hat explicitly supports your target design.

## 2. Why this topic matters at Corporate L3

- DCGM exporter metrics is not only a dashboard task; it is a reliability, security, capacity, and supportability discipline.
- A senior engineer must understand where a signal originates, how it is scraped or forwarded, what labels are attached, how it is retained, and who acts on it.
- The implementation must survive upgrades, multi-tenancy, runtime changes, node replacement, certificate rotation, disconnected environments, and incident conditions.
- DCGM Exporter exposes Prometheus metrics on /metrics and is commonly deployed as a DaemonSet on GPU nodes. Confirm metric collection configuration because profiling fields depend on hardware and DCGM settings.
- The project therefore uses layered signals: resource state, application metrics, synthetic checks, events, logs, and—where valuable—traces.

## 4. Architecture and data flow

### 4.1 Core components

- **GPU Operator:** role in the telemetry or monitored workload path.
- **ClusterPolicy:** role in the telemetry or monitored workload path.
- **dcgm-exporter DaemonSet:** role in the telemetry or monitored workload path.
- **Service:** role in the telemetry or monitored workload path.
- **ServiceMonitor:** role in the telemetry or monitored workload path.
- **Prometheus:** role in the telemetry or monitored workload path.
- **OpenShift dashboard ConfigMap:** role in the telemetry or monitored workload path.

### 4.2 Logical flow

1. The workload or exporter exposes an HTTP metrics endpoint, usually `/metrics`.
2. A Service and named port provide stable discovery for the endpoint.
3. A ServiceMonitor or PodMonitor selects the target and defines path, interval, scheme, TLS, and authentication.
4. Prometheus discovers the monitor resource, applies relabeling, and stores time series.
5. Recording rules precompute expensive or standardized service-level expressions.
6. PrometheusRule objects evaluate alert conditions and send firing alerts to Alertmanager.
7. Alertmanager groups, inhibits, routes, and notifies receivers.
8. OpenShift Console or Grafana queries Prometheus/Thanos and renders operational views.
9. Logs, events, and traces provide high-cardinality diagnostic context that should not be forced into metric labels.
10. Runbooks connect alerts and dashboards to deterministic triage and remediation steps.

### 4.4 Production architecture decisions

- Use platform monitoring only for supported core namespaces and components.
- Use UWM for project-owned AI applications and custom exporters.
- Use the OpenShift AI dedicated observability stack only according to its support status and your risk acceptance.
- Choose one long-term metrics architecture: in-cluster retention, remote write, or a federated/global system.
- Define a cluster label and environment label before multi-cluster aggregation.
- Use a controlled metric contract for custom runtimes and exporters.
- Keep page-generating alerts close to the user-visible failure and use lower-severity signals for diagnosis.
- Use synthetic checks for dependencies that expose no reliable server-side metric.

| 12 | Active firing alerts | `sum by (severity) (ALERTS{alertstate="firing"})` | Use bounded filters in production. |

### 9.1 Query engineering rules

- Always identify the metric type and unit before applying rate or aggregation.
- Apply rate/increase to counters before aggregation unless reset behavior is intentionally handled another way.
- Aggregate histogram buckets by `le` and required dimensions before `histogram_quantile`.
- Use `clamp_min` to avoid division by zero in ratios.
- Add a minimum-traffic guard to error-ratio and latency alerts.
- Avoid broad regex over high-cardinality labels.
- Create recording rules for queries used by multiple panels or alerts.
- Show explicit no-data behavior; absence can mean healthy idle, broken scrape, or missing instrumentation.
- Use `timestamp()` and `time()` to verify freshness.
- Benchmark query duration before publishing a fleet-wide dashboard.

## 10. Recording rules

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: dcgm-exporter-metrics-recording
  namespace: ai-monitoring-15
spec:
  groups:
    - name: dcgm-exporter-metrics.recording
      interval: 30s
      rules:
        - record: ai:dcgm-exporter-metrics:target_availability:ratio5m
          expr: avg_over_time(up{namespace="ai-monitoring-15"}[5m])
          labels:
            service: dcgm-exporter-metrics
            owner: ai-platform
        - record: ai:dcgm-exporter-metrics:pod_restarts:sum15m
          expr: sum(increase(kube_pod_container_status_restarts_total{namespace="ai-monitoring-15"}[15m]))
          labels:
            service: dcgm-exporter-metrics
        - record: ai:dcgm-exporter-metrics:signal_present
          expr: count(up) > bool 0
          labels:
            service: dcgm-exporter-metrics
```

## 11. Alert rules

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: dcgm-exporter-metrics-alerts
  namespace: ai-monitoring-15
spec:
  groups:
    - name: dcgm-exporter-metrics.alerts
      rules:

      - alert: DCGMtargetdown
        expr: min_over_time(up{namespace="ai-monitoring-15"}[5m]) == 0
        for: 5m
        labels:
          severity: critical
          service: dcgm-exporter-metrics
          owner: ai-platform
        annotations:
          summary: "DCGM target down for DCGM exporter metrics"
          description: "Signal up crossed the validated threshold. Check the linked dashboard and runbook before remediation."
          runbook_url: "https://runbooks.example.com/openshift-ai/dcgm-exporter-metrics/dcgmtargetdown"

      - alert: XIDerrorsdetected
        expr: max_over_time(DCGM_FI_DEV_XID_ERRORS[5m]) > 0
        for: 10m
        labels:
          severity: warning
          service: dcgm-exporter-metrics
          owner: ai-platform
        annotations:
          summary: "XID errors detected for DCGM exporter metrics"
          description: "Signal DCGM_FI_DEV_XID_ERRORS crossed the validated threshold. Check the linked dashboard and runbook before remediation."
          runbook_url: "https://runbooks.example.com/openshift-ai/dcgm-exporter-metrics/xiderrorsdetected"

      - alert: GPUtoohot
        expr: max_over_time(DCGM_FI_DEV_GPU_TEMP[10m]) > 85
        for: 10m
        labels:
          severity: critical
          service: dcgm-exporter-metrics
          owner: ai-platform
        annotations:
          summary: "GPU too hot for DCGM exporter metrics"
          description: "Signal DCGM_FI_DEV_GPU_TEMP crossed the validated threshold. Check the linked dashboard and runbook before remediation."
          runbook_url: "https://runbooks.example.com/openshift-ai/dcgm-exporter-metrics/gputoohot"

      - alert: GPUmemorycritical
        expr: 100 * DCGM_FI_DEV_FB_USED / clamp_min(DCGM_FI_DEV_FB_USED + DCGM_FI_DEV_FB_FREE, 1) > 90
        for: 10m
        labels:
          severity: warning
          service: dcgm-exporter-metrics
          owner: ai-platform
        annotations:
          summary: "GPU memory critical for DCGM exporter metrics"
          description: "Signal DCGM_FI_DEV_FB_USED/DCGM_FI_DEV_FB_FREE crossed the validated threshold. Check the linked dashboard and runbook before remediation."
          runbook_url: "https://runbooks.example.com/openshift-ai/dcgm-exporter-metrics/gpumemorycritical"

      - alert: Telemetrystale
        expr: time() - max(timestamp(up{namespace="ai-monitoring-15"})) > 300
        for: 10m
        labels:
          severity: warning
          service: dcgm-exporter-metrics
          owner: ai-platform
        annotations:
          summary: "Telemetry stale for DCGM exporter metrics"
          description: "Signal timestamp(up) crossed the validated threshold. Check the linked dashboard and runbook before remediation."
          runbook_url: "https://runbooks.example.com/openshift-ai/dcgm-exporter-metrics/telemetrystale"
```

### 11.1 Alert acceptance criteria

- [ ] Expression returns the intended series in normal, warning, and failure states.
- [ ] The `for` duration suppresses rollout and scrape transients.
- [ ] The alert has service, owner, severity, environment, and cluster context.
- [ ] Summary and description explain user impact, not only a metric threshold.
- [ ] Runbook is reachable by the on-call team.
- [ ] Receiver delivery is tested and evidenced.
- [ ] Silence and inhibition behavior is documented.
- [ ] Recovery is automatically verified after remediation.

## 15. Troubleshooting decision matrix

| Symptom | Likely causes | L3 evidence and action |
|---|---|---|
| No target appears | ServiceMonitor/PodMonitor selector mismatch; wrong namespace; no named service port | Compare labels and selectors; inspect Prometheus targets; verify RBAC and network policy |
| Target is down | Wrong path/port/scheme; TLS/auth failure; application not listening | curl the endpoint from a debug pod; inspect target error; verify certificate and bearer token |
| Metric is absent | Exporter disabled; metric renamed; relabeling dropped it; scrape timeout | Inspect raw /metrics; query metadata; compare image version and exporter configuration |
| Dashboard shows N/A | Wrong variable value; label mismatch; data-source permission; time range too short | Run panel query directly; inspect labels; broaden time; check data-source status |
| PromQL is slow | Unbounded regex; high cardinality; long range; missing recording rule | Use bounded matchers; pre-aggregate; reduce range; create recording rules |
| Alert never fires | Expression wrong; no data; for duration not elapsed; rule not selected | Query expression; inspect rule status; use promtool; verify PrometheusRule labels |
| Alert flaps | Threshold too tight; sparse traffic; no hysteresis; rollout transients | Add for duration, minimum traffic, separate warning/critical, or use multi-window burn |
| Notifications fail | Receiver secret/config invalid; egress/TLS/DNS issue | Inspect Alertmanager status/logs; test endpoint; check proxy and NetworkPolicy |
| Cardinality grows | Dynamic labels such as request ID, path, user, model hash | Drop/relabel labels; redesign instrumentation; cap dimensions |
| Metrics are stale | Exporter hung; target unreachable; clock issue; scrape disabled | Check timestamp(), up, scrape duration, pod health, node time sync |
| Pod metrics missing | Pod terminated; kubelet scrape issue; namespace access | Check pod UID/time range; kubelet targets; UWM namespace permissions |
| PVC metrics missing | CSI driver does not expose volume stats or volume not mounted | Check kubelet volume stats and CSI capability; use storage backend metrics |
| GPU metrics missing | dcgm-exporter absent; GPU node selector; ServiceMonitor not discovered | Check ClusterPolicy, DaemonSet, service, endpoint and raw /metrics |
| Route probe fails | DNS, TLS, router, OAuth redirect, backend endpoint | Run dig/curl -vk from internal and external probes; inspect route and endpoints |
| Model metrics missing | Runtime does not expose metrics or service port not declared | Inspect runtime docs and /metrics; patch Service/ServiceMonitor; avoid assuming KServe metrics |
| Pipeline status unclear | Backend metric names changed; task labels inconsistent | Use Kubernetes status and backend API; standardize labels and run IDs |
| Logs and metrics disagree | Different time zones/windows; sampling; pod replacement | Normalize UTC; use pod UID; correlate deployment and event timeline |
| Remote write backlog | Receiver unavailable; network issue; queue undersized | Inspect queue metrics; test endpoint; tune shards/capacity only after fixing receiver |
| Monitoring PVC fills | Retention too long; cardinality high; no capacity planning | Reduce cardinality/retention or expand PVC according to supported configuration |
| Access forbidden | RBAC or namespace isolation prevents query/target access | Use oc auth can-i; validate cluster roles and project permissions |

### 15.1 Deterministic target troubleshooting

1. Confirm the workload pod is Ready and listening on the expected port.

3. Confirm the Service port has the exact name referenced by ServiceMonitor.
4. Confirm ServiceMonitor selector matches Service labels.
5. Confirm the monitor resource is in a namespace watched by UWM.
6. Confirm NetworkPolicy allows Prometheus ingress.
7. Confirm TLS/auth settings by curling from a pod in the monitoring namespace.
8. Inspect Prometheus target error text.
9. Inspect Prometheus Operator logs for rejected configuration.
10. Inspect sample/label limits and metric relabeling.

## 16. Capacity and performance engineering

- Measure active series, samples per second, scrape payload bytes, rule duration, query duration, and retention growth.
- Estimate daily storage from measured ingestion and compression instead of a generic bytes-per-sample assumption.
- Set scrape intervals according to decision latency; do not scrape every exporter at 5 seconds without need.
- Use recording rules to reduce repeated high-cost range queries.
- Keep dashboard refresh intervals slower than scrape intervals unless a specific use case requires otherwise.
- Separate high-frequency GPU/runtime metrics from low-frequency inventory metrics.
- Load-test remote-write receivers and network paths.
- Plan PVC expansion and monitoring storage IOPS before retention changes.
- Use query logs temporarily to find expensive PromQL, then disable extra logging.
- Review top label names and values during every capacity review.

## 25. Final L3 notes

- Do not copy metric names from a blog into production without checking the live exporter.
- Do not treat a green dashboard as proof of end-user availability; include synthetic and SLO views.
- Do not page on every technical symptom; page on urgent user impact and route diagnostic warnings appropriately.
- Do not solve cardinality or storage incidents only by adding resources; fix label and query design.
- Do not make manual monitoring changes without Git history and rollback.
- Do not close an incident until monitoring confirms stable recovery and the detection gap is reviewed.
