# 09. AI platform engineering responsibilities
> **Track:** OpenShift AI Fundamentals — Corporate/L3
> **Audience:** Senior OpenShift administrators, platform engineers, MLOps engineers, SREs, security engineers, architects, and technical leads
> **Version basis:** Aligned to the Red Hat OpenShift AI Self-Managed 3.5 documentation stream available in July 2026. Always confirm support matrices, API stability, operator channels, and component status for your exact subscription and cluster release.
> **Hands-on project:** Create an AI platform operating model and production readiness framework
---
## Executive definition
AI platform engineering delivers secure, reliable, self-service AI capabilities by combining OpenShift administration, storage, networking, accelerators, automation, observability, governance, and developer experience.
This module treats the subject as an enterprise platform capability rather than a product-demo feature. The emphasis is architecture, ownership, controls, operability, failure handling, repeatability, and measurable production outcomes.
## Learning outcomes
- Define service ownership.
- Build reusable platform capabilities.
- Create SLOs and runbooks.
- Establish capacity and cost controls.
- Translate the topic into architecture diagrams, operational procedures, security controls, and acceptance tests.
- Explain trade-offs to application owners, data scientists, auditors, and senior management.
- Diagnose failures using a layer-by-layer and evidence-driven troubleshooting method.
## Scope and assumptions
- A supported Red Hat OpenShift cluster is available or planned.
- The OpenShift AI subscription, operator channel, and support matrix are validated before implementation.
- Identity, DNS, certificates, storage classes, ingress, registry access, and monitoring are treated as shared platform dependencies.
- GPU or alternative accelerator capacity is optional for fundamentals but mandatory for many production training and large-model inference workloads.
- S3-compatible object storage is planned for datasets, pipeline artifacts, model artifacts, and other lifecycle data when required.
- Production changes are delivered through Git, peer review, automated validation, and controlled promotion.
- Examples use placeholders and must not be copied into production without security review.
- Feature status can differ between General Availability, Technology Preview, Developer Preview, and community upstream implementations.
