# 20. Workbench cleanup issue

> This guide is written for senior OpenShift, Kubernetes, platform engineering, SRE, and MLOps teams.
> Commands use placeholders and must be validated in a non-production environment before production execution.
> Resource names and APIs can differ by OpenShift AI release, enabled components, and whether the workbench is a basic workbench or a project workbench.
> Discover the installed APIs first; do not assume that a resource name from another release exists in your cluster.

## Document goals

- Primary symptom: Stopping or deleting a workbench leaves resources, storage, or access artifacts behind.
- Build a reproducible lab from scratch.
- Separate dashboard symptoms from controller, Kubernetes, node, image, storage, network, identity, and external dependency failures.
- Collect an escalation-quality evidence bundle before deleting transient evidence.
- Restore service with the least risky reversible change.
- Prove recovery with technical and user-level validation.
- Convert the incident into monitoring, policy, automation, and capacity improvements.

## Version and support position

- The stable operational baseline in this guide is Red Hat OpenShift AI Self-Managed 3.4 documentation.
- OpenShift AI 3.5 documentation is used only for forward-looking differences and must not be treated as a supported production baseline unless your subscription and release channel support it.
- Custom images can be imported and made selectable, but Red Hat support does not repair unsupported content inside a customer-built image.
- In OpenShift AI 3.4, idle workbench culling is disabled by default until configured.
- The cluster-wide user session duration can take precedence over the idle workbench timeout.
- OpenShift AI 3.4 verifies culling through the `notebook-controller-culler-config` ConfigMap in `redhat-ods-applications`.
- Kubernetes `ImagePullBackOff` means the kubelet cannot pull an image and retries with increasing backoff.
- Never edit an operator-managed generated resource as the permanent fix unless the product documentation explicitly instructs you to do so.

## Executive diagnosis

### What the symptom means

Stopping or deleting a workbench leaves resources, storage, or access artifacts behind.

The dashboard status is an aggregation, not the root cause.
A senior engineer proves where progress stopped by following ownership from the user action to the generated workload.
The first irreversible action must not be deleting the Pod; first preserve events, current logs, previous logs, generated YAML, controller logs, and timestamps.
The first comparison should be between one failing workbench and one known-good workbench in the same cluster.
The second comparison should be between the same workbench before and after the last change.
The third comparison should be between the requested configuration and the object actually admitted by the API server.

### Fast severity model

| Severity | Scope | Immediate action |
|---|---|---|
| SEV-1 | Many users or all workbenches fail; business-critical development or incident response is blocked. | Activate incident command, freeze unrelated changes, collect cluster-wide evidence. |
| SEV-2 | A team, project, node pool, image family, storage class, or registry path is affected. | Assign platform, storage, network, or identity owner and begin scoped mitigation. |
| SEV-3 | One workbench or one user is affected and a workaround exists. | Preserve evidence, compare with known-good, repair safely. |
| SEV-4 | Cosmetic, intermittent, or non-production symptom. | Track as problem-management or engineering backlog. |

## Architecture and failure boundaries

A workbench request crosses several independently owned control planes.
A dashboard button can succeed while a downstream controller, admission plugin, scheduler, kubelet, CSI driver, registry, or ingress path fails.

### Boundary 1: User, dashboard, and identity

Responsibility: user-selected project, allowed groups, OAuth session, dashboard validation, ownership, and browser redirects.
Primary proof: inspect objects, status conditions, events, logs, and metrics owned by the user, dashboard, and identity boundary.
Common false assumption: a healthy adjacent layer proves that the user, dashboard, and identity boundary is healthy.
Escalation owner: identify the team with change authority over user, dashboard, and identity.
Rollback rule: reverse only the smallest change within user, dashboard, and identity that explains the failure.

### Boundary 2: OpenShift AI controllers

Responsibility: reconciliation of workbench, image, connection, culling, generated workload, and displayed status.
Primary proof: inspect objects, status conditions, events, logs, and metrics owned by the openshift ai controllers boundary.
Common false assumption: a healthy adjacent layer proves that the openshift ai controllers boundary is healthy.
Escalation owner: identify the team with change authority over openshift ai controllers.
Rollback rule: reverse only the smallest change within openshift ai controllers that explains the failure.

### Boundary 3: Kubernetes API, admission, and policy

Responsibility: RBAC, ResourceQuota, LimitRange, SCC, policy engines, webhooks, and object validation.
Primary proof: inspect objects, status conditions, events, logs, and metrics owned by the kubernetes api, admission, and policy boundary.
Common false assumption: a healthy adjacent layer proves that the kubernetes api, admission, and policy boundary is healthy.
Escalation owner: identify the team with change authority over kubernetes api, admission, and policy.
Rollback rule: reverse only the smallest change within kubernetes api, admission, and policy that explains the failure.

### Boundary 4: Scheduler, node, and accelerator

Responsibility: requests, selectors, affinity, taints, Kueue, node pressure, kubelet, device plugins, GPU drivers, and allocatable resources.
Primary proof: inspect objects, status conditions, events, logs, and metrics owned by the scheduler, node, and accelerator boundary.
Common false assumption: a healthy adjacent layer proves that the scheduler, node, and accelerator boundary is healthy.
Escalation owner: identify the team with change authority over scheduler, node, and accelerator.
Rollback rule: reverse only the smallest change within scheduler, node, and accelerator that explains the failure.

### Boundary 5: Image, storage, and external dependencies

Responsibility: registry, pull secret, proxy, certificates, package mirrors, PVC, CSI, filesystem, object storage, and identity dependencies.
Primary proof: inspect objects, status conditions, events, logs, and metrics owned by the image, storage, and external dependencies boundary.
Common false assumption: a healthy adjacent layer proves that the image, storage, and external dependencies boundary is healthy.
Escalation owner: identify the team with change authority over image, storage, and external dependencies.
Rollback rule: reverse only the smallest change within image, storage, and external dependencies that explains the failure.

### Boundary 6: Networking, access path, and observability

Responsibility: Service, EndpointSlice, Route or Gateway API, DNS, TLS, OAuth proxy, NetworkPolicy, events, logs, metrics, and audit records.
Primary proof: inspect objects, status conditions, events, logs, and metrics owned by the networking, access path, and observability boundary.
Common false assumption: a healthy adjacent layer proves that the networking, access path, and observability boundary is healthy.
Escalation owner: identify the team with change authority over networking, access path, and observability.
Rollback rule: reverse only the smallest change within networking, access path, and observability that explains the failure.

## Create the troubleshooting project from scratch

### Lab objective

Create a safe project that reproduces `Workbench cleanup issue` without modifying a production workbench.
Use a dedicated namespace, dedicated service account, explicit ResourceQuota, explicit LimitRange, small PVC, and disposable test workload.
Do not inject failures into shared operator namespaces.

### Step 1: Create the project and labels

```bash
export LAB_NS="rhoai-wb-20-workbench-cleanup-issue"
oc new-project "$LAB_NS"
oc label namespace "$LAB_NS"   app.kubernetes.io/part-of=rhoai-workbench-troubleshooting   troubleshooting.redhat.com/topic="workbench-cleanup-issue"   environment=lab --overwrite
```
Expected result: the project exists and the current user can create namespaced resources.
Failure meaning: project creation failure is a prerequisite or RBAC problem, not a workbench problem.

### Step 2: Create a bounded service account and pull-secret placeholder

```yaml

  name: wb-lab
```


### Step 3: Create ResourceQuota and LimitRange

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: wb-lab-quota
spec:
  hard:
    requests.cpu: "4"
    requests.memory: 8Gi
    limits.cpu: "8"
    limits.memory: 16Gi
    persistentvolumeclaims: "5"
---
apiVersion: v1
kind: LimitRange
metadata:
  name: wb-lab-limits
spec:
  limits:
  - type: Container
    defaultRequest:
      cpu: 250m
      memory: 512Mi
    default:
      cpu: "1"
      memory: 2Gi
```
This deliberately exposes quota and defaulting behavior for troubleshooting.

### Step 4: Create baseline storage

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: wb-home
spec:
  accessModes:
  - ReadWriteOnce
  resources:
    requests:
      storage: 2Gi
```
If the cluster has no default StorageClass, set `storageClassName` explicitly.
Wait for `Bound` before treating a later mount failure as a kubelet or filesystem problem.

### Step 5: Create a baseline workload that tests the same platform dependencies

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: wb-baseline

        - |
          id
          test -w /workspace
          echo baseline > /workspace/baseline.txt
          sleep infinity

            cpu: 100m
```

The baseline does not replace an OpenShift AI workbench.
It isolates core scheduling, image, secret, PVC, arbitrary-UID, and node behavior before the product controller is involved.

## Evidence collection bundle

### Evidence rules

- Use UTC timestamps.
- Redact tokens, passwords, access keys, cookies, and private registry credentials.
- Do not redact resource names, event reasons, status conditions, image digests, node names, or timestamps unless policy requires it.
- Collect previous container logs before deleting or restarting the Pod.
- Collect namespace events before their retention window expires.
- Record the exact user action and browser-visible error.
- Record the last known good time and first known bad time.
- Record changes to images, quotas, profiles, storage classes, operators, certificates, proxy, DNS, and identity.
- Compare failing and known-good objects with `oc diff` or normalized YAML.
- Include cluster and OpenShift AI versions in every escalation.

### Collection script

```bash
#!/usr/bin/env bash
set -euo pipefail
NS="${1:?namespace required}"
POD="${2:-}"
STAMP="$(date -u +%Y%m%dT%H%M%SZ)"
OUT="rhoai-workbench-evidence-${NS}-${STAMP}"
mkdir -p "$OUT"

oc version > "$OUT/oc-version.txt" 2>&1 || true
oc get clusterversion -o yaml > "$OUT/clusterversion.yaml" 2>&1 || true
oc get datasciencecluster,dscinitialization -A -o yaml > "$OUT/rhoai-control-plane.yaml" 2>&1 || true
oc get csv -A > "$OUT/csv.txt" 2>&1 || true
oc api-resources > "$OUT/api-resources.txt" 2>&1 || true
oc get all -n "$NS" -o wide > "$OUT/all-wide.txt" 2>&1 || true
oc get all -n "$NS" -o yaml > "$OUT/all.yaml" 2>&1 || true
oc get events -n "$NS" --sort-by=.lastTimestamp > "$OUT/events.txt" 2>&1 || true
oc get pvc,secret,configmap,serviceaccount,role,rolebinding,networkpolicy -n "$NS" -o yaml > "$OUT/supporting.yaml" 2>&1 || true
oc get route,httproute,service,endpoints,endpointslice -n "$NS" -o yaml > "$OUT/network.yaml" 2>&1 || true
oc get resourcequota,limitrange -n "$NS" -o yaml > "$OUT/policy.yaml" 2>&1 || true
oc get nodes -o wide > "$OUT/nodes.txt" 2>&1 || true
oc adm top nodes > "$OUT/top-nodes.txt" 2>&1 || true
```

### Failed container detector

```bash
oc get pod -A -o json | jq -r '
.items[] as $p |
($p.status.containerStatuses // [])[]? |
select(.state.waiting.reason != null or .lastState.terminated.reason != null) |
[
  $p.metadata.namespace,
  $p.metadata.name,
  .name,
  (.state.waiting.reason // .lastState.terminated.reason),
  (.restartCount|tostring)
] | @tsv'
```
### Pending reason report

```bash
oc get pod -A --field-selector=status.phase=Pending -o json | jq -r '
.items[] |
[
 .metadata.namespace,
 .metadata.name,
 ([.status.conditions[]? | select(.type=="PodScheduled") | .reason] | join(",")),
 ([.status.conditions[]? | select(.type=="PodScheduled") | .message] | join(" "))
] | @tsv'
```

## Change, rollback, and validation

1. State the confirmed root cause and evidence.
2. Define the smallest declarative change.
3. Identify affected users and maintenance need.
4. Record the last approved configuration.
5. Define technical rollback commands.
6. Define user-level validation.
7. Apply in a lab or canary project.
8. Observe reconciliation and events.
9. Validate access, kernel, storage, and restart behavior.
10. Roll out to remaining scope.
11. Monitor the soak window.
12. Close with evidence and update the runbook.

### Validation matrix

| Domain | Pass condition | Proof |
|---|---|---|
| Controller | Desired resource reconciles without error. | Status conditions and controller logs. |
| Pod | Running, Ready, stable restart count. | Pod status and events. |
| Storage | Read/write and persistence across restart. | File checksum before and after. |
| Secret | Expected keys are available without exposing values. | Key names and application behavior. |
| Network | Service has endpoints and URL returns expected authenticated response. | EndpointSlice, route status, curl headers. |
| IDE | JupyterLab or selected IDE loads. | User test. |
| Kernel | Kernel starts and executes a basic cell. | Notebook output and kernel logs. |
| Resource | No OOM, excessive throttling, eviction, or GPU allocation error. | Metrics and container state. |
| Cleanup | Stop/delete behavior matches retention policy. | Remaining object inventory. |

## Preventive engineering

- Maintain one known-good Red Hat-provided workbench canary per hardware and storage class.
- Pin approved custom images by digest and retain rollback digests.
- Test arbitrary UID, writable paths, base URL, probes, certificates, and package lock files in CI.
- Run a registry pull test from every eligible node pool.
- Continuously verify PVC provisioning and mount latency.
- Validate hardware profiles against actual node labels, taints, allocatable resources, and quota.
- Alert on unschedulable workbench Pods and prolonged image pulls.
- Alert on repeated container restarts and OOMKilled terminations.
- Monitor CPU throttling and memory headroom by profile.
- Validate Service endpoints and authenticated workbench URL synthetically.
- Review user group, project RoleBinding, and secret access regularly.
- Document idle timeout and cluster session timeout precedence.
- Automate orphan-resource inventory and cleanup approval.
- Test disconnected mirrors, proxy, noProxy, and custom CA changes before rollout.
- Keep an evidence collection script in the operations repository.
- Run quarterly game days using the fault injections in this guide.

## End-of-guide competency checklist

- [ ] I can create a safe workbench troubleshooting lab.
- [ ] I can discover the installed workbench APIs rather than assume them.
- [ ] I can preserve evidence before restarting.
- [ ] I can follow ownership from dashboard to controller to Pod and dependencies.
- [ ] I can interpret events and status conditions.
- [ ] I can diagnose scheduling, storage, image, secret, access, route, GPU, memory, CPU, and permission failures.
- [ ] I can repair the declarative source rather than a generated child.
- [ ] I can validate at both platform and user levels.
- [ ] I can execute and prove rollback.
- [ ] I can produce an escalation-quality evidence package.
- [ ] I can add alerts, canaries, policies, and game days to prevent recurrence.
