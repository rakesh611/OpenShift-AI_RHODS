# 12. Network latency tuning
> Corporate/L3 engineering guide for Red Hat OpenShift AI performance engineering.
> Baseline: Red Hat OpenShift AI 3.5 and OpenShift Container Platform 4.20 documentation available in July 2026.
> Treat every numeric value as a starting hypothesis. Validate it with workload-specific tests on the target hardware and storage.
---
## 1. Executive objective
Minimize request-path latency and jitter across pod, service, route, ingress, DNS, TLS, and external storage paths.
This guide treats **cluster and endpoint networking** as an end-to-end system rather than a single Pod setting.
The L3 engineer is expected to correlate application behavior, Kubernetes scheduling, OpenShift platform services, storage, networking, and hardware telemetry.
A change is accepted only when it improves the target SLO without creating an unacceptable regression in reliability, security, cost, or tenant fairness.

## 2. Performance engineering operating model
1. Define the user-visible objective before selecting a metric.
2. Measure end-to-end latency and decompose it into queue, service, storage, and network components.
3. Use percentiles and distributions; averages hide contention and long tails.
4. Keep a control run, a treatment run, and a documented rollback threshold.
5. Repeat tests after caches are cold and after caches are warm.
6. Record cluster version, operator versions, node type, GPU model, driver, runtime image, and model revision.
7. Avoid benchmarking on an uncontrolled shared cluster unless noisy-neighbor effects are the experiment.
8. Preserve security controls during tuning; disabling TLS, authentication, or isolation is not an acceptable optimization.
9. Distinguish request from limit, reservation from use, and utilization from saturation.
10. Optimize the critical path, not the most visible graph.
11. Confirm statistical significance or at least repeatability before production rollout.
12. Deploy through GitOps so the winning configuration is reviewable and reversible.

### 5.1 Workload-specific inspection checklist
1. Record creation timestamp, scheduled timestamp, container start timestamp, and readiness transition.
2. Compare requested resources with observed p50, p95, and peak usage.
3. Inspect Pod QoS class and whether CPU limits cause CFS throttling.
4. Check node allocatable resources, pressure conditions, and competing workloads.
5. Inspect PVC mode, mounted filesystem, backend health, and zone placement.
6. Check route, service endpoints, DNS resolution, TLS negotiation, and connection reuse.
7. For GPU workloads, record GPU model, driver, firmware, device plugin, runtime, MIG mode, and DCGM metrics.
8. For LLM workloads, record model revision, precision, quantization, max context, scheduler settings, and parallelism.
9. For pipelines, record component image digests, cache settings, artifact sizes, retry policy, and DAG critical path.

## 6. Measurement plan
| Layer | Question | Evidence | Decision |
|---|---|---|---|
| Client | Is the delay visible before the request reaches OpenShift? | client timing, DNS and TLS breakdown | fix client, network or request shape |
| Ingress | Does the route add queueing, retries, or handshake cost? | router metrics and logs | tune path, keepalive or capacity |
| Service | Are requests balanced across ready endpoints? | endpoint and connection metrics | fix readiness or distribution |
| Pod | Is the process saturated, throttled, blocked, or restarting? | container and runtime metrics | right-size or tune concurrency |
| Node | Is the node CPU, memory, GPU, I/O, or network saturated? | node exporter, DCGM and events | move, isolate or add capacity |
| Storage | Is data or model access the critical path? | CSI and backend telemetry | change layout, class or locality |
| Object storage | Are request count, object size, or transfer concurrency limiting? | S3 client and backend metrics | tune multipart and layout |
| Application | Does the algorithm or model dominate? | profiler and runtime metrics | optimize code, precision, batch or model |
## 7. Benchmark design
1. Define the workload population and representative data distribution.
2. Define concurrency, arrival pattern, burst behavior, and think time.
3. Define cold-cache and warm-cache test phases.
4. Use fixed model, image, dataset, and configuration digests.
5. Run a warmup period that is excluded from the measured interval.
6. Collect client-side and server-side timestamps.
7. Run long enough to expose garbage collection, cache eviction, autoscaling, and thermal behavior.
8. Record errors and timeouts; do not calculate latency only from successful requests.
9. Repeat tests and compare distributions, not a single best run.
10. Stop the test when safety thresholds are exceeded.

## 8. Tuning workflow
1. **Observe:** Collect immutable evidence before changing anything.
2. **Localize:** Identify whether the dominant wait is admission, queue, CPU, GPU, memory, storage, network, or application.
3. **Hypothesize:** State a falsifiable explanation and the metric that would confirm it.
4. **Change:** Modify the smallest practical control through a reviewed manifest.
5. **Load test:** Use the same traffic model and data as the baseline.
6. **Compare:** Check the target metric and all guardrails.
7. **Fail safely:** Rollback immediately on reliability, security, or cost regression.
8. **Promote:** Move the validated configuration through GitOps overlays.
9. **Monitor:** Watch for workload drift and revalidate after upgrades.

## 12. Validation gates
- [ ] Gate 1: Functional output is correct for a golden dataset or request set.
- [ ] Gate 2: Target latency or throughput improves across repeated trials.
- [ ] Gate 3: Error rate does not regress.
- [ ] Gate 4: No new OOM, eviction, restart, or readiness failures appear.
- [ ] Gate 5: Resource usage remains inside quota and node safety margins.
- [ ] Gate 6: Autoscaling does not oscillate or exceed capacity assumptions.
- [ ] Gate 7: Failover or restart behavior remains inside the availability objective.
- [ ] Gate 8: Security controls, TLS, authentication, network policy, and audit remain enabled.
- [ ] Gate 9: Cost per successful unit is measured and accepted.
- [ ] Gate 10: Runbook, dashboard, alert, owner, and rollback are updated.
## 13. Troubleshooting decision tree
```text
SLO violation
  |-- Is demand above tested capacity? -- yes --> rate limit, scale, or add capacity
  |
  |-- Is the Pod pending? -- yes --> inspect quota, requests, affinity, taints, GPU and topology
  |
  |-- Is the Pod restarting or unready? -- yes --> inspect OOM, probes, runtime and dependency failures
  |
  |-- Is queue time high? -- yes --> tune concurrency, batching, replicas and admission
  |
  |-- Is CPU throttled? -- yes --> correct limit, request and thread count
  |
  |-- Is GPU idle? -- yes --> inspect CPU/input pipeline, batch size, precision and synchronization
  |
  |-- Is storage/network slow? -- yes --> isolate path, locality, object layout and backend saturation
  |
  `-- Profile application/model execution and compare with a known-good build
```
### 13.1 Symptom-to-evidence matrix
| Symptom | First evidence | Likely domains | Immediate safe action |
|---|---|---|---|
| Pod Pending | events and scheduler reason | quota, requests, affinity, taints, GPU | do not reduce requests blindly; identify the constraint |
| High p99 only | latency histogram and queue depth | contention, retries, GC, storage tail | capture traces and compare affected requests |
| Low GPU use | DCGM plus CPU and input timing | small batch, CPU starvation, I/O, sync | run a controlled synthetic input test |
| OOM kill | pod status and memory series | limit, leak, batch, model/KV cache | rollback the last memory-increasing change |
| Slow startup | events, image pull and model load logs | registry, S3/PVC, runtime warmup | preserve logs and measure each phase |
| HPA not scaling | HPA conditions and metrics API | missing metric, missing request, selector | fix metric availability before changing target |
| Replica oscillation | desired/current replica history | metric noise, cooldown, cold start | increase stabilization only after confirming signal |
| Pipeline delay | critical path and pod timeline | DAG, scheduler, image, S3 | identify the longest blocking step |
## 14. Production change plan
1. Create a change ticket with hypothesis, blast radius, owner, and rollback.
2. Confirm monitoring and alert routing before rollout.
3. Apply the change to a canary workload or limited tenant.
4. Run the approved smoke and load tests.
5. Observe at least one representative peak window when feasible.
6. Compare with the previous release using the same dashboard window.
7. Promote gradually and stop on guardrail violation.
8. Update capacity and cost forecasts with the measured result.
9. Close the change only after rollback artifacts and documentation are stored.

## 17. Incident runbook
1. Declare impact, affected users, first observed time, and current error-budget effect.
2. Freeze tuning changes and identify recent deployments, node changes, quotas, storage, network, or operator updates.
3. Use a known-good request or pipeline input to reproduce the symptom.
4. Build a timestamped timeline from client, route, service, Pod, node, storage, and external dependencies.
5. Check pending, restart, OOM, eviction, readiness, and autoscaling conditions.
6. Compare affected and unaffected replicas or nodes.
7. Reduce blast radius using traffic shift, concurrency cap, rollback, or minimum warm replicas.
8. Avoid destructive restarts until logs, events, and transient metrics are preserved.
9. Validate recovery against the original SLO and golden request set.
10. Create follow-up actions for code, configuration, capacity, alerting, and documentation.
### 17.1 Evidence bundle
- [ ] Namespace objects and custom resources in YAML.
- [ ] Events sorted by time.
- [ ] Pod and operator logs.
- [ ] Prometheus snapshots or exported query results.
- [ ] Node description and allocatable resources.
- [ ] GPU/DCGM evidence when applicable.
- [ ] Storage and S3 timing.
- [ ] Client timing and payload shape.
- [ ] Git diff and deployment history.
- [ ] Final root cause, contributing factors, and validation evidence.
## 18. Capacity and cost model
Use measured service demand rather than nominal hardware specifications.
| Model item | Calculation approach |
|---|---|
| Required replicas | ceil(peak demand per second / sustainable demand per replica) + failure reserve |
| CPU request | p95 steady CPU plus startup allowance and an explicit safety margin |
| Memory request | p95 working set plus cache/fragmentation allowance |
| GPU capacity | concurrent models × GPUs per replica + maintenance/failure reserve, adjusted for fragmentation |
| Storage throughput | sum of concurrent read/write demand at the critical workload phase |
| Object storage requests | objects per run × concurrent runs, separated into GET, PUT, LIST, and multipart operations |
| Network capacity | payload bytes × request rate plus protocol, retry, and replication overhead |
| Cost per unit | allocated infrastructure and platform cost / successful requests, tokens, samples, or runs |
## 19. Security and governance constraints
1. Do not bypass authentication or TLS to claim a performance improvement.
2. Do not place secrets in notebooks, pipeline arguments, environment dumps, or benchmark reports.
3. Use signed and scanned images from approved registries.
4. Preserve namespace isolation and NetworkPolicy during tests.
5. Mask sensitive prompts, model inputs, outputs, and datasets in logs.
6. Review priority, quota, and affinity changes for tenant fairness.
7. Apply node-level performance profiles only through the approved platform change process.
8. Document whether a feature is generally available, Technology Preview, or unsupported in the installed release.
9. Keep benchmark data retention and access aligned with organizational policy.
10. Require peer review for production SLO, autoscaling, GPU, and node tuning changes.
