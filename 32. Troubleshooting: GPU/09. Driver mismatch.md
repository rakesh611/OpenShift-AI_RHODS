# 09. Driver mismatch

> Corporate L3 troubleshooting and hands-on project guide for Red Hat OpenShift AI and OpenShift Container Platform.

## Document control

- Topic: **Driver mismatch**
- Audience: Senior OpenShift administrators, platform engineers, SREs, MLOps engineers, and GPU infrastructure specialists
- Depth: Corporate L3 / production support
- Product context: Red Hat OpenShift AI 3.x, OpenShift Container Platform 4.x, NVIDIA GPU Operator, CUDA, DCGM
- Method: Build a healthy baseline, reproduce controlled faults, collect evidence, isolate the failing layer, remediate, validate, and prevent recurrence
- Safety: Perform disruptive tests only in a disposable lab or an approved maintenance window
- Version rule: Verify the supported OpenShift, OpenShift AI, GPU Operator, driver, CUDA, and GPU combination before production changes

## 1. Executive summary

This guide treats **Driver mismatch** as a layered platform incident rather than a single command failure.
 
The primary diagnostic layer is host kernel driver, driver container version, NVML user space, toolkit mounts, and upgrade sequencing.
 
A reliable investigation moves from physical inventory to node discovery, operator reconciliation, driver and runtime readiness, Kubernetes resource advertisement, pod admission, application compatibility, and observability.
 
The most important L3 behavior is to preserve evidence before changing the node. A reboot can clear symptoms while destroying the information required to identify the real root cause.
 
Every remediation in this guide includes a validation gate. Do not declare recovery merely because a pod becomes Running; prove device visibility, CUDA execution, resource accounting, telemetry, and workload-level success.
 
## 2. Learning objectives

- Explain where Driver mismatch sits in the OpenShift AI GPU dependency chain.
- Create a reproducible GPU validation project from scratch.
- Separate hardware, node OS, Operator, Kubernetes scheduler, container runtime, CUDA, and application failures.
- Use `oc`, node debugging, NVIDIA utilities, Prometheus data, and application logs without making unsupported assumptions.
- Design controlled fault-injection exercises that are reversible and safe.
- Produce an enterprise incident timeline, evidence package, root-cause analysis, and preventive action plan.
- Automate baseline checks so that drift is detected before users report failures.

## 4. GPU dependency chain

1. Physical GPU or cloud/vGPU assignment is present.
2. Firmware and PCIe topology expose the device to the operating system.
3. OpenShift node is Ready and the device is visible through `lspci`.
4. NFD labels the node and NVIDIA GPU Feature Discovery adds GPU-specific labels.
5. GPU Operator reconciles the ClusterPolicy and deploys required operands.
6. Driver loads kernel modules and exposes `/dev/nvidia*` devices.
7. Container Toolkit configures CRI-O and the NVIDIA runtime handler.
8. Device plugin registers extended resources with kubelet.
9. Scheduler admits a pod that requests the correct resource name.
10. Runtime injects devices and user-space libraries into the container.
11. CUDA/framework/app supports the driver, GPU architecture, and requested workload mode.
12. DCGM exporter and Prometheus provide health and performance telemetry.

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: gpu-lab-driver-mismatch
  labels:
    purpose: gpu-troubleshooting
---
apiVersion: v1
kind: Pod
metadata:
  name: gpu-validation
  namespace: gpu-lab-driver-mismatch
spec:
  restartPolicy: Never
  containers:
  - name: cuda
    image: nvcr.io/nvidia/cuda:12.6.3-base-ubi9
    command: ["bash", "-lc"]
    args:
    - |
      echo "Starting GPU validation"
      nvidia-smi
      sleep 3600
    resources:
      limits:
        nvidia.com/gpu: 1
```

## 9. Initial 15-minute triage

1. Freeze unnecessary changes and identify whether impact is cluster-wide, node-specific, project-specific, image-specific, or workload-specific.
2. Capture pod status, scheduling events, requested resources, node assignment, and last transition times.
3. Check all GPU Operator and NFD pods and identify the earliest unhealthy dependency.
4. Compare node `capacity` and `allocatable` values with the physical GPU inventory.
5. Run `lspci`, `lsmod`, `dmesg`, and `nvidia-smi -q` through a supported node debug workflow.
6. Check recent upgrades, MachineConfigPool rollout, node reboot, firmware change, image change, quota change, and hardware-profile change.
7. Test a known-good CUDA image and a minimal framework operation.
8. Check DCGM metrics and Xid/thermal/ECC signals for hardware degradation.
9. Decide whether to isolate the node, drain it, or keep it online for evidence collection.
10. State the current hypothesis, supporting evidence, contradictory evidence, and next discriminating test.

## 16. Automation: evidence collection script

```bash
#!/usr/bin/env bash
set -euo pipefail
NODE=${1:?Usage: $0 <gpu-node> [namespace]}
NS=${2:-nvidia-gpu-operator}
STAMP=$(date +%Y%m%d-%H%M%S)
OUT=gpu-evidence-${NODE}-${STAMP}
mkdir -p "$OUT"
oc get node "$NODE" -o yaml > "$OUT/node.yaml"
oc describe node "$NODE" > "$OUT/node-describe.txt"
oc get pods -A -o wide > "$OUT/pods-all.txt"
oc get events -A --sort-by=.lastTimestamp > "$OUT/events.txt"
oc get clusterpolicy -A -o yaml > "$OUT/clusterpolicy.yaml" 2>&1 || true
oc get nodefeaturediscovery -A -o yaml > "$OUT/nfd.yaml" 2>&1 || true
oc logs -n "$NS" -l app=gpu-operator --all-containers --tail=2000 > "$OUT/operator.log" 2>&1 || true
oc debug node/"$NODE" -- chroot /host bash -lc 'lspci -nnk; lsmod; nvidia-smi -q; dmesg -T | tail -2000' > "$OUT/node-hardware.txt" 2>&1 || true
tar -czf "${OUT}.tgz" "$OUT"
echo "Created ${OUT}.tgz"
```
