The Kueue Operator is a Kubernetes-native batch job queueing and resource management system designed for AI/ML, HPC, batch processing, and GPU-intensive workloads.

It solves a major Kubernetes limitation:

Kubernetes schedules Pods individually, but enterprise AI/ML environments need scheduling at the job/workload level.

Kueue introduces:

Job queueing

Resource quotas

Fair sharing

Cluster-wide workload admission control

GPU-aware scheduling

Multi-tenant governance

In enterprise AI platforms like Red Hat OpenShift AI and Kubeflow, Kueue acts as the central batch scheduler for:

Training jobs

Fine-tuning jobs

Distributed inference

Ray clusters

Spark jobs

MPI workloads

Pipeline executions

Why Kueue Was Needed

Kubernetes Native Scheduler Limitation

Default Kubernetes scheduler works like this:
```plain
Pod → Find Node → Schedule
```
But AI environments need:
```plain
Job → Validate Resources → Queue → Fair Share → Admit → Run
```
Example problem:

Suppose:

Team A submits 20 GPU jobs

Team B submits 2 urgent jobs

Without Kueue:

Team A can consume all GPUs

Team B starves

Kueue solves this using:

Queues

Cohorts

Quotas

PriorityClasses

Admission checks

Major Kueue Components

1. ClusterQueue

This is the MOST IMPORTANT Kueue object.

A ClusterQueue defines:

Resource quotas

Available hardware

Borrowing policies

Fair-sharing logic

Example:
```yaml
apiVersion: kueue.x-k8s.io/v1beta1
kind: ClusterQueue
metadata:
  name: gpu-clusterqueue
spec:
  resourceGroups:
  - coveredResources: ["cpu", "memory", "nvidia.com/gpu"]
    flavors:
    - name: gpu-a100
      resources:
      - name: cpu
        nominalQuota: 200
      - name: memory
        nominalQuota: 1Ti
      - name: nvidia.com/gpu
        nominalQuota: 16
```
This means:

Total 16 GPUs available

Shared across workloads

2. LocalQueue

Namespace-specific queue mapped to ClusterQueue.

Example:
```yaml
apiVersion: kueue.x-k8s.io/v1beta1
kind: LocalQueue
metadata:
  name: ds-team-queue
  namespace: data-science
spec:
  clusterQueue: gpu-clusterqueue
```
Purpose:

Tenant isolation

Namespace-level job submission

3. Workload

4. ResourceFlavor

Defines hardware classes.

Example:

A100 GPUs

H100 GPUs

Spot nodes

CPU-only nodes

Example:
```yaml

  name: a100

  nodeLabels:

```
This allows:

GPU-aware scheduling

Hardware affinity

5. Cohorts

Cohorts allow quota borrowing across queues.

Example:
```plain
Team-A Queue → 8 GPUs
Team-B Queue → 8 GPUs

Unused GPUs can be borrowed dynamically.
```
Critical for:

Enterprise GPU utilization

AI clusters with burst workloads

Admission Control (Very Important)

This is Kueue’s key innovation.

Without Kueue:

Pods immediately compete for resources

With Kueue:

Job waits until ALL required resources are available

Example:
```plain
Training Job requires:
- 8 GPUs
- 256 GB RAM
- 64 CPU

Kueue blocks partial scheduling.
```
This prevents:

Deadlocks

Partial distributed training failures

GPU fragmentation

Fair Sharing

Enterprise Multi-Tenant Scheduling

Kueue uses:

Queue weights

Priority

Borrowing

Fair-share policies

Example:

| Team          | GPU Quota |
| ------------- | --------- |

| Vision Team   | 8         |
| Research Team | 4         |

Kueue ensures:

No starvation

Controlled bursting

Balanced utilization

Gang Scheduling

Critical for distributed AI training.

Problem Without Gang Scheduling

Distributed training requires ALL pods simultaneously.

Example:

8-worker PyTorchJob

Without gang scheduling:

5 pods scheduled

3 pending

Entire training hangs

Kueue solves this:

Admit only when all resources available
