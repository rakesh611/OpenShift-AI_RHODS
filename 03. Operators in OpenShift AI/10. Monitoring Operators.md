In Kubernetes and Red Hat OpenShift, Monitoring Operators automate the deployment, lifecycle management, scaling, configuration, and upgrades of the monitoring stack.

A Monitoring Operator is not just “install Prometheus.”

It becomes the control plane for observability inside the cluster.

It manages:

Metrics collection

Alerting

Logging integrations

Dashboards

Service discovery

Retention policies

HA monitoring

TLS/security

Remote write/federation

Monitoring CRDs

Upgrade orchestration

1. Why Monitoring Operators Exist

Before Operators:

Teams manually installed:

Prometheus

Grafana

Alertmanager

Exporters

Configurations were static

Scaling was difficult

Service discovery was manual

Upgrades caused outages

HA setup was complex

In Kubernetes:

Pods are dynamic

IPs change

Services scale automatically

Nodes join/leave frequently

Traditional monitoring tools fail in such environments.

So Kubernetes introduced:

Controllers

Reconciliation loops

CRDs

Operators

Monitoring Operators make observability:

Kubernetes-native

Self-healing

Declarative

Automated

5. CRDs Used by Monitoring Operators

A. ServiceMonitor

Defines service-based scraping.

Example:
```yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: nginx-monitor
spec:
  selector:
    matchLabels:
      app: nginx
  endpoints:
  - port: metrics
    interval: 30s
```
What Happens Internally

Operator:

Watches ServiceMonitor

Generates scrape config

Updates Prometheus config secret

Reloads Prometheus dynamically

B. PodMonitor

Used when monitoring pods directly.

Useful for:

Sidecars

Stateful workloads

DaemonSets

Example:
```yaml
kind: PodMonitor
spec:
  selector:
    matchLabels:
      app: redis
```
C. PrometheusRule

Stores alerting and recording rules.

Example:
```yaml
groups:
- name: node-alerts
  rules:
  - alert: HighCPUUsage
    expr: node_cpu_seconds_total > 80
```
Operator loads these automatically.

D. Probe

Used for:

Blackbox monitoring

HTTP checks

DNS checks

TCP checks

Example:
```yaml
kind: Probe
spec:
  prober:
    url: blackbox-exporter.monitoring.svc:9115
```

17. Cardinality (Very Important)

Most production Prometheus failures happen because of:

High Cardinality

Bad metric:
```plain
http_request_id_938383838
```
Every unique label creates new time series.

Explosion occurs.

Best practice:

Avoid dynamic labels

Avoid user/session IDs

Control histogram buckets

23. Production Best Practices

Use Separate Monitoring Tiers

Platform monitoring

Application monitoring

Business monitoring

Use Retention Policies

Different retention:

| Metrics Type | Retention |
| ------------ | --------- |
| Infra        | 15d       |
| Audit        | 90d       |
| Business KPI | 1 year    |

Use Dedicated Nodes

Monitoring is resource-intensive.

Use:
```yaml
nodeSelector:
  monitoring: "true"
```
Use Anti-affinity

Prevent replicas on same node.

Use Remote Write

For DR and central analytics.
