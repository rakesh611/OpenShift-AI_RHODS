> **Level:** Red Hat OpenShift AI Corporate/L3 — intended for engineers with approximately 10+ years of Linux, Kubernetes, OpenShift, DevOps, SRE, or platform experience.

## 1. Executive objective

Enable controlled collaboration among data scientists, ML engineers, data engineers, application developers, security teams, and SREs while preserving reproducibility and accountability.

**Corporate design position:** Collaboration should occur through shared project services and versioned artifacts, not by sharing personal tokens or attaching every user to the same writable workbench home volume.

### 2.1 Control-plane and data-plane reasoning
- The OpenShift AI dashboard is the supported user workflow and orchestration interface.
- Kubernetes and OpenShift APIs are the enforcement and reconciliation layer.
- Project resources are namespace scoped unless a shared platform component is explicitly cluster or platform scoped.
- External systems such as S3-compatible object storage, databases, Git, identity providers, and registries remain separate failure and security domains.
- GitOps is the preferred enterprise mechanism for repeatable baselines, while dynamic user workloads may remain dashboard managed with policy controls.

## 5. From-scratch implementation workflow

**Primary dashboard path:** `OpenShift AI dashboard → Projects → Permissions, Workbenches, Pipelines, Models`

1. Open an approved service request containing business purpose, data classification, environments, expected users, resource sizing, recovery objectives, and expiry/review date.
2. Validate that the requested project name follows DNS-compatible enterprise naming and does not expose sensitive information.
3. Map identity-provider groups to project administrator, contributor, auditor, and automation roles.
4. Create or select the OpenShift project namespace and apply mandatory ownership, environment, cost-center, lifecycle, and classification metadata.
5. Apply baseline RBAC and test positive and negative access using `oc auth can-i --as`.
6. Apply ResourceQuota and LimitRange values based on measured workload estimates and shared-cluster capacity.
7. Apply default-deny network policy and explicit allow rules for DNS, image registry, object storage, pipelines, serving, monitoring, and approved APIs.
8. Provision project storage and data connections without exposing credentials in Git, tickets, notebooks, or shell history.
9. Create the required workbench, pipeline, registry integration, or serving resource through the supported dashboard workflow.
10. Export version-sensitive resources, sanitize generated fields, and place only safe declarative configuration in Git.
11. Run functional, security, performance, backup, restore, and rollback validation appropriate to the topic.
12. Capture evidence and hand over the project with ownership, support, monitoring, cost, and lifecycle responsibilities documented.

### 6.1 Safe manifest handling
- Use `oc explain <resource> --recursive` against the target cluster before editing fields.
- Export a supported dashboard-created resource when the API schema is release-sensitive.
- Remove `status`, `managedFields`, `uid`, `resourceVersion`, `generation`, and `creationTimestamp` before committing.
- Do not commit Secret data, bearer tokens, S3 keys, database passwords, kubeconfigs, or signed URLs.
- Use namespace overlays for environment-specific names, endpoints, StorageClasses, and quota sizes.
- Run server-side dry-run and policy tests before merge.
- Require peer review from platform and security owners for RBAC, network, SCC, and external exposure changes.
- Record the tested OpenShift and OpenShift AI versions in the repository README.

## 8. Troubleshooting method

Use the following evidence-first sequence:
1. Restate the failed user action, expected result, actual result, time, namespace, identity, and affected resource.
2. Confirm login identity and active project with `oc whoami` and `oc project`.
3. Check authorization with `oc auth can-i` using the real user or service-account identity.
4. Inspect the custom resource, owner references, conditions, finalizers, and events.
5. Identify the reconciling operator and inspect its deployment health and logs.
6. Inspect generated pods, services, routes/gateways, PVCs, Secrets, and service accounts.
7. Check quota, LimitRange, scheduling, node labels, taints, tolerations, accelerator availability, and image pulls.
8. Check NetworkPolicy, DNS, proxy, certificate trust, object-store endpoint, database endpoint, and egress controls.
9. Compare current state with Git and the last known-good manifest.
10. Apply the smallest reversible change, capture evidence, and retest the original user action.

## 9. Security and compliance controls

1. Use group-based RBAC and prohibit shared human accounts.
2. Separate project administration from platform administration.
3. Minimize Secret read permissions; Kubernetes `edit` may be broader than some enterprises permit.
4. Use short-lived credentials or workload identity where supported.
5. Apply default-deny network policies and explicit allow rules.
6. Enforce approved images, signed artifacts, vulnerability scanning, and supported runtimes.
7. Encrypt storage and object-store traffic; validate custom CA trust explicitly.
8. Apply data-classification labels and retention rules to PVCs, buckets, and model artifacts.
9. Capture OpenShift audit records and application-specific audit evidence.
10. Review service accounts, tokens, role bindings, routes, and external credentials periodically.
11. Require expiry dates and compensating controls for exceptions.
12. Test revocation, user offboarding, and compromised-credential response.

## 12. Backup, restore, and disaster recovery

1. Inventory all namespaced resources and distinguish declarative configuration from mutable data.
2. Protect PVC data with supported snapshots or data movement according to the storage backend.
3. Protect external object storage with versioning, replication, lifecycle protection, or native backup.
4. Protect pipeline metadata databases and artifact buckets consistently.
5. Protect model registry metadata and artifact backends according to registry architecture.
6. Store manifests in Git, but do not assume Git is a backup for PVCs, databases, or object data.
7. Document storage-class, identity-provider, route/gateway, certificate, and endpoint mappings for alternate-cluster restore.
8. Rotate credentials after a recovery event when confidentiality cannot be guaranteed.
9. Run scheduled restore tests and capture measured RPO/RTO.
10. Obtain business acceptance using representative notebooks, pipelines, and model predictions.

## 21. Glossary

- **Project:** OpenShift AI organizational construct backed by an OpenShift project/namespace for namespaced resources.
- **Workbench:** Managed development environment, commonly represented by a Notebook custom resource and related pod, storage, service, and route resources.
- **Data connection:** Dashboard-visible configuration that injects credentials and endpoint information, commonly backed by a Secret.
- **Pipeline server:** Project-attached service that stores and runs AI pipeline definitions, runs, metadata, and artifacts.
- **Model server:** Serving environment that loads a model artifact and exposes an inference endpoint.
- **Model registry:** Shared lifecycle and metadata repository for registered models and versions; distinct from serving.
- **ResourceQuota:** Namespace-scoped aggregate resource and object limit.
- **LimitRange:** Namespace policy that provides or enforces per-object/container request and limit constraints.
- **RBAC:** Role-based access control using Roles/ClusterRoles and bindings to users, groups, and service accounts.
- **NetworkPolicy:** Namespaced policy controlling allowed pod ingress and egress when supported by the cluster network provider.
- **PVC:** PersistentVolumeClaim used by workloads to request durable storage.
- **S3-compatible storage:** Object storage accessed through an API compatible with common S3 operations.
- **RPO:** Maximum acceptable data-loss interval.
- **RTO:** Maximum acceptable service-recovery duration.
- **GitOps:** Declarative configuration management in which Git-reviewed desired state is reconciled to clusters.
