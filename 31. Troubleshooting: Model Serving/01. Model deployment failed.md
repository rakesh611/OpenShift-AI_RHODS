# 01. Model deployment failed

## 1. Purpose and scope

Deployment request is accepted but the model never becomes usable.

This runbook is for senior Red Hat OpenShift AI platform engineers, SREs, MLOps engineers, and escalation teams. It uses evidence-driven isolation and avoids blind restarts.

### Learning outcomes

1. Reproduce **Model deployment failed** safely.
2. Read KServe conditions and generated OpenShift resources.
3. Separate control-plane, storage, runtime, scheduling, networking, authentication, and capacity faults.
4. Apply the smallest corrective change.
5. Validate infrastructure and model semantics.
6. Add preventive controls, metrics, and escalation evidence.

## 2. Relevant architecture

```text
Dashboard/GitOps -> InferenceService -> KServe controller -> ServingRuntime -> workload -> pod
Model source -> storage initializer/mount -> /mnt/models -> runtime process -> readiness
Client -> DNS -> router/gateway -> route -> service -> EndpointSlice -> predictor pod
```

### Failure domains

| Domain | What to inspect | Typical evidence |
|---|---|---|
| API/control plane | InferenceService spec/status and controller reconciliation | conditions, generation, events |
| Runtime | ServingRuntime image, formats, protocol, command, args | runtime YAML and logs |
| Storage | URI, connection secret, CA, artifact layout | initializer logs and `/mnt/models` |
| Scheduling | requests, limits, quota, taints, affinity, accelerator | pod events and node allocatable |
| Process | exit code, probes, memory, GPU, ports | current/previous logs and status |
| Network | service, EndpointSlice, route/gateway, policy, DNS | curl tests and resource YAML |
| Security | token, service account, RBAC, gateway policy, TLS | 401/403, TokenReview, policy logs |
| Performance | latency, queue, CPU/GPU/memory, replicas | Prometheus metrics and load test |

## 3. Incident signature

### Primary symptom

**Model deployment failed**

### Typical signals

- Ready=False.
- No Ready predictor pod.
- Warning events.
- Runtime or storage errors.

### User impact

- A model can be unavailable, partially degraded, or slow.
- Pipelines can block while waiting for `Ready=True`.
- Retries can increase router, storage, CPU, GPU, and queue pressure.
- A rollout can affect only the new revision or all replicas.

### Severity model

| Severity | Example |
|---|---|
| SEV-1 | Shared serving dependency or multiple critical models unavailable. |
| SEV-2 | One critical production model unavailable or outside SLO. |
| SEV-3 | Partial/nonproduction impact with a workaround. |
| SEV-4 | Lab, documentation, or preventive-control defect. |

## 4. Root-cause hypotheses

| ID | Hypothesis | Proof standard |
|---|---|---|
| RC-01 | platform/runtime disabled | Confirm with a condition, event, log, metric, or direct component test. |
| RC-02 | invalid InferenceService YAML | Confirm with a condition, event, log, metric, or direct component test. |
| RC-03 | image pull failure | Confirm with a condition, event, log, metric, or direct component test. |
| RC-04 | storage secret failure | Confirm with a condition, event, log, metric, or direct component test. |
| RC-05 | unschedulable resources | Confirm with a condition, event, log, metric, or direct component test. |
| RC-06 | runtime exits | Confirm with a condition, event, log, metric, or direct component test. |

A valid root cause identifies the component, exact invalid state, trigger, causal evidence, and why controls did not prevent it.

- Required accelerator operators are healthy when using GPUs or other accelerators.

Prefer the OpenShift AI dashboard so the generated secret uses the schema expected by the installed release. For CLI-only work, inspect an approved connection and reproduce its key names exactly.

## 6. Reproduce **Model deployment failed** safely

### Fault-injection objective

In an isolated project, **reference a nonexistent runtime**.

### Save the last-known-good revision

```bash
oc get inferenceservice "$ISVC" -n "$NS" -o yaml > known-good-isvc.yaml
oc get servingruntime,clusterservingruntime -A -o yaml > known-good-runtimes.yaml
```

### Observe the fault

```bash
oc annotate inferenceservice "$ISVC" -n "$NS" lab.example/fault="model-deployment-failed" --overwrite
oc get inferenceservice "$ISVC" -n "$NS" -w
oc get events -n "$NS" --sort-by=.lastTimestamp
oc get pod,deploy,svc,route,endpoints,endpointslice -n "$NS" -o wide
```

### Safety guardrails

- Never inject the fault into production.
- Time-box the exercise.
- Preserve the good YAML and evidence.
- Do not print real credentials.
- Remove temporary policies or resource reductions.
- Confirm the namespace is healthy after cleanup.

## 7. Corporate L3 triage workflow

### 7.1 Freeze the facts

Record incident UTC time, cluster, namespace, model, release, runtime, artifact digest/version, caller type, endpoint, and last change.

### 7.2 Read status before restarting

```bash
oc get inferenceservice "$ISVC" -n "$NS" -o json | jq '{generation:.metadata.generation,observedGeneration:.status.observedGeneration,url:.status.url,conditions:.status.conditions}'
```

Decision order:

1. Compare `metadata.generation` and `status.observedGeneration`.
2. Find the earliest concrete False condition.
3. Read its reason, message, and transition time.
4. Follow the dependency named by that message.
5. Treat `Ready=False` as a summary, not the root cause.

### 7.3 Trace both dependency chains

```text
InferenceService -> workload -> pod -> service -> endpoints -> route/gateway -> client
InferenceService -> runtime -> image -> storage -> /mnt/models -> model process
```

```bash
oc get inferenceservice "$ISVC" -n "$NS" -o yaml
oc get pod,deploy,rs,svc,route,endpoints,endpointslice -n "$NS" --show-labels
oc get events -n "$NS" --sort-by=.lastTimestamp | tail -n 100
```

### 7.4 Inspect lifecycle and previous logs

```bash
POD=$(oc get pod -n "$NS" -l serving.kserve.io/inferenceservice="$ISVC" -o jsonpath='{.items[0].metadata.name}' 2>/dev/null || true)
oc describe pod "$POD" -n "$NS"
oc logs "$POD" -n "$NS" --all-containers --tail=300
oc logs "$POD" -n "$NS" --all-containers --previous --tail=300
oc get pod "$POD" -n "$NS" -o json | jq '.status.containerStatuses'
```

### 7.5 Test one hop at a time

```bash
oc get svc,endpoints,endpointslice,route -n "$NS" -o wide
oc run netcheck -n "$NS" --rm -it --restart=Never --image=registry.access.redhat.com/ubi9/ubi-minimal -- sh
```

Test service DNS internally before testing the external host. Internal success plus external failure isolates the problem above the service layer.

### 7.6 Preserve evidence

```bash
TS=$(date +%Y%m%d-%H%M%S)
mkdir -p "evidence/$TS"
oc get inferenceservice "$ISVC" -n "$NS" -o yaml > "evidence/$TS/isvc.yaml"
oc get pod,deploy,rs,svc,route,endpoints,endpointslice -n "$NS" -o yaml > "evidence/$TS/resources.yaml"
oc get events -n "$NS" --sort-by=.lastTimestamp > "evidence/$TS/events.txt"
oc logs "$POD" -n "$NS" --all-containers --tail=1000 > "evidence/$TS/logs.txt" 2>&1 || true
oc logs "$POD" -n "$NS" --all-containers --previous --tail=1000 > "evidence/$TS/previous-logs.txt" 2>&1 || true
```


## 8. Topic-specific diagnosis

### 8.1 Confirm the status and condition reason

```bash
oc get inferenceservice "$ISVC" -n "$NS" -o wide
oc describe inferenceservice "$ISVC" -n "$NS"
oc get inferenceservice "$ISVC" -n "$NS" -o json | jq '.status.conditions'
```

Expected evidence to correlate:

- Ready=False.
- No Ready predictor pod.
- Warning events.
- Runtime or storage errors.

### 8.2 Prove or eliminate each hypothesis

1. Prove or eliminate **platform/runtime disabled** using status, events, logs, metrics, and a direct test.
2. Prove or eliminate **invalid InferenceService YAML** using status, events, logs, metrics, and a direct test.
3. Prove or eliminate **image pull failure** using status, events, logs, metrics, and a direct test.
4. Prove or eliminate **storage secret failure** using status, events, logs, metrics, and a direct test.
5. Prove or eliminate **unschedulable resources** using status, events, logs, metrics, and a direct test.
6. Prove or eliminate **runtime exits** using status, events, logs, metrics, and a direct test.

### 8.3 Runtime and model compatibility

```bash
oc get servingruntime -n "$NS" -o yaml
oc get clusterservingruntime -o yaml
oc get inferenceservice "$ISVC" -n "$NS" -o json | jq '.spec.predictor'
```

Compare runtime `metadata.name`, `supportedModelFormats`, protocol versions, image architecture, ports, accelerator resources, model path, custom arguments, and environment variables.

### 8.4 Scheduling and resource checks

```bash
oc get pod -n "$NS" -o wide
oc describe pod "$POD" -n "$NS"
oc get nodes -o custom-columns=NAME:.metadata.name,CPU:.status.allocatable.cpu,MEM:.status.allocatable.memory,GPU:.status.allocatable.nvidia\.com/gpu
oc get resourcequota,limitrange -n "$NS" -o yaml
```

Look for `FailedScheduling`, taints, affinity mismatch, quota, insufficient CPU/memory/GPU/ephemeral storage, and differences between the requested hardware profile and generated pod.

### 8.5 Storage checks

```bash
oc get secret "$S3_SECRET" -n "$NS" -o json | jq '.metadata.name,.type,(.data|keys)'
oc logs "$POD" -n "$NS" --all-containers --tail=500 | egrep -i 's3|storage|download|model|artifact|denied|not found|timeout|x509'
oc exec -n "$NS" "$POD" -c kserve-container -- sh -c 'id; ls -la /mnt/models; du -sh /mnt/models 2>/dev/null || true'
```

Confirm expected filenames, sizes, checksum, tokenizer/config, shard indexes, and exact case-sensitive path.

### 8.6 Endpoint checks

```bash
oc get svc,endpoints,endpointslice,route -n "$NS" -o wide
oc get route -n "$NS" -o yaml
oc get svc -n "$NS" -o yaml
curl -skv "https://$HOST/v1/models" -o /tmp/response.txt
```

Validate route admission, service selectors, EndpointSlice Ready addresses, route target port, service targetPort, runtime port, host, path, protocol, and model name.

### 8.7 Interpret HTTP outcomes

| Result | Primary interpretation |
|---|---|
| 401 | Missing, malformed, invalid, expired, or wrong token type. |
| 403 | Authenticated but not authorized, or a different dependency such as S3/KMS denied access. |
| 404 | Wrong host, path, model name, API version, or route target. |
| 503 | No healthy backend, bad target port, overload, or rollout/scale gap. |
| Timeout | DNS, NetworkPolicy, route, proxy, service endpoint, or backend saturation. |

## 9. Remediation

Apply only the correction supported by evidence:

1. Restore valid runtime.
2. Fix storage and image access.
3. Right-size resources.
4. Reconcile after preserving evidence.

### Controlled reconciliation

```bash
oc annotate inferenceservice "$ISVC" -n "$NS" troubleshooting.example/reconciled-at="$(date -Iseconds)" --overwrite
oc get inferenceservice "$ISVC" -n "$NS" -w
```

A harmless annotation change is preferable to deleting the resource because it preserves identity and evidence.

### Restore the lab baseline

```bash
oc apply -f known-good-isvc.yaml
oc get inferenceservice "$ISVC" -n "$NS" -w
```

For GitOps-managed resources, commit the correction and use the approved emergency synchronization process.

## 10. Validation

### Infrastructure

```bash
oc get inferenceservice "$ISVC" -n "$NS" -o json | jq '.status.conditions'
oc get pod,deploy,svc,route,endpoints,endpointslice -n "$NS" -o wide
oc get events -n "$NS" --sort-by=.lastTimestamp | tail -n 50
```

Required results:

- `Ready=True`.
- `observedGeneration` matches the current generation.
- Stable Ready predictor pod.
- Ready service endpoints.
- Admitted external route only when intended.
- No repeating warning event.

### Functional and semantic validation

```bash
curl -skv -H 'Content-Type: application/json' \
  ${TOKEN:+-H "Authorization: Bearer $TOKEN"} \
  "https://$HOST/<runtime-specific-path>" -d @known-good-request.json
```

Validate response status, schema, model identity/version, deterministic test-vector output, and latency. A 200 response from the wrong model is not a successful recovery.

### Soak test

Run controlled traffic for 15-30 minutes. Compare error rate, P95/P99 latency, CPU, throttling, memory, GPU, queue, replica count, and restarts with the last known good release.

## 11. Monitoring and alerting

| Signal | Why it matters | Suggested alert behavior |
|---|---|---|
| InferenceService Ready condition | Direct service readiness | Alert when False beyond normal cold start. |
| Condition transition age | Detects stuck reconciliation | Alert on sustained False/Unknown. |
| Ready endpoint count | Proves usable backend capacity | Alert when zero for exposed production model. |
| Predictor restart count | Detects process instability | Alert on repeated restarts. |
| HTTP 4xx/5xx by model | Separates client/auth/backend failure | Alert on SLO-impacting rates. |
| P95/P99 and TTFT | Detects user-visible degradation | Compare to model-specific SLO. |
| CPU throttle and memory usage | Detects resource constraints | Alert before OOM/SLO breach. |
| GPU memory/KV cache/queue | Detects accelerator pressure | Correlate with concurrency and latency. |
| Autoscaler desired/current replicas | Detects scaling failure | Alert on prolonged divergence. |
| Model load/download duration | Detects cold-start/storage regression | Compare by artifact size and release. |

## 12. Prevention controls

1. Validate artifact existence, checksum, format, and companion files in CI.
2. Pin model and runtime images by immutable version or digest.
3. Validate YAML and policy before merge.
4. Maintain a version/runtime/model/accelerator compatibility matrix.
5. Run canary inference and semantic tests before promotion.
6. Retain last-known-good manifests, digests, secrets, and rollback steps.
7. Derive resources from measured startup and steady-state profiles.
8. Test route, TLS, token, and NetworkPolicy changes in preproduction.
9. Track cold-start and model-load P95/P99.
10. Use synthetic probes with a deterministic payload and output assertion.

## 13. Common mistakes

- Restarting before collecting previous logs and conditions.
- Deleting the InferenceService and losing evidence.
- Treating every 403 as OpenShift RBAC.
- Using `curl -k` as the permanent TLS fix.
- Raising every resource limit without measurement.
- Using mutable image tags or model paths.
- Comparing display names instead of `metadata.name`.
- Testing only HTTP status, not model semantics.
- Hand-creating resources that fight KServe reconciliation.
- Ignoring GitOps, admission, quota, and policy controllers.

## 14. Escalation evidence

Collect and redact:

- Cluster, OpenShift, and OpenShift AI versions.
- Namespace, InferenceService, runtime, and release.
- Incident UTC timeline and last change.
- Generation, observedGeneration, and all conditions.
- InferenceService and runtime YAML.
- Generated workload, pod, service, route, and EndpointSlice YAML.
- Sorted events and current/previous logs for every container.
- Container termination reason and exit code.
- Node resources, labels, taints, quota, and LimitRange.
- NetworkPolicy and route/gateway configuration.
- Artifact URI without credentials, version, digest, and checksum.
- Runtime image digest.
- Exact request with token redacted and response headers/body.
- Metrics queries and last-known-good comparison.

## 15. Senior review questions

1. Which controller owns the failing resource?
2. Which condition failed first?
3. Was observedGeneration current?
4. Can a minimal supported model reproduce the issue?
5. Does internal access work while external access fails?
6. Which component emitted the HTTP error?
7. What changed immediately before impact?
8. Is the artifact immutable and verifiable?
9. Is resource pressure causal or merely correlated?
10. Which automated control should prevent recurrence?
