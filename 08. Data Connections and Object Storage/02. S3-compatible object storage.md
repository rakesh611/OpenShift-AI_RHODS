# 02. S3-compatible object storage
> Scope: enterprise architecture, implementation from scratch, validation, security, performance, observability, failure analysis, and operational governance.
## 1. Executive summary
S3 compatibility means that a storage platform implements enough of the Amazon S3 API and authentication behavior for S3 clients to create buckets and manipulate objects. Compatibility is not binary: endpoint syntax, Signature Version 4, region handling, virtual-hosted addressing, lifecycle actions, encryption headers, object lock, and multipart behavior can differ.
This chapter is written for a senior OpenShift AI engineer who must design the control plane and data path, implement the project, prove the result, and own production incidents. Commands are examples; replace names, endpoints, credentials, regions, storage classes, and resource sizes with approved values.
## 2. Learning outcomes

## 3. Architecture deep dive
### 3.1. Architecture element
Client SDK or CLI signs each request using credentials, request headers, timestamp, region, and canonical resource path.
### 3.2. Architecture element
Endpoint resolves to an S3 gateway, cloud service, or in-cluster service.
### 3.3. Architecture element
Gateway authenticates the access key and evaluates identity, bucket, and object permissions.
### 3.4. Architecture element
Bucket namespace contains objects addressed by keys; directories are logical prefixes rather than filesystems.
### 3.5. Architecture element
Multipart upload divides large objects into independently transferred parts and completes them with a manifest.
### 3.6. Architecture element
Versioning, lifecycle, replication, retention, and encryption are provider-side controls.
### 3.7. Architecture element
OpenShift AI consumes the service through a data connection rather than depending on provider-specific APIs.
### 3.9. End-to-end request path
1. The user or controller selects a project-scoped connection.
2. The consuming workload receives connection metadata and credentials through a supported mechanism.
3. Cluster DNS resolves the endpoint hostname.
4. NetworkPolicy, firewall, proxy, route, and load balancer permit the flow.
5. TLS validates endpoint identity and protects the request.
6. The client signs the S3 request using the configured region and credential.
7. The provider authenticates the principal and evaluates authorization.
8. The gateway and backend complete the object operation.
9. Metrics, audit events, and request IDs provide operational evidence.
## 4. Corporate design decisions
- Create a compatibility matrix before approving a provider for pipelines and model serving.
- Test the exact SDK versions used in notebook, pipeline, and serving images.
- Standardize region values even when the provider treats region as optional.
- Record whether a custom endpoint requires path-style addressing.
- Validate list, get, put, delete, multipart, range-read, and presigned URL behavior.
- Do not assume AWS-specific IAM, KMS, eventing, or lifecycle semantics exist on every compatible platform.
### 4.1. Mandatory decision record
- Business owner and platform owner
- Environment and data classification
- Provider, region, endpoint, and addressing style
- Bucket and prefix ownership
- Credential type, scope, owner, and rotation interval
- TLS certificate and CA ownership
- Encryption and key-management model
- RPO, RTO, retention, versioning, and lifecycle
- Expected object count, size distribution, throughput, and latency
- Monitoring, alerting, escalation, and change windows
## 5. Project from scratch
### 5.1. Reference scenario
Build a project named `rhoai-connection-lab` for a fraud-detection team. The team needs read-only datasets, write-enabled pipeline artifact storage, immutable model storage, and a separate backup target. Production controls are demonstrated in a non-production namespace before rollout.
### 5.2. Prerequisites
- OpenShift Container Platform cluster with Red Hat OpenShift AI installed and Ready.
- OpenShift AI project-owner or administrator permissions for the lab namespace.
- `oc`, `kubectl`, `aws`, `curl`, `openssl`, `jq`, and Python 3 with `boto3` available from an approved toolbox.
- Reachability from the OpenShift AI workload network to the object-storage endpoint.
- An object-storage test account that is isolated from production data.
- A change record and rollback plan for production exercises.
### 5.3. Implementation sequence
1. Deploy or obtain an S3-compatible endpoint.
2. Create a tenant or account and a restricted user.
3. Create a test bucket and enable versioning if supported.
4. Upload small, medium, and multipart test objects.
5. Test read-after-write behavior, range requests, metadata, and checksum handling.
6. Create an OpenShift AI connection Secret.
7. Run boto3 and AWS CLI compatibility tests from a workbench pod.
8. Test model loading from a nested prefix.
9. Test pipeline artifact upload and download.
10. Document unsupported S3 APIs and approved workarounds.

### 5.5. Topic-specific implementation examples
#### Example 1
```bash
aws --endpoint-url https://s3.example.com s3api list-buckets
aws --endpoint-url https://s3.example.com s3api head-bucket --bucket rhoai-lab
aws --endpoint-url https://s3.example.com s3 cp ./sample.bin s3://rhoai-lab/compat/sample.bin
aws --endpoint-url https://s3.example.com s3api head-object   --bucket rhoai-lab --key compat/sample.bin
```
#### Example 2
```bash
python - <<'PY'
import boto3
s3 = boto3.client(
    "s3",
    endpoint_url="https://s3.example.com",
    region_name="us-east-1",
)
print(s3.list_objects_v2(Bucket="rhoai-lab", Prefix="compat/"))
PY
```
### 5.6. Generic OpenShift AI S3 connection Secret
```yaml
apiVersion: v1
kind: Secret
metadata:
  name: lab-s3-connection
  namespace: rhoai-connection-lab
  annotations:
    opendatahub.io/connection-type-protocol: "s3"
type: Opaque
stringData:
  AWS_S3_ENDPOINT: "https://s3.example.com"
  AWS_S3_BUCKET: "rhoai-lab"
  AWS_ACCESS_KEY_ID: "REPLACE_ME"
  AWS_SECRET_ACCESS_KEY: "REPLACE_ME"
  AWS_DEFAULT_REGION: "us-east-1"
```
Apply through an approved secure process. A successful Secret creation only proves that Kubernetes accepted the object; it does not prove that the provider, endpoint, region, policy, or TLS configuration is correct.
## 6. Security engineering
- Require TLS and validate the issuing CA.
- Restrict account permissions to approved buckets and prefixes.
- Verify support for server-side encryption and audit its actual enforcement.
- Disable anonymous access and test that unauthenticated requests fail.
- Review implementation-specific CVEs and supported versions.
### 6.1. Minimum production controls
- Project-specific least-privilege identity
- TLS verification with an approved CA
- Encryption at rest with governed keys
- Public and anonymous access disabled
- RBAC restriction on Secret reads
- Provider data-plane audit logging
- Credential rotation and emergency revocation
- Backup or recoverability appropriate to data tier
- Admission and Git scanning to prevent secret leakage
- Quarterly entitlement and bucket-policy review
## 7. Performance and capacity
- Benchmark GET, PUT, LIST, HEAD, DELETE, and multipart operations separately.
- Test representative object-size distributions, not only large sequential files.
- Measure concurrency scaling and the error rate under load.
- Confirm consistency behavior for overwrite, delete, and list operations.
- Watch gateway CPU, memory, disk, network, and backend storage latency.
### 7.1. Benchmark matrix
| Test | Object profile | Concurrency | Evidence |
|---|---:|---:|---|
| Metadata baseline | HEAD/LIST | 1 and 20 | p50/p95/p99 latency |
| Small objects | 1 KiB–1 MiB | 1, 20, 100 | operations/s and errors |
| Medium objects | 64–512 MiB | 4, 8, 16 | throughput and CPU |
| Large objects | 1–20 GiB | multipart | part size, throughput, retries |
| Model package | actual layout | serving replicas | cold-start phases |
| Pipeline artifacts | actual task output | concurrent runs | upload/download time |
## 8. Observability and SRE
Monitor at least the following signals:
- 4xx and 5xx rate
- time to first byte
- PUT and GET throughput
- multipart completion failures
- gateway saturation
- backend disk latency
### 8.1. Correlation dimensions
- OpenShift namespace, pod, service account, and workload name
- Connection Secret name without displaying values
- Provider principal or access-key identifier
- Bucket and object prefix
- Endpoint and region
- HTTP status, S3 error code, request ID, and timestamp
- Object size and operation type
- Gateway/backend health event and change record
## 9. Troubleshooting matrix
| Symptom | Likely cause | L3 corrective action |
|---|---|---|
| SignatureDoesNotMatch | Canonical request, region, clock, proxy, or path-style difference | Compare signed request inputs and test with the provider's recommended client settings. |
| PermanentRedirect or wrong-region response | Endpoint and region do not match the bucket | Use the provider's regional endpoint and correct region. |
| List works but upload fails | Missing PutObject permission or unsupported encryption header | Inspect policy and retry without provider-incompatible headers. |
| Large uploads fail | Multipart limits, proxy body limits, timeout, or incomplete-upload policy | Test explicit part size and bypass intermediate proxies. |
### 9.1. Evidence-first triage order
1. Capture the exact error, timestamp, namespace, workload, operation, and recent change.
2. Verify the workload references the intended connection.
3. Verify Secret metadata and required key names without printing values.
4. Resolve DNS from the failing pod.
5. Test TCP and TLS using the configured hostname.
6. Run a signed `HeadBucket` request with the same endpoint and region.
7. Run a prefix list or `HeadObject` for the exact object.
8. Use provider audit or gateway logs and correlate the request ID.
9. Inspect backend storage and network saturation.
10. Apply one targeted correction and retest the complete workload.
## 10. Failure-injection drills
- Rotate the access key while a workbench remains running; document whether restart or reload is required.
- Remove `ListBucket` but retain `GetObject`; observe application behavior.
- Use an incorrect region and capture the S3 error.
- Present an untrusted certificate and confirm the client rejects it.
- Block egress with NetworkPolicy and validate the alert path.
- Rename or delete the connection Secret in a lab and observe controller behavior.
- Throttle or saturate the object gateway and measure retry/tail-latency behavior.
- Delete a test object version and perform a documented restore.
## 11. Validation and acceptance
- Secret contains the required field names and the S3 protocol annotation.
- Endpoint resolves and is reachable from the actual consumer namespace.
- TLS verification succeeds without insecure bypass flags.
- `HeadBucket` succeeds with the intended credential.
- Required object operations succeed and explicitly forbidden operations fail.
- Workbench, pipeline, or serving workload references the intended connection.
- Provider audit logs show the expected principal and source.
- No credentials appear in Git, pod logs, events, or support artifacts.
- Performance meets the documented baseline for representative object sizes.
- Credential rotation and workload recovery have been tested.

## 12. Advanced L3 field notes
- An S3-compatible label does not guarantee support for every AWS feature.
- Model servers often expose differences sooner than notebooks because startup depends on deterministic object download behavior.
- Keep compatibility tests in CI so provider upgrades or client-image changes are detected before production.
- Keep a sanitized request sample that records endpoint, region, addressing style, SDK version, and error code.
- Provider upgrades and client-image upgrades should trigger automated compatibility regression tests.
- Use workload-specific service accounts to improve attribution even when the storage credential is stored in a Secret.
- A storage incident can appear as a notebook, pipeline, or model-serving incident; follow the shared request path.
- Do not confuse provider replication, Kubernetes PVC protection, and application-level backup; they cover different failure modes.
- Document every intentional deviation from the standard with owner, expiry date, and compensating control.
