# 19. Pipeline YAML error

> Red Hat OpenShift AI Corporate L3 troubleshooting and hands-on project runbook

- **Topic:** Pipeline YAML error
- **Audience:** OpenShift AI platform engineers, SREs, cluster administrators, ML platform engineers, and L3 support
- **Depth:** Senior/corporate production troubleshooting
- **Format:** Architecture + build-from-scratch lab + failure injection + diagnosis + remediation + prevention
- **Version posture:** Discovery-driven and version-aware; verify all exact resource names against the installed OpenShift AI release
- **Safety:** Perform destructive exercises only in a disposable project or lab cluster

---

## 1. Executive summary

**Primary symptom:** Pipeline YAML cannot be imported, applied, parsed, or executed.

**Primary technical layer:** KFP compilation, IR schema, Kubernetes manifest validation, parameter typing, and import parsing.

**L3 recovery principle:** Regenerate from source with a supported KFP SDK, validate YAML and schema, inspect server-side dry-run errors, and avoid hand-editing compiled IR.

A senior engineer must avoid jumping directly to deletion or broad privilege changes. The correct approach is to map the visible symptom to the pipeline lifecycle, identify the first broken dependency, collect immutable evidence, apply a minimal reversible correction, and validate the entire control-plane and data-plane path.

OpenShift AI pipelines are based on Kubeflow Pipelines concepts. Product releases can change API modes, generated resource names, metadata storage, workspace behavior, and supported SDK versions. Always use `oc api-resources`, DSPA status, installed release documentation, and actual labels/selectors to discover the implementation.

## 2. Learning objectives

- Explain how Pipeline YAML error appears in the OpenShift AI dashboard, API, Kubernetes objects, events, and logs.

- Collect evidence suitable for an internal incident record or Red Hat support case.
- Use least-privilege RBAC and avoid unsafe cluster-wide shortcuts.
- Create a deterministic canary pipeline and acceptance tests.
- Design monitoring, alerts, SLOs, and preventive controls.
- Handle version skew between OpenShift AI, KFP SDK, Python, and compiled IR.
- Automate repeatable health checks without leaking credentials.
- Lead an L3 incident from detection through post-incident review.

## 5. Symptom recognition and impact

- Pipeline YAML cannot be imported, applied, parsed, or executed.
- Dashboard operation returns a generic error while Kubernetes events contain the actual failure.
- A run changes state but one task remains Pending, Running, Error, or Terminating.
- The main container and the launcher/driver container report different outcomes.
- Artifacts or metadata are absent even though business code appears to have completed.
- The issue affects only one namespace because project-scoped credentials, quota, policy, or storage differs.
- The issue affects all namespaces because a shared controller, registry, object store, DNS path, or upgrade changed.
- Repeated retries create noise, cost, and more orphaned resources without improving diagnosis.

**Potential business impact**

- Model training, validation, batch inference, or promotion workflows stop.
- Artifacts may be incomplete, inconsistent, or unavailable for audit.
- Scheduled retraining or data-quality checks miss their service window.
- GPU and compute resources remain allocated to stuck tasks.
- Teams lose confidence in platform reliability and bypass governed workflows.
- Incident response can cause data loss if engineers delete pipeline servers, metadata stores, PVCs, or buckets prematurely.

## 8. Build the lab from scratch

The following project creates a controlled troubleshooting environment. Adjust API fields to your installed release and use the OpenShift AI dashboard when that is the supported configuration path.

**8.1 Define environment variables**

```bash
export NS=rhoai-pipeline-l3-lab
export SA=pipeline-l3-runner
export BUCKET=<approved-lab-bucket>
export S3_ENDPOINT=<https://s3-compatible-endpoint>
export AWS_REGION=<region>
```

**8.2 Create and label the project**

```bash
oc new-project "$NS"
oc label namespace "$NS" purpose=rhoai-pipeline-l3-lab --overwrite
oc project "$NS"
```

**8.3 Create a dedicated service account**

```bash
oc create serviceaccount "$SA" -n "$NS"
oc get serviceaccount "$SA" -n "$NS" -o yaml
```

**8.4 Create the object-storage connection secret safely**

```bash
read -r -p "Access key ID: " AWS_ACCESS_KEY_ID
read -r -s -p "Secret access key: " AWS_SECRET_ACCESS_KEY
echo
oc create secret generic pipeline-lab-s3   -n "$NS"   --from-literal=AWS_ACCESS_KEY_ID="$AWS_ACCESS_KEY_ID"   --from-literal=AWS_SECRET_ACCESS_KEY="$AWS_SECRET_ACCESS_KEY"   --from-literal=AWS_S3_ENDPOINT="$S3_ENDPOINT"   --from-literal=AWS_DEFAULT_REGION="$AWS_REGION"   --from-literal=AWS_S3_BUCKET="$BUCKET"
unset AWS_ACCESS_KEY_ID AWS_SECRET_ACCESS_KEY
```

> The exact secret keys and labels expected by the OpenShift AI dashboard/DSPA can vary by release. Prefer creating a data connection through the supported UI or documented API, then inspect only metadata—not decoded values.

**8.7 Create a reproducible Python toolchain**

```bash

```

**8.8 Create a minimal canary pipeline**

```bash
cat > canary_pipeline.py <<'PY'
from kfp import dsl, compiler

@dsl.component(base_image="registry.access.redhat.com/ubi9/python-311")
def producer(text: str) -> str:
    print(f"producer received: {text}")
    return text.upper()

@dsl.component(base_image="registry.access.redhat.com/ubi9/python-311")
def consumer(value: str):
    print(f"consumer received: {value}")
    assert value, "value must not be empty"

@dsl.pipeline(name="rhoai-l3-canary")
def pipeline(message: str = "healthy"):
    p = producer(text=message)
    consumer(value=p.output)

if __name__ == "__main__":
    compiler.Compiler().compile(
        pipeline_func=pipeline,
        package_path="rhoai-l3-canary.yaml",
    )
PY

python canary_pipeline.py
head -n 20 rhoai-l3-canary.yaml
```

## 9. Failure-injection project for this topic

**Goal:** Reproduce **Pipeline YAML error** without touching production.

**Failure injection:** Compile a valid sample, then intentionally remove pipelineSpec or alter a parameter type to compare YAML parser, API validation, and runtime errors.

**Procedure**

1. Create or select a disposable lab project.
2. Confirm the canary pipeline succeeds before the fault is introduced.
3. Export baseline YAML, events, logs, storage tests, and timing.
4. Introduce exactly one fault.
5. Run the canary or topic-specific test once.
6. Capture the first observable deviation and all downstream symptoms.
7. Use the decision tree to find the primary failure.
8. Apply the minimal correction.
9. Rerun with the same inputs and caching disabled where relevant.
10. Compare healthy, failed, and recovered evidence.
11. Remove the fault and verify no persistent side effects remain.
12. Write a concise root-cause statement and prevention action.

## 10. Root-cause taxonomy

01. **file is plain workflow YAML rather than compiled KFP IR**
02. **YAML indentation or syntax is invalid**
03. **pipelineSpec key is missing where required**
04. **unknown or unsupported schema version is used**
05. **component inputs and outputs have incompatible types**
06. **parameter default cannot be serialized**
07. **duplicate names violate compiler or Kubernetes rules**
08. **container command/args serialize incorrectly**
09. **Kubernetes-native wrapper fields are malformed**
10. **file exceeds API or UI size constraints**
11. **templating tool corrupts multiline YAML**
12. **SDK/compiler version is incompatible with the server**


### Root cause 01: file is plain workflow YAML rather than compiled KFP IR

**Why this cause fits:** This failure belongs to KFP compilation, IR schema, Kubernetes manifest validation, parameter typing, and import parsing. The visible symptom can be misleading, so confirm it with Kubernetes events, workload state, and the component-specific logs before changing configuration.

**Evidence to collect before remediation**
- Record the exact timestamp, project, run ID/name, task/component name, user, and service account.
- Capture the full error string without paraphrasing it.
- Export the DSPA and affected pod/workload YAML.
- Collect namespace events sorted by time.
- Collect logs from every container, including previous logs after a restart.
- Record recent changes to images, secrets, RBAC, storage, network policy, quotas, and product versions.
- Determine whether the failure is reproducible in a new run with caching disabled.
- Compare a failed run with the most recent successful run.

**Commands**

```bash
oc get dspa -n "$NS" -o yaml > evidence/dspa.yaml
oc get pod -n "$NS" -o wide > evidence/pods.txt
oc get events -n "$NS" --sort-by=.lastTimestamp > evidence/events.txt
oc get pod <affected-pod> -n "$NS" -o yaml > evidence/affected-pod.yaml
oc describe pod <affected-pod> -n "$NS" > evidence/affected-pod.describe.txt
oc logs <affected-pod> -n "$NS" --all-containers=true --prefix=true > evidence/affected-pod.log 2>&1
```

**Decision logic**

- If the event or log explicitly references **file is plain workflow YAML rather than compiled KFP IR**, treat this branch as confirmed.
- If the pod never started, prioritize scheduling, admission, image pull, and volume events over application logs.
- If the main container succeeded but the task failed, inspect launcher, driver, sidecar, and artifact-handling logs.
- If only one project fails, compare namespace-scoped objects and policies with a healthy project.
- If all projects fail, move upward to the operator, shared services, storage endpoint, registry, DNS, or cluster change.
- If the issue began immediately after an upgrade, compare supported versions and recompile pipeline definitions in a clean environment.

**Remediation sequence**

1. Preserve evidence and determine blast radius.
2. Make the smallest reversible change that addresses the proven cause.
3. Allow operator-managed resources to reconcile; do not permanently hand-edit generated deployments.
4. Rerun a minimal canary pipeline before rerunning the business workload.
5. Disable caching only where needed to ensure the repaired component executes.
6. Validate artifacts, metadata, logs, and terminal run status.
7. Document the change, owner, rollback, and preventive control.

**What not to do**

- Do not grant cluster-admin as a diagnostic shortcut.
- Do not delete the DSPA, database, PVC, or bucket before exporting evidence and understanding data-loss impact.
- Do not rotate credentials without coordinating all consumers.
- Do not assume a UI message is the root cause.
- Do not retry repeatedly without changing or measuring anything.
- Do not copy secrets into tickets or terminal transcripts.

**Verification gates**

- The original Pipeline YAML error symptom no longer reproduces.
- DSPA conditions show the expected healthy state for the installed release.
- Managed pods are Ready with stable restart counts.
- A canary run completes and all declared artifacts are present.
- The UI and CLI/API report consistent run status.
- No new warning events appear during the verification window.
- Monitoring and alerting cover the detected failure mode.

## 11. Topic-specific L3 diagnosis

The diagnosis must prove why **Pipeline YAML error** occurs, not merely show that a component is unhealthy.

**11.1 Establish blast radius**

- One task in one run.
- All tasks in one run.
- All runs for one pipeline version.
- All pipelines in one project.
- All projects on one cluster.
- Only scheduled runs.
- Only workloads using one service account, image, storage class, or object-store endpoint.
- Only workloads created after a specific change.

**11.2 Compare against a healthy control**

- Compare: OpenShift AI release and operator CSV.
- Compare: DSPA spec and status.
- Compare: service and endpoint selectors.
- Compare: pod service account and security context.
- Compare: image digest and pull secret linkage.
- Compare: resource requests, limits, quota, and LimitRange.
- Compare: node placement, taints, affinity, and storage topology.
- Compare: NetworkPolicy, DNS, proxy, and no_proxy.
- Compare: S3 endpoint, region, path-style mode, bucket, and prefix.
- Compare: metadata store mode and schema health.
- Compare: KFP SDK, Python, compiler output, and pipeline version.
- Compare: cache setting, retry policy, timeout, and schedule configuration.

## 14. Remediation strategy


### Contain

- Pause scheduled/recurring runs if they amplify impact.
- Prevent repeated retries from consuming scarce resources.
- Preserve pods and logs when retention is short.
- Communicate blast radius and data-integrity risk.

### Correct

- Regenerate from source with a supported KFP SDK, validate YAML and schema, inspect server-side dry-run errors, and avoid hand-editing compiled IR.
- Change only the proven broken dependency.
- Prefer declarative or operator-supported configuration.
- Use least privilege and approved images/registries.

### Recover

- Run the canary pipeline.
- Rerun or duplicate the affected run according to business policy.
- Verify artifacts and metadata before downstream promotion.
- Clean only confirmed orphaned resources.

### Prevent

- Create monitoring for the failure signature.
- Add preflight tests to CI/CD or GitOps.
- Pin SDK and image versions.
- Document ownership, escalation, and rollback.

## 17. Automation: safe health-check script

```bash
#!/usr/bin/env bash
set -euo pipefail

NS="${1:?usage: $0 <namespace>}"
OUT="${2:-pipeline-health-${NS}-$(date +%Y%m%d-%H%M%S)}"
mkdir -p "$OUT"

oc get dspa -n "$NS" -o yaml > "$OUT/dspa.yaml" 2>&1 || true
oc get deploy,sts,svc,route,endpoints,endpointslice -n "$NS" -o wide > "$OUT/control-plane.txt" 2>&1 || true
oc get pod -n "$NS" -o wide > "$OUT/pods.txt" 2>&1 || true
oc get pvc -n "$NS" -o wide > "$OUT/pvc.txt" 2>&1 || true
oc get sa,role,rolebinding -n "$NS" -o yaml > "$OUT/rbac.yaml" 2>&1 || true
oc get networkpolicy -n "$NS" -o yaml > "$OUT/networkpolicy.yaml" 2>&1 || true
oc get events -n "$NS" --sort-by=.lastTimestamp > "$OUT/events.txt" 2>&1 || true

while read -r pod; do
  [ -n "$pod" ] || continue
  oc get pod "$pod" -n "$NS" -o yaml > "$OUT/${pod}.yaml" 2>&1 || true
  oc logs "$pod" -n "$NS" --all-containers=true --prefix=true --timestamps \
    > "$OUT/${pod}.log" 2>&1 || true
  oc logs "$pod" -n "$NS" --all-containers=true --previous --prefix=true --timestamps \
    > "$OUT/${pod}.previous.log" 2>&1 || true
done < <(oc get pod -n "$NS" -o name | cut -d/ -f2)

grep -RniE 'error|failed|forbidden|denied|timeout|x509|backoff|oom|evict|invalid' "$OUT" \
  > "$OUT/error-index.txt" || true

tar -czf "${OUT}.tar.gz" "$OUT"
sha256sum "${OUT}.tar.gz" > "${OUT}.tar.gz.sha256"
echo "Created ${OUT}.tar.gz"
```

The script intentionally does not decode Secrets. Review the archive for accidental tokens or presigned URLs before sharing it.
