## Project from scratch
### Project objective: Deploy an explainer beside a predictor and validate explanation output
The lab uses a dedicated namespace so every generated object can be inspected and deleted safely. Replace example images, endpoints, credentials, storage locations, and model formats with values approved for your environment.
### Step 1: Create the project and baseline labels
```bash
oc new-project kserve-lab
oc label namespace kserve-lab app.kubernetes.io/part-of=kserve-deep-dive
oc label namespace kserve-lab environment=lab owner=platform-ai
```
### Step 2: Create a least-privilege service account
```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: model-runtime
  namespace: kserve-lab
automountServiceAccountToken: false
```
### Step 3: Create storage credentials safely
```bash
oc -n kserve-lab create secret generic model-storage --from-literal=AWS_ACCESS_KEY_ID='<replace>' --from-literal=AWS_SECRET_ACCESS_KEY='<replace>' --from-literal=AWS_S3_ENDPOINT='<replace>' --from-literal=AWS_DEFAULT_REGION='<replace>'
oc -n kserve-lab label secret model-storage opendatahub.io/dashboard=true
```
> Never commit real credentials. Prefer external secret management, short-lived credentials, workload identity where supported, and documented rotation.
### Step 4: Create or select a ServingRuntime
The focus of this module is **InferenceService predictor plus explainer configuration and background data access**. The example below is intentionally generic and must be aligned with the supported runtime shipped with your OpenShift AI release.
```yaml
apiVersion: serving.kserve.io/v1alpha1
kind: ServingRuntime
metadata:
  name: custom-mlserver
  namespace: kserve-lab
  labels:
    opendatahub.io/dashboard: "true"
  annotations:
    openshift.io/display-name: Custom MLServer Runtime
spec:
  supportedModelFormats:
    - name: sklearn
      version: "1"
      autoSelect: true
      priority: 10
  protocolVersions:
    - v2
  multiModel: false
  containers:
    - name: kserve-container
      image: quay.io/example/mlserver@sha256:REPLACE_WITH_APPROVED_DIGEST
      args:
        - --model_name={{.Name}}
        - --http_port=8080
        - --model_dir=/mnt/models
      ports:
        - name: h2c
          containerPort: 8080
          protocol: TCP
      securityContext:
        allowPrivilegeEscalation: false
        capabilities:
          drop: ["ALL"]
        runAsNonRoot: true
        seccompProfile:
          type: RuntimeDefault
```
### Step 5: Create the InferenceService
```yaml
apiVersion: serving.kserve.io/v1beta1
kind: InferenceService
metadata:
  name: demo-model
  namespace: kserve-lab
  annotations:
    serving.kserve.io/deploymentMode: Standard
spec:
  predictor:
    minReplicas: 1
    maxReplicas: 3
    model:
      modelFormat:
        name: sklearn
      runtime: custom-mlserver
      storageUri: s3://models/sklearn/iris/
      resources:
        requests:
          cpu: "250m"
          memory: "512Mi"
        limits:
          cpu: "1"
          memory: "2Gi"
```

## Production design guidance
1. Pin approved runtime images by digest and scan them continuously.
2. Define CPU, memory, ephemeral storage, and accelerator requests from measured startup and steady-state profiles.
3. Separate platform-admin runtime ownership from project-team InferenceService ownership.
4. Use quotas, limit ranges, priority classes, topology rules, and disruption budgets to control noisy-neighbor and maintenance risk.
5. Use internal endpoints by default; expose external routes only for approved consumers and protocols.
6. Make readiness budgets model-specific; large models often need startup probes that are much longer than web applications.
7. Create synthetic inference checks that validate response shape and semantic sanity, not only HTTP 200.
8. Record model artifact digest, runtime digest, configuration revision, and dataset/model version in deployment metadata.
9. Use canary or parallel endpoint patterns when a runtime or model change can alter output behavior.
10. Test rollback before production and retain the previous model/runtime artifacts for the declared rollback window.
11. Treat upstream-only configuration as experimental until supportability is confirmed for the exact Red Hat release.
## Security architecture
### Identity
Use distinct service accounts for runtime pods, CI/CD deployers, model consumers, and operators.
### RBAC
Grant permissions to the smallest namespace and resource set; remember that Kubernetes RBAC does not by itself authorize HTTP inference calls.
### Secrets
Keep credentials out of manifests and logs; rotate them and verify that failed init containers do not echo values.
### Network
Apply default-deny policies and explicitly allow DNS, object storage, required controller/webhook paths, and approved inference consumers.
### Endpoint authorization
Use OpenShift AI token authentication or an approved service-mesh/API-gateway policy, depending on supported architecture.
### TLS
Validate both external inference TLS and outbound model-storage TLS; never normalize `-k` as a production client practice.
### Supply chain
Pin image digests, verify signatures/SBOM where available, and restrict registries through policy.
### Audit
Capture who changed runtime/model configuration, when it reconciled, and which endpoint/model version served each release.
## Observability and SLOs
### Availability
Successful synthetic inference / total synthetic attempts over the SLO window.
### Readiness
Time from accepted configuration generation to Ready=True and usable endpoint.
### Latency
p50, p95, and p99 end-to-end latency, plus time-to-first-token and inter-token latency for generative runtimes.
### Throughput
Requests, inferences, samples, or tokens per second, measured with concurrency context.
### Errors
HTTP/gRPC errors, model protocol errors, authorization failures, timeouts, and invalid request rate.
### Saturation
CPU throttling, memory working set, GPU memory/utilization, queue depth, pending requests, storage throughput, and network saturation.
### Reconciliation
Controller error rate, reconciliation duration, work queue depth, and stale observed generation.
### Cost
Resource-hours and accelerator-hours per successful inference or per million tokens.

## Troubleshooting decision tree
### Symptom: API object missing
Check namespace, name, RBAC, API discovery, and whether GitOps applied the manifest.
### Symptom: Admission rejected
Read the exact schema/webhook message; use `oc explain` and server-side dry-run.
### Symptom: Generation not observed
Inspect controller health/logs, finalizers, conflicts, and operator degradation.
### Symptom: No pod created
Inspect runtime selection, generated Deployment, quota, and reconciliation conditions.
### Symptom: Pod Pending
Inspect scheduler events, requests, taints, selectors, PVC binding, quota, and accelerator availability.
### Symptom: Init container failing
Inspect storage credentials, endpoint, TLS trust, path, network policy, and disk space.
### Symptom: Pod Running but not Ready
Inspect startup/readiness probes, model load logs, protocol path, and service endpoints.
### Symptom: Ready internally but external call fails
Inspect Route/Gateway admission, DNS, TLS, authorization, network policy, and client path.
### Symptom: Inference returns 4xx
Validate endpoint path, payload schema, content type, model name, token, and API version.
### Symptom: Inference returns 5xx
Inspect runtime logs, model exceptions, OOM, dependency failure, and concurrency pressure.
### Symptom: Latency high
Separate client, router, queue, transformer, predictor, storage, CPU/GPU, and downstream latency.
### Symptom: Autoscaling ineffective
Check metrics API, resource requests, target metric, max replicas, quota, and scheduling capacity.

## L3 scenario workbook
The scenarios below are intentionally repetitive in method but varied in failure layer. Senior engineers should be able to execute the same disciplined evidence cycle under different symptoms without guessing or making uncontrolled changes.
### Scenario 001: Unsupported Explainer Type during admission

- **Operational context:** A `Explainer` workload shows symptoms linked to **background dataset** while the primary Kubernetes/OpenShift object under review is `PVC`.
- **Severity assumption:** Start as SEV-3; raise or lower severity only after measuring user impact, affected models, and error budget consumption.
- **Initial symptom:** The deployment is present, but readiness, route availability, inference correctness, or latency is outside the declared SLO.
- **First evidence command:** `oc get isvc demo -o yaml`
- **Expected healthy evidence:** Desired generation equals observed generation; relevant conditions are `True`; pods are Ready; services have endpoints; external routes are admitted when enabled.
- **Failure evidence:** Condition reason/message, warning events, container termination state, missing endpoints, authentication rejection, or resource pressure points to unsupported explainer type.
- **Hypothesis 1:** Configuration in the `PVC` is invalid or incompatible with the selected runtime.
- **Hypothesis 2:** The controller generated resources correctly, but an infrastructure dependency for background dataset is degraded.
- **Hypothesis 3:** The model server is healthy at process level but not ready at model or protocol level.
- **Disprove quickly:** Compare the current manifest with the last known-good Git revision and inspect managed fields before making changes.
- **Containment:** Stop rollout expansion, preserve logs/events, and restrict external traffic if responses may be incorrect or unsafe.
- **Corrective action:** Change one variable at a time, apply a minimal patch, wait for reconciliation, then re-check conditions and inference endpoints.
