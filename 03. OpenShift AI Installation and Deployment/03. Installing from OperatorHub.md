# 03. Installing from OperatorHub

## Purpose

Perform a console-based OperatorHub installation while preserving auditable OLM objects and repeatable CLI evidence.

This chapter is designed for senior OpenShift administrators, platform engineers, MLOps engineers, SREs, and technical leads. It treats installation as an auditable platform lifecycle rather than a one-time click-through exercise.

## Version and support guardrail

- Training baseline: Red Hat OpenShift AI Self-Managed 3.4 / 3.4.2 maintenance context (July 2026).
- Query the live `PackageManifest`, supported configuration matrix, release notes, and operator catalog before using any channel, CSV, API field, or dependency in production.
- Red Hat documents `fast`, `fast-x.y`, `stable`, `stable-x.y`, `eus-x.y`, and `alpha` channel families for OpenShift AI 3.4. Legacy `embedded` and `beta` channels should not be selected for new installations.
- OpenShift AI 3.4 uses `datasciencecluster.opendatahub.io/v2` for `DataScienceCluster` and `dscinitialization.opendatahub.io/v2` for `DSCInitialization` examples.
- A direct 2.25-to-3.x transition requires the published migration path; do not treat it as a routine in-channel patch update.

## Senior-level mental model
- Separate OLM installation state from OpenShift AI component state.
- A Succeeded CSV proves the operator bundle installed; it does not prove every OpenShift AI component is ready.
- A Running pod is not necessarily Ready, reachable, authorized, or functionally healthy.
- The DataScienceCluster is the component desired-state contract; the DSCInitialization is the platform initialization contract.
- Operator reconciliation is continuous. Manual edits to managed resources are usually temporary and can create configuration drift.
- Disconnected installation adds catalog, payload, trust, DNS, and credential failure domains.
- Production changes require prechecks, evidence capture, staged rollout, and post-change validation.
- Rollback is not synonymous with downgrading an Operator. Many operator upgrades are forward-only at the API/data level.

## L3 troubleshooting method
1. **Define the symptom:** State what is failing, who is affected, when it began, and the last known good state.
2. **Scope the blast radius:** Determine cluster, namespace, component, node, network path, storage class, and user scope.
3. **Build a timeline:** Correlate change records, OLM transitions, events, restarts, alerts, and certificate or credential changes.
4. **Collect evidence:** Export YAML, describe output, logs, events, metrics, route tests, DNS tests, and node diagnostics.
5. **Test the dependency chain:** Catalog → bundle → CSV → operator → DSCI/DSC → component workload → service → route → OAuth/API.
6. **Form and falsify hypotheses:** Change one variable at a time; prefer reversible tests over production mutations.
7. **Remediate safely:** Use declarative patches, change approval, backup, and explicit rollback boundary.
8. **Verify and prevent recurrence:** Repeat synthetic tests, confirm alerts clear, document root cause, and add guardrails.
