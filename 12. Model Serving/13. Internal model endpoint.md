## 1. Executive definition

Internal model endpoint focuses on private in-cluster access through Kubernetes Service discovery and namespace-aware network controls.
The main platform objects or components are ClusterIP Service, service DNS, ServiceAccount, and NetworkPolicy.
The hands-on implementation uses an application pod invoking a model without exposing a public route.
The primary operational risk is overly broad east-west access, DNS failures, namespace mismatch, and service-port confusion.
The principal signals are service reachability, connection latency, denied flows, DNS errors, and backend readiness.

At Corporate/L3 level, the objective is not merely to make one prediction succeed. The objective is to produce a deployment that is repeatable, supportable, secure, observable, capacity-tested, upgrade-aware, and reversible.

## 2. Current platform position and support awareness

- OpenShift AI model serving is based on KServe and normally gives each model a dedicated model server in the single-model serving architecture.
- KServe RawDeployment uses standard Kubernetes-style workload resources and does not provide the old Knative scale-to-zero behavior.
- KServe Serverless deployment mode is deprecated in current OpenShift AI release documentation.
- ModelMesh multi-model serving is deprecated; new designs should favor the current model serving platform unless a documented migration exception exists.
- Runtime auto-selection depends on a clear match among model type, model format, accelerator or hardware profile, and enabled serving runtime metadata.
- Custom serving runtimes are owned and maintained by the customer; image provenance, licensing, vulnerability management, compatibility, and lifecycle support must be documented.
- Metrics-based autoscaling described for OpenShift AI 3.5 is Technology Preview. Treat it as a lab or controlled evaluation unless the installed supported release states otherwise.
- Distributed inference capabilities can have Technology Preview or Developer Preview status depending on the specific feature and release.
- Always inspect release notes, support removals, known issues, and the exact cluster CRDs before applying examples.

## 4. Architecture model

- **Business/API consumer:** sends a predictive record, tensor, prompt, or streaming request and expects a stable contract.
- **DNS and external entry:** resolves an internal service name or an external Route/Gateway hostname.
- **Authentication and authorization:** validates the caller and enforces which identity may invoke which model.
- **Traffic policy:** applies TLS, timeout, request-size, rate, retry, and routing behavior.
- **Kubernetes Service:** selects ready predictor endpoints and provides stable virtual addressing.
- **Predictor pod:** contains the selected serving runtime and loaded model.
- **Storage initializer or model loader:** retrieves artifacts from S3-compatible storage, PVC, URI repository, or OCI image as supported.
- **ServingRuntime:** declares the runtime image, protocol, ports, model formats, and template behavior.
- **InferenceService:** declares model location, runtime, resources, replicas, deployment mode, and desired serving state.
- **KServe controller:** validates and reconciles desired state into generated Kubernetes resources.
- **OpenShift scheduler:** places pods based on requests, quota, affinity, taints, topology, and accelerator availability.
- **Monitoring stack:** scrapes runtime, workload, route/gateway, and accelerator metrics.
- **Logging stack:** collects runtime and platform events while enforcing data minimization.
- **GitOps repository:** stores approved manifests, environment overlays, model references, image digests, and rollback history.
- **Model registry and governance:** records ownership, lineage, approval, version, documentation, and intended use.

### 4.1 Control-plane sequence

1. An engineer commits or applies the desired ServingRuntime and InferenceService configuration.
2. The API server validates schema, admission policy, RBAC, quota, and object metadata.
3. The KServe controller observes the new or changed InferenceService.
4. The controller resolves the selected runtime and model format compatibility.
5. The controller generates or updates Kubernetes workload and network resources.
6. The scheduler evaluates node capacity, accelerator resources, affinity, taints, tolerations, and topology.
7. The model artifact is mounted, pulled, copied, or loaded using the selected storage method.
8. The model server starts, allocates memory, loads weights or model objects, and initializes the inference API.
9. Readiness becomes true only when the server can safely accept traffic.
10. The Service publishes ready endpoints; a Route or Gateway can then forward external traffic.
11. Monitoring begins collecting availability, runtime, request, and accelerator signals.
12. GitOps and release controls record the exact model, runtime image digest, manifest, and approval evidence.

### 4.2 Data-plane sequence

1. The client resolves the endpoint and establishes TCP/TLS or HTTP/2.
2. The entry layer validates credentials and policy when authentication is enabled.
3. The request is checked for method, path, host, content type, size, and schema.
4. The Service selects a ready backend.
5. The runtime performs preprocessing and converts the request into model inputs.
6. The model executes on CPU, GPU, or another supported accelerator.
7. The runtime performs postprocessing, serialization, and optional streaming.
8. The response returns through the same network path.
9. Metrics, logs, and optional traces record latency, status, saturation, and correlation data.
10. SLO evaluation and alerts identify abnormal latency, throughput, error, or availability behavior.

### 7.10 Golden request validation script

```bash
#!/usr/bin/env bash
set -Eeuo pipefail

: "${ENDPOINT:?Set ENDPOINT}"
: "${TOKEN:?Set TOKEN}"

tmp_body="$(mktemp)"
trap 'rm -f "${tmp_body}"' EXIT

http_code="$(
  curl --silent --show-error     --output "${tmp_body}"     --write-out '%{http_code}'     --connect-timeout 5     --max-time 60     -H "Authorization: Bearer ${TOKEN}"     -H "Content-Type: application/json"     "${ENDPOINT}"     --data-binary @tests/golden-request.json
)"

case "${http_code}" in
  200)
    python3 tests/assert_response.py "${tmp_body}"
    ;;
  401|403)
    echo "Authentication or authorization failure: HTTP ${http_code}" >&2
    exit 20
    ;;
  429)
    echo "Capacity or rate policy rejected the request: HTTP 429" >&2
    exit 30
    ;;
  500|502|503|504)
    echo "Server or upstream failure: HTTP ${http_code}" >&2
    cat "${tmp_body}" >&2
    exit 40
    ;;
  *)
    echo "Unexpected HTTP status: ${http_code}" >&2
    cat "${tmp_body}" >&2
    exit 50
    ;;
esac
```

## 8. Implementation decisions

| Decision | Corporate/L3 requirement |
|---|---|
| Model source | Use versioned S3 object prefixes, immutable OCI digests, or controlled PVC paths. Record checksum and lineage. |
| Runtime | Prefer a supported preinstalled runtime. Use a custom runtime only with an explicit ownership and lifecycle model. |
| Protocol | Select REST or gRPC according to client ecosystem, streaming needs, payload size, latency, and gateway support. |
| Deployment mode | Use the currently supported RawDeployment model for standard Kubernetes behavior; do not design new dependencies around deprecated Serverless mode. |
| Resources | Set requests from measured steady-state demand and limits from tested safe peaks. Include model-load memory, not only request-time memory. |
| Accelerator | Use approved hardware profiles and supported accelerator Operators. Validate driver, runtime, device plugin, and telemetry. |
| Storage | Measure artifact download, mount, and load time. Ensure credentials and CA trust are available without embedding them in images. |
| Availability | Set minimum replicas and rollout strategy according to SLO and available duplicate accelerator capacity. |
| Exposure | Default to internal-only. Add an external Route or Gateway only after threat modeling and approval. |
| Authentication | Use short-lived workload identity or service-account tokens. Enforce authorization at the endpoint entry layer. |
| NetworkPolicy | Allow only required namespaces, service accounts, ports, DNS, object storage, registry, and monitoring flows. |
| Observability | Collect controller, pod, route/gateway, runtime, model, client, and accelerator signals. |
| Rollback | Version model artifact, runtime image, manifests, API schema, secrets, and policies as one release unit. |
| Testing | Run schema, correctness, negative, security, resilience, and load tests before promotion. |
| Support | Document whether each feature is GA, deprecated, Technology Preview, Developer Preview, or unsupported custom content. |

## 9. Security and governance controls

1. Use immutable container image digests and verify signatures or trusted provenance where organizational tooling supports it.
2. Restrict model-serving images to approved registries.
3. Scan runtime and model-packaging images continuously.
4. Run as a non-root UID compatible with OpenShift security constraints.
5. Use read-only root filesystem where the runtime supports it.
6. Drop Linux capabilities unless a documented runtime requirement exists.
7. Do not mount the service account token unless the pod requires Kubernetes API access.
8. Separate model-fetch identity from client inference identity.
9. Use short-lived tokens and workload identity rather than static long-lived bearer tokens.
10. Never store credentials in Git, model artifacts, notebooks, runtime images, shell history, or request examples.
11. Use external secret management when available and approved.
12. Restrict ingress with NetworkPolicy and route/gateway authorization policy.
13. Restrict egress to object storage, registries, DNS, telemetry, and approved dependencies.
14. Protect external endpoints with TLS and validate certificate rotation.
15. Set request body, header, message, context, and token limits.
16. Apply rate limits and concurrency limits based on tested capacity.
17. Define prompt and response logging policy; default to metadata-only logging for sensitive use cases.
18. Classify the model, prompts, features, outputs, and embeddings according to enterprise data policy.
19. Maintain a model card with owner, purpose, prohibited use, data lineage, risk, and validation evidence.
20. Record model artifact checksum, image digest, runtime version, configuration commit, and deployment time.
21. Separate developer, approver, and production deployer permissions.
22. Use namespace quotas and accelerator quotas to prevent resource monopolization.
23. Audit Route/Gateway creation and changes to authentication annotations or policy.
24. Create alerts for unexpected public exposure, auth bypass, high denial rate, and anomalous clients.
25. Test revocation and incident credential rotation.
26. Test backup and recovery of manifests, policies, certificates, and version metadata.
27. Review custom runtime licensing and third-party support obligations.
28. Document preview features and prevent accidental promotion into production.
29. Retain only the logs and metrics needed for operations and compliance.
30. Perform periodic access review for project users, service accounts, and cluster-scoped runtime administrators.

## 10. Resource sizing method

1. Measure model artifact size on storage.
2. Measure peak resident memory while loading the model.
3. Measure steady-state memory after initialization.
4. Measure CPU required for preprocessing, tokenization, serialization, and networking.
5. Measure accelerator memory including model weights, runtime overhead, KV cache, and fragmentation.
6. Measure startup duration for cold image pull, model transfer, and model initialization.
7. Run a warm-up request set before recording performance.
8. Increase concurrency gradually and record latency, throughput, queue depth, errors, and utilization.
9. Identify the sustainable operating point before p95 latency or error rate violates the SLO.
10. Add headroom for traffic variance, node maintenance, rollout overlap, and failover.
11. Set requests to obtain reliable scheduling and limits to prevent unsafe contention.
12. Validate ResourceQuota and LimitRange behavior.
13. Validate topology, taints, tolerations, and accelerator scheduling.
14. Repeat tests after runtime, model, driver, kernel, storage, network, or hardware changes.
15. Record the test dataset, prompt lengths, output lengths, concurrency, and environment for reproducibility.

## 13. Deployment strategies and rollback

1. Rolling update keeps old pods available until new pods are ready but may require roughly double the requested CPU, memory, or accelerator capacity during transition.
2. Recreate terminates the old workload before the new workload is ready and conserves scarce resources at the cost of downtime.
3. For large GPU models, confirm whether the namespace and cluster can host two copies before selecting rolling update.
4. Treat the model artifact, runtime image, runtime arguments, resource profile, API contract, and security policy as one versioned release.
5. Use immutable model prefixes or OCI digests so rollback does not depend on mutable storage content.
6. Run golden, negative-auth, schema, latency, and error checks before shifting production traffic.
7. Preserve the previous release until the observation window closes.
8. Rollback through the owning InferenceService or GitOps source, not by editing generated Deployments.
9. After rollback, verify correctness and SLO recovery rather than considering pod readiness sufficient.
10. Record the failed release evidence and create a prevention action.

### 13.1 Rollback command pattern

kustomize build overlays/prod | oc apply -f -

oc wait   --for=condition=Ready   inferenceservice/<model-name>   -n <namespace>   --timeout=20m

./tests/rollback-verify.sh

## 14. Troubleshooting methodology

1. State the exact failing request, endpoint, namespace, model, runtime, timestamp, and expected result.
2. Classify the failure as DNS, TLS, authentication, authorization, route/gateway, service, pod, storage, model, runtime, capacity, or client.
3. Capture current desired state from Git and live state from the API.
4. Inspect InferenceService conditions before inspecting generated objects.
5. Inspect events before restarting or deleting pods.
6. Check scheduling and quota before investigating application logs for a Pending pod.
7. Check init and storage-initializer logs before runtime logs when model transfer is incomplete.
8. Test the internal service before the external route to separate data-plane layers.
9. Test an authorized and unauthorized request to separate connectivity from policy.
10. Use a known-good golden request to eliminate client schema variation.
11. Check endpoint paths and model names against the selected runtime protocol.
12. Measure CPU, memory, GPU, queue, and latency during the incident.
13. Change one variable at a time and record the result.
14. Use rollback when the blast radius or SLO impact is unacceptable.
15. Create a timeline, root cause, contributing factors, corrective action, and prevention plan.

## 15. Failure signatures and likely causes

| Signature | Investigate first |
|---|---|
| Pending | insufficient CPU, memory, GPU, quota, affinity mismatch, taint, PVC binding, or topology constraint |
| ImagePullBackOff | invalid image, denied registry, missing pull secret, network/proxy, CA trust, or architecture mismatch |
| Init failure | storage credentials, endpoint, certificate, object path, PVC mount, checksum, or disk capacity |
| CrashLoopBackOff | invalid runtime arguments, model incompatibility, OOM, missing library, permission, or bad command |
| Ready=False | model still loading, readiness path wrong, runtime unhealthy, dependency unavailable, or generated service mismatch |
| 404 | wrong host, path, model name, route target, or protocol |
| 401 | missing, malformed, expired, wrong-audience, or untrusted token |
| 403 | authenticated identity lacks authorization or policy denies the request |
| 429 | rate limit, concurrency limit, or capacity protection |
| 502 | gateway cannot communicate correctly with backend or protocol mismatch |
| 503 | no ready endpoints, route/gateway backend unavailable, or rollout gap |
| 504 | gateway timeout, slow model, queue saturation, long generation, or network dependency |
| TLS failure | hostname mismatch, expired certificate, untrusted CA, incomplete chain, or protocol policy |
| High p95/p99 | queueing, cold start, CPU throttle, GPU saturation, storage, network, long prompts, or output length |
| Low GPU use with queue | CPU/tokenizer bottleneck, batching issue, tiny requests, synchronization, or placement problem |
| OOMKilled | model plus runtime plus cache exceeds limit, fragmentation, context length, or batch/concurrency too high |
