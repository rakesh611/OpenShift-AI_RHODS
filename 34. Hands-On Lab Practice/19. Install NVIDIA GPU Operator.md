# 19. Install NVIDIA GPU Operator

> This chapter is written as a standalone enterprise lab, implementation guide, operational runbook,
> troubleshooting workbook, interview preparation guide, and production-hardening checklist.

## 1. Executive objective

Install Node Feature Discovery and the NVIDIA GPU Operator, create the required operands, verify
driver/device-plugin/DCGM health, and expose allocatable GPUs.

**Primary resource or control:** NFD Operator, NVIDIA GPU Operator, NodeFeatureDiscovery, ClusterPolicy

**Primary namespace or scope:** `openshift-nfd and nvidia-gpu-operator`

The lab starts from an empty or minimally prepared environment and ends only after the change is
validated functionally, operationally, securely, and from a rollback perspective. The expected standard
is that another senior engineer can reproduce install nvidia gpu operator by following this file.

## 12. Manifest validation and safe apply

```bash
# Syntax and schema checks
yamllint manifest.yaml 2>/dev/null || true
oc apply --dry-run=client -f manifest.yaml -o yaml
oc apply --dry-run=server -f manifest.yaml -o yaml

# Diff before apply
oc diff -f manifest.yaml || true

# Apply and record the server-accepted object
oc apply -f manifest.yaml
oc get -f manifest.yaml -o yaml > server-accepted.yaml

# Observe reconciliation
oc get events -n "$LAB_PROJECT" --sort-by=.lastTimestamp
oc get pods -n "$LAB_PROJECT" -w
```

Validation interpretation:

- Client-side validation catches basic syntax and local schema errors.
- Server-side validation catches served-version, admission, policy, and webhook errors.
- `oc diff` exposes ownership conflicts and unintended field changes.
- The server-accepted object is more valuable than the submitted file during troubleshooting.
- Reconciliation is complete only when the controlling CR condition and generated workload are healthy.

## 16. Failure-injection tests

- [ ] FI01: Use an invalid resource name and confirm admission rejects it.
- [ ] FI02: Remove one required permission from a test service account and confirm a controlled 403.
- [ ] FI03: Use an invalid S3 key in a temporary secret and identify the exact failing component.
- [ ] FI04: Block one dependency with a temporary NetworkPolicy and observe timeout evidence.
- [ ] FI05: Set a request above quota and confirm the API or scheduler failure is explicit.
- [ ] FI06: Use a nonexistent image tag and capture ImagePullBackOff evidence.
- [ ] FI07: Use a wrong model path or artifact checksum and confirm integrity checks fail.
- [ ] FI08: Restart a generated pod and confirm the controller restores it.
- [ ] FI09: Revoke a short-lived token and confirm the endpoint rejects it.
- [ ] FI10: Revert the Git commit and confirm the previous healthy state is restored.

Run failure injection only in a lab or approved non-production window. Every test must include a stop
condition, expected failure signal, rollback command, and evidence capture.

- Declare rollback if the controlling CR does not progress, the workload cannot become Ready, security controls fail, or the SLO regression exceeds the approved threshold.
- Capture evidence before rollback.
- Revert one change set rather than applying unrelated fixes.
- Verify the previous state functionally and operationally.
- Record whether data or artifacts created during the failed change require reconciliation.

```bash
# GitOps-oriented rollback
git log --oneline -10
git revert <bad-commit>
git push origin main
argocd app diff rhoai-lab
argocd app sync rhoai-lab

# Direct-manifest rollback for lab use
oc apply -f last-known-good.yaml
```

## 18. Production hardening checklist

- [ ] H01: Pin Operator channels and document the upgrade path.
- [ ] H02: Pin images and model artifacts by immutable digest or version.
- [ ] H03: Use external production-grade databases where the component requires persistence.
- [ ] H04: Use S3 bucket versioning, encryption, lifecycle controls, and least-privilege prefixes.
- [ ] H05: Use enterprise CA trust and reject insecure TLS workarounds.
- [ ] H06: Use project-scoped RBAC and avoid individual cluster-admin grants.
- [ ] H07: Apply default-deny network policies with explicit dependency allowances.
- [ ] H08: Set requests, limits, quotas, and capacity alerts.
- [ ] H09: Configure PodDisruptionBudgets or replicas where supported and meaningful.
- [ ] H10: Back up API resources and all external state as one recovery design.
- [ ] H11: Test restore into an isolated namespace or cluster.
- [ ] H12: Create SLOs and alerts with runbook links.
- [ ] H13: Define image vulnerability and signature gates.
- [ ] H14: Define model approval, promotion, rollback, and retirement policy.
- [ ] H15: Review known issues for the installed RHOAI minor before rollout.

## 19. Known design risks

- Risk R01: Kernel-driver incompatibility.
- Risk R02: MCP degraded during driver toolkit changes.
- Risk R03: Secure Boot or unsupported GPU.
- Risk R04: Proxy/registry access blocks operand images.
- Risk R05: A dashboard workflow may generate fields that are not obvious from a minimal CR.
- Risk R06: An Operator may reconcile fields that GitOps also attempts to own.
- Risk R07: A healthy API object may still depend on external S3, database, DNS, or CA state.
- Risk R08: A rollback can restore configuration without restoring compatible data.
- Risk R09: Mutable tags and unversioned model paths make root-cause analysis unreliable.
- Risk R10: Namespace deletion can remove PVCs, secrets, service accounts, and audit context.

```text
Start
  |

  |      +-- No -> schema, served API version, admission, policy, RBAC
  |      +-- Yes
  |
  +-- Does the controlling CR show Ready/Available?
  |      +-- No -> conditions, events, controller logs, prerequisites
  |      +-- Yes
  |
  +-- Were generated workloads created?
  |      +-- No -> controller ownership, labels, webhook, namespace scope
  |      +-- Yes
  |
  +-- Are pods scheduled and images pulled?
  |      +-- No -> quota, taints, affinity, storage, image auth, GPU
  |      +-- Yes
  |
  +-- Are init containers, probes, and application process healthy?
  |      +-- No -> S3, TLS, permissions, runtime arguments, model load
  |      +-- Yes
  |
  +-- Is the service reachable and authorized?
  |      +-- No -> Service/Endpoints, Route/Gateway, NetworkPolicy, authn/authz
  |      +-- Yes
  |
  +-- Does it meet correctness, latency, security, and recovery requirements?
         +-- No -> tune or redesign with evidence
         +-- Yes -> close change and retain evidence
```

## 25. Day-2 operations runbook

| Frequency | Required action |
|---|---|
| Daily | Check Ready conditions, pod restarts, Warning events, endpoint availability, and capacity. |
| Weekly | Review image and model versions, failed jobs, quota headroom, certificate expiry, and backup status. |
| Monthly | Review access, network flows, storage growth, SLO trends, alert quality, and dependency lifecycle. |
| Quarterly | Test restore, rotate credentials, review known issues, and validate runbooks with another engineer. |
| Before upgrade | Export CRs, read release notes, validate prerequisites, create backups, and define rollback. |
| After upgrade | Confirm served APIs, component versions, generated resources, functional tests, and metrics. |
| During incident | Freeze unrelated changes, capture evidence, establish timeline, apply reversible mitigation. |
| After incident | Document root cause, corrective action, owner, due date, and validation of prevention. |

## 29. Glossary

| Term | Meaning |
|---|---|
| CRD | CustomResourceDefinition; extends the Kubernetes API. |
| CR | Custom resource; an instance reconciled by a controller. |
| DSPA | DataSciencePipelinesApplication; namespace-scoped pipelines stack. |
| DSC | DataScienceCluster; controls OpenShift AI component management state. |
| InferenceService | KServe resource describing a model-serving deployment. |
| ServingRuntime | KServe runtime template defining how a model server runs. |
| Hardware profile | Governed compute and accelerator configuration exposed to users. |
| ModelCar | OCI-based model storage format used for faster and portable KServe deployment. |
| RPO | Maximum acceptable data loss measured in time. |
| RTO | Maximum acceptable time to restore service. |
| SLO | Measurable reliability objective for a service. |
| SCC | OpenShift SecurityContextConstraints. |
| NFD | Node Feature Discovery, which labels hardware capabilities. |
| DCGM | NVIDIA Data Center GPU Manager metrics and diagnostics. |
| TrustyAI | OpenShift AI capability for model bias and data-drift monitoring. |
